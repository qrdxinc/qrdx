このガイドを終えると、QRエディター、アカウント、スキャンアナリティクス付きの動的QRコード、ホスト型ページ、ワークスペース、保存済みテーマを備えたQRdxが、自分で管理するPostgresデータベース上の独自URLで動くようになります。Docker Composeを使う場合の所要時間は約30分で、そのほとんどは最初のイメージのビルドです。

ウェブアプリは AGPL-3.0 ライセンスのオープンソースです。ただし、ワークスペースのシングルサインオンと監査ログの2つは例外です。これらは `ee/` フォルダーにあり、QRdx商用ライセンスの対象で、ライセンスキー（`QRDX_EE_LICENSE`）を設定しない限り無効です。本番環境で使うにはQRdxとの書面による契約が必要です。詳しくは [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md) をご覧ください。[`qrdx` React ライブラリ](/docs/getting-started)や [CLI](/docs/developers/cli) を使うだけなら、これらは一切不要です。どちらもMITライセンスで、バックエンドなしでどこでも動作します。リポジトリの各部分とそのライセンスは、[QRdxのオープンソース](/open-source-qr-code-generator)に一覧があります。

<Callout type="warn" title="Docker環境は新しい機能です">
  手順どおりに動かない場合は、実行したコマンドとその出力を添えて[Issueを作成](https://github.com/qrdxinc/qrdx/issues)してください。
</Callout>

## 始める前に [#before-you-start]

- Compose v2 と BuildKit が使えるDocker（Docker Desktop と最新のDocker Engineには両方含まれています）。手動セットアップの場合は、Node.js 22（22.22.3 以降）と [Bun](https://bun.com/docs/installation) 1.4。
- イメージのビルド中にDockerが使えるメモリが8 GB以上。
- アカウントを作成できるサインイン手段：GitHubまたはGoogleのOAuthアプリ、もしくはメールのサインインコードを送るための [Resend](https://resend.com)。サインインコードがメールで送信されるのは、`NEXT_PUBLIC_APP_URL` が `localhost` ではない場合だけです。`bun run dev` ではコードがターミナルに表示されますが、Dockerイメージでは表示されません。そのため、ローカルでDockerを試す場合はGitHubまたはGoogleでのサインインが必要です。
- Postgres：`docker-compose.yml` に含まれるコンテナ、または [Neon](https://neon.tech) のデータベース。
- ローカルでのテスト以外では、ドメインと、HTTPSを終端するリバースプロキシ。

ドキュメントはセルフホストのインスタンスには含まれません。インスタンスは、ドキュメントへのすべてのリンク（`/docs` とその配下のページ、それらのMarkdown版、`/llms-full.txt`）を、qrdx.dev上の同じページに転送します。

### データベース接続のしくみ [#how-the-database-connection-works]

アプリは、NeonのサーバーレスHTTPドライバー経由でPostgresに接続します。

- **Neon：** そのまま使えます。`DATABASE_URL` にNeonの接続文字列を設定してください。
- **通常のPostgres：** 手前にNeon互換のHTTPプロキシが必要です。`docker-compose.yml` はプロキシ（[local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)）を1つ起動し、アプリがクエリをそこへ送るよう `DATABASE_HTTP_ENDPOINT` を設定します。

スキーマは `packages/database/schema.ts` から取得され、`drizzle-kit push` で適用されます。手動で実行するマイグレーションファイルはありません。

## Docker Composeでのクイックスタート [#quick-start-with-docker-compose]

### 1. リポジトリをクローンする [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. 環境を設定する [#2-configure-the-environment]

サンプルファイルを、Composeが読み込むリポジトリのルートにコピーし、セッションシークレットを生成します。

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

`.env` を開いて、次の値を設定してください。それ以外の行はコメントアウトのままで構いません。

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

各値の入手先は次のとおりです。

| 変数 | 入手先 |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | インスタンスの公開URL。末尾にスラッシュは付けません。ローカルでのテストでは `http://localhost:3000` のままにします。 |
| `BETTER_AUTH_URL` | 同じ値です。この行のコメントを外してください。 |
| `BETTER_AUTH_SECRET` | `openssl rand -base64 32` の出力。 |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | コールバックURLが `<your url>/api/auth/callback/github` の [GitHub OAuthアプリ](https://github.com/settings/developers)。 |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | GitHubの代わりに使う場合：リダイレクトURIが `<your url>/api/auth/callback/google` の [Google OAuthクライアント](https://console.cloud.google.com/apis/credentials)。 |

`DATABASE_URL` はそのままにしてください。Composeはアプリを専用のPostgresコンテナに接続し、`.env` の値は無視します。データベースのパスワードを変更するには、最初の起動前に `POSTGRES_PASSWORD` を設定します。

### 3. スタックを起動する [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

このコマンドはイメージをビルドし、Postgresとプロキシを起動して、1回限りの `migrate` サービス（`drizzle-kit push`）を実行し、その後ポート3000でアプリを起動します。最初のビルドには数分かかります。完了すると、4つのサービスは次のように表示されます。

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

`migrate` は終了するのが正常です。スキーマを同期して停止します。スキーマの同期とアプリの起動の様子を確認するには、次を実行します。

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. サインインする [#4-sign-in]

ブラウザーで `NEXT_PUBLIC_APP_URL` を開き、GitHub、Google、またはメールコードでサインインします。アカウントは初回のサインイン時に作成されます。

### 5. 自分を管理者にする [#5-make-yourself-an-admin]

手順4で作成したアカウントのメールアドレスを `.env` に追加します。

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

変更を読み込ませるためにアプリのコンテナを作り直し、サインインして `/admin` を開きます。

```bash title="Terminal"
docker compose up -d app
```

このメールアドレスは、初めて `/admin` を開いたときに管理者になります。`ADMIN_USER_IDS` も、ユーザーIDを使う点以外は同じように動作します。

## Neonなどのマネージド型Postgresを使う [#use-neon-or-another-managed-postgres]

付属のPostgresを使わず、アプリのイメージだけを実行することもできます。`.env` の `DATABASE_URL` にNeonの接続文字列を設定し、`DATABASE_HTTP_ENDPOINT` は未設定のままにしてください。

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

スキーマは、マイグレーター用イメージを使って、最初に1回、そして更新のたびに適用します。

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Node.jsでの手動セットアップ [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

本番環境では、アプリをビルドしてから起動します。

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` はNeonのドライバーで接続するため、Neonデータベースが必要です。代わりにローカル開発でDockerのPostgresを使うには、`docker compose up -d db db-proxy` で起動し、`docker compose run --rm migrate` でスキーマを適用して、`apps/app/.env.local` に次の値を設定します。

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

## 環境変数 [#environment-variables]

[`apps/app/.env.example`](https://github.com/qrdxinc/qrdx/blob/main/apps/app/.env.example) には、すべての変数と、その入手先のメモが載っています。アプリは起動時にすべての値を検証し、必須の値がない場合や値が無効な場合は、該当する変数名を示して起動を中止します。

### 必須 [#required]

| 変数 | 用途 |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | インスタンスの公開URL |
| `DATABASE_URL` | Postgresの接続文字列（Composeが設定します） |
| `BETTER_AUTH_SECRET` | セッションとCookieの署名に使います |

ユーザーがサインインできるように、OAuthプロバイダー（GitHubまたはGoogle）を1つ、またはメールのサインインコード用にResendを追加してください。

### オプションのサービス [#optional-services]

各変数は、対応する機能だけを有効にします。空の値は未設定として扱われます。設定されていても無効な値（URLではないURLや、短すぎるキーなど）の場合は、アプリが変数名を示して停止します。

| サービス | 変数 | 未設定の場合 |
| --- | --- | --- |
| GitHubサインイン | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | GitHubサインインは使えません |
| Googleサインイン | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Googleサインインは使えません |
| 認証のベースURL | `BETTER_AUTH_URL` | リクエストごとに推測され、ログに警告が出ます |
| 管理パネル | `ADMIN_EMAILS`, `ADMIN_USER_IDS` | `/admin` を開けるユーザーはいません |
| ワークスペースのシングルサインオン | `QRDX_EE_LICENSE` | シングルサインオンは無効のままです。**Sign in with SSO** も SSO設定も表示されず、サインイン用のルートも存在しません。SSOは QRdx商用ライセンスの対象である `ee/` フォルダーに含まれるため、本番で使うには QRdx との書面による契約が必要です。[シングルサインオン](/docs/help/teams/single-sign-on)をご覧ください |
| ワークスペースの監査ログ | `QRDX_EE_LICENSE` | 監査ログは無効のままです。何も記録されず、**設定** → **監査ログ** も表示されません。シングルサインオンと同様に、QRdx商用ライセンスの対象である `ee/` フォルダーに含まれます。記録は {facts.auditLogRetentionDays} 日間保持され、それより古いものは[スケジュールされたWebhookジョブ](#scheduled-jobs)が削除します。[監査ログ](/docs/help/teams/audit-log)をご覧ください |
| AIテーマ、プロンプト強化、AI QRアート（Vercel AI Gateway） | `AI_GATEWAY_API_KEY` | AIリクエストは失敗し、AIのページはナビゲーションとサイトマップから外れます。エディターは通常どおり動作します。キーはご自身のVercelアカウント（AI Gateway、API keys）で作成してください。利用料金はそのアカウントのAI Gatewayクレジットに請求され、アプリ自体をVercelで動かす必要はありません。各タスクのモデルは `apps/app/lib/ai/models.ts` で設定します |

| メール（Resend） | `RESEND_API_KEY`, `EMAIL_FROM` | メールは送信されずログに記録されるため、メールのサインインコードは送れません。チームへの招待にはコピーできるリンクを使います。[通知](/docs/notifications#self-hosting)をご覧ください |
| Vercelのカスタムドメイン | `VERCEL_API_TOKEN`, `VERCEL_PROJECT_ID`, `VERCEL_TEAM_ID` | Vercel以外では未設定のままにしてください。その場合、ドメインはDNSの `TXT` レコードで検証されます。[カスタムドメイン](/docs/custom-domains#self-hosting)をご覧ください |
| ワンクリックDNS設定（Domain Connect） | `DOMAIN_CONNECT_PROVIDER_ID`, `DOMAIN_CONNECT_SERVICE_ID`, `DOMAIN_CONNECT_PRIVATE_KEY` | **Set up with …** ボタンは表示されず、ユーザーがDNSレコードを自分で追加します。各DNSプロバイダーに承認された独自のDomain Connectテンプレートと、DNSに登録した公開鍵が必要です。[カスタムドメイン](/docs/custom-domains#self-hosting)をご覧ください |
| スケジュールジョブ | `CRON_SECRET` | 本番では[週次ダイジェストとWebhook再試行のルート](#scheduled-jobs)が `401` を返すため、ダイジェストは送信されず、失敗したWebhookは再試行されず、{facts.auditLogRetentionDays} 日より古い監査ログの記録も削除されません |

連携を有効にしたら、本番では `INTEGRATION_ENCRYPTION_KEY` を必ず設定してください。保存されたトークンの暗号化に使われます。`openssl rand -hex 32` で生成できます。

<Callout type="info" title="NEXT_PUBLIC_* の値はビルド時に固定されます">
  `NEXT_PUBLIC_*` の値は、アプリのビルド時にブラウザー用バンドルへ埋め込まれるため、変更するには再ビルドが必要です。Dockerビルドが `.env` から読み込むのは、次の6つだけです。これらは `docker-compose.yml` でビルド引数として渡されます。`NEXT_PUBLIC_APP_URL`、`NEXT_PUBLIC_POSTHOG_KEY`、`NEXT_PUBLIC_POSTHOG_HOST`、`NEXT_PUBLIC_FEATUREBASE_APP_ID`、そして2つのProの製品IDです。それ以外の値（Businessの製品ID、`NEXT_PUBLIC_QRDX_EUR_PRICES`、`NEXT_PUBLIC_SHORT_LINK_BASE_URL`、Turnstileのサイトキー、UmamiのID）をDockerイメージに設定するには、`docker-compose.yml` の `app` サービスの `build.args` に追加し、Dockerfileのビルドステージにも `ARG` として追加してから、`docker compose up -d --build` を実行してください。手動セットアップでは、すべて `apps/app/.env.local` から読み込まれます。
</Callout>

### スケジュールジョブ [#scheduled-jobs]

定期的な処理は2つのルートが行います。`/api/cron/webhooks` は失敗したWebhookの配信を再試行し、古い監査ログの記録を削除します。`/api/cron/digest` は週次ダイジェストを送信します。Vercelでは `apps/app/vercel.json` がこれらをスケジュールします。それ以外の環境では、ご自身で呼び出さない限り何も呼び出されません。`CRON_SECRET` を設定し、お使いのスケジューラーからそれを付けて両方を呼び出してください。

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

ヘッダーがない場合、本番ではルートは `401` を返します。ダイジェストの `shard` パラメーターについては、[通知](/docs/notifications#self-hosting)で説明しています。

## リバースプロキシとHTTPS [#reverse-proxy-and-https]

TLSを終端するCaddy、nginx、Traefikなどのリバースプロキシをアプリの前段に置き、ポート3000をインターネットに直接公開しないでください。レート制限、セキュリティメール、[監査ログ](/docs/help/teams/audit-log)は、クライアントIPをまず `X-Real-IP` から、次に `X-Forwarded-For` の最初のアドレスから読み取ります（Vercelでは、その間に `X-Vercel-Forwarded-For` が入ります）。そのため、プロキシがこれらのヘッダーを設定し、アプリにはプロキシ経由でのみ到達できるようにしてください。プロキシには、接続を受け取った元のアドレスを `X-Real-IP` に設定させてください。`X-Forwarded-For` に追記するだけのプロキシでは、クライアントが任意のアドレスを先頭に置けてしまいます。

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

Caddyはこれらのヘッダーをデフォルトで設定します。HTTPSが動作したら、`NEXT_PUBLIC_APP_URL` と `BETTER_AUTH_URL` を `https://` のURLに変更し、OAuthのコールバックURLを更新して、再ビルドしてください。

### Content-Security-Policy [#content-security-policy]

本番ビルドでは、QRdx自身のページでContent-Security-Policyを送信します。サインイン後のページにはリクエストごとに新しいスクリプトnonceが付き、事前レンダリングされたページにはスクリプトホストの許可リストが適用されます。ホスト型ページ（`/p`）には緩いポリシーが適用されます。所有者のピクセルが動作し、どこからでもメディアを埋め込むためです。リバースプロキシでも `Content-Security-Policy` を設定している場合、ブラウザーは両方を適用するため、プロキシ側では設定しないでください。新しい環境を確認している間は、`CSP_REPORT_ONLY=1` を設定すると、ポリシーをレポート専用で送信します。違反は `/api/csp-report` に記録されます。Vercel以外でHTTPS配信する場合は `CSP_HTTPS=1` を追加すると、ブラウザーが `http://` のリソースをアップグレードします。どちらもアプリの実行場所で読み取られ、事前レンダリングされたページのヘッダーについてはビルド場所でも読み取られます。Dockerfileはこれらをビルドに渡さないため、事前レンダリングされたページで必要な場合は、ビルド引数としても追加してください。

## QRdxを更新する [#update-qrdx]

まずデータベースをバックアップしてください（下記参照）。そのうえでプルして再ビルドします。`migrate` サービスが、アプリの起動前にスキーマを再び同期します。

```bash title="Terminal"
git pull
docker compose up -d --build
```

手動セットアップの場合は、`git pull`、`bun install`、`bun run db:push` を実行してから、再ビルドして再起動してください。

スキーマの変更でデータが削除される場合、`drizzle-kit push` は確認を求め、`migrate` サービスは得られない応答を待ち続けます。その場合は、ターミナルで実行して変更内容を確認し、承認してください。

```bash title="Terminal"
docker compose run --rm migrate
```

## バックアップと復元 [#back-up-and-restore]

QRdxが保存するものはすべてPostgresにあります。ただしアップロードされたファイルはR2バケットにあります。更新のたびに、また定期的に、データベースをダンプしてください。

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

空のデータベースに復元するには:

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Neonを使う場合は、代わりにNeon自身のバックアップとブランチ機能を使ってください。

## qrdx.devとの違い [#what-is-different-from-qrdxdev]

- **ドキュメント**はqrdx.devで公開されています。お使いのインスタンスでは、すべてのドキュメントURLがqrdx.devにリダイレクトされます。
- **支払いとプラン**にはPolarが必要です。Polarがない場合、すべてのアカウントにフリーの上限が適用され、誰もアップグレードできません。上限そのものは `apps/app/lib/plans.ts` にあり、お使いのインスタンス向けに変更できます。
- **アフィリエイトプログラム、請求書払いのリクエスト、非営利団体向け割引、エンタープライズ向けお問い合わせフォーム**はQRdx自身の営業活動であり、QRdx自体が稼働している環境でのみ動作します。セルフホスト版にはいずれもありません。
- **スキャンの位置情報:** 国、地域、市区町村はVercelのジオヘッダーから取得されます。Cloudflareの背後では国のみが読み取られ（`CF-IPCountry`）、それ以外では位置情報は不明と表示され、[エリアルール](/docs/precise-location#route-scans-by-area)は位置情報を共有したスキャンにのみ一致します。
- **カスタムドメイン**は、DNSの `TXT` レコードで検証され、リバースプロキシでルーティングされます。ただし、VercelでDomains APIの変数を設定して実行している場合は除きます。**Set up with …** ボタンには独自のDomain Connectテンプレートが必要です。QRdxのテンプレートはqrdx.devでのみ動作します。
- **チャットボットと連携**には、それぞれ連携先のサービスに登録した自分のアプリが必要です（上の表を参照）。
- **管理ページ**はアプリ自体が提供します。qrdx.devでは、一部を別のコンソールにプロキシしています。

## トラブルシューティング [#troubleshooting]

### 起動時に「Invalid environment variables」と表示される [#invalid-environment-variables-on-startup]

ログには、不足している、または無効な変数が1つずつ表示され、続けて設定場所が示されます。必須の値が不足しているか、任意の値に無効な内容が設定されています。たとえば、完全な `http://` または `https://` のアドレスではないURLや、短すぎるシークレットです。空の値は未設定として扱われ、問題ありません。`.env` で指摘された変数を修正し、`docker compose up -d app` でコンテナーを再作成してください。

### OAuthの `redirect_uri` が一致しない [#oauth-redirect_uri-mismatch]

OAuthアプリのコールバックURLは、正確に `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` または `/api/auth/callback/google` である必要があります。`BETTER_AUTH_URL` には、`NEXT_PUBLIC_APP_URL` と同じベースURLを設定してください。

### アプリがデータベースに接続できない（`fetch failed`） [#the-app-cant-reach-the-database-fetch-failed]

通常のPostgresでは、`DATABASE_HTTP_ENDPOINT` を稼働中のプロキシに向ける必要があります。`docker compose ps db-proxy` で稼働中になっていることを確認してください。

### `migrate` が終了しない [#migrate-never-finishes]

`drizzle-kit push` が確認を待っています。ターミナルで `docker compose run --rm migrate` を実行して応答してください。[QRdxを更新する](#update-qrdx)を参照してください。

### `NEXT_PUBLIC_*` の値を変更しても反映されない [#a-changed-next_public_-value-has-no-effect]

イメージを再ビルドしてください: `docker compose up -d --build`。

### ポート4444がすでに使用されている [#port-4444-is-already-in-use]

`docker-compose.yml` の `db-proxy` のポートマッピングを変更してください。使用するのは、ホスト上でのローカル開発のみです。

### 「the --mount option requires BuildKit」 [#the---mount-option-requires-buildkit]

お使いのDockerにBuildKitがありません。`buildx` プラグインをインストールするか、Dockerを更新してください。

### ビルドが `Killed` または終了コード137で止まる [#the-build-stops-with-killed-or-exit-code-137]

Dockerのメモリが不足しました。少なくとも8 GBを割り当て（Docker Desktop: **Settings** → **Resources**）、もう一度 `docker compose up -d --build` を実行してください。

### 「sign-in code email is off for this deployment」 [#sign-in-code-email-is-off-for-this-deployment]

`NEXT_PUBLIC_APP_URL` が `localhost` の間は、メールコードは送信されません。ローカルでのテストには、GitHubまたはGoogleでのサインインを使ってください。

まだ解決しませんか？ シークレットを除いた `docker compose logs app` の出力を添えて、[Issueを作成してください](https://github.com/qrdxinc/qrdx/issues)。

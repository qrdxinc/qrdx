À la fin de ce guide, QRdx tournera sur votre propre URL : l'éditeur de QR code, les comptes, les QR codes dynamiques avec statistiques de scan, les pages hébergées, les espaces de travail et les thèmes enregistrés, sur une base Postgres que vous contrôlez. La méthode Docker Compose prend environ une demi-heure, dont l'essentiel pour la première construction de l'image.

L'application web est open source sous licence AGPL-3.0. Deux parties ne le sont pas : l'authentification unique (SSO) des espaces de travail et le journal d'audit se trouvent dans les dossiers `ee/`, sous la licence commerciale de QRdx, et restent désactivés tant que vous ne définissez pas de clé de licence (`QRDX_EE_LICENSE`). Les utiliser en production nécessite un accord écrit avec QRdx ; consultez [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md). Vous n'avez besoin de rien de tout cela pour utiliser la [bibliothèque React `qrdx`](/docs/getting-started) ou la [CLI](/docs/developers/cli) : elles fonctionnent partout sans backend, sous licence MIT. [L'open source chez QRdx](/open-source-qr-code-generator) détaille chaque partie du dépôt et sa licence.

## Avant de commencer [#before-you-start]

- Docker avec Compose v2 et BuildKit (Docker Desktop et les versions actuelles de Docker Engine incluent les deux), ou Node.js 22 (22.22.3 ou version ultérieure) et [Bun](https://bun.com/docs/installation) 1.4 pour l'installation manuelle.
- Au moins 8 Go de mémoire pour Docker pendant la construction de l'image.
- Un moyen de vous connecter, afin de pouvoir créer des comptes : une application OAuth GitHub ou Google, ou [Resend](https://resend.com) pour les codes de connexion par e-mail. Les codes de connexion ne sont envoyés par e-mail que si `NEXT_PUBLIC_APP_URL` n'est pas `localhost`. `bun run dev` les affiche dans le terminal à la place, mais l'image Docker ne le fait pas : un test local avec Docker nécessite donc une connexion GitHub ou Google.
- Postgres : le conteneur fourni dans `docker-compose.yml`, ou une base [Neon](https://neon.tech).
- Pour tout usage au-delà d'un test local, un domaine et un reverse proxy qui termine le HTTPS.

La documentation ne fait pas partie d'une instance auto-hébergée. Votre instance redirige tous les liens de la documentation (`/docs` et les pages situées en dessous, leurs copies Markdown et `/llms-full.txt`) vers les mêmes pages sur qrdx.dev.

### Fonctionnement de la connexion à la base de données [#how-the-database-connection-works]

L'application communique avec Postgres via le pilote HTTP serverless de Neon.

- **Neon :** fonctionne directement. Définissez `DATABASE_URL` avec votre chaîne de connexion Neon.
- **Postgres standard :** nécessite un proxy HTTP compatible Neon devant la base. `docker-compose.yml` en exécute un ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) et définit `DATABASE_HTTP_ENDPOINT` pour que l'application lui envoie ses requêtes.

Le schéma provient de `packages/database/schema.ts` et est appliqué avec `drizzle-kit push`. Aucun fichier de migration n'est à exécuter à la main.

## Démarrage rapide avec Docker Compose [#quick-start-with-docker-compose]

### 1. Cloner le dépôt [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. Configurer l'environnement [#2-configure-the-environment]

Copiez le fichier d'exemple à la racine du dépôt, là où Compose le lit, et générez le secret de session :

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

Ouvrez `.env` et définissez ces valeurs. Toutes les autres lignes peuvent rester commentées.

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

Origine de chaque valeur :

| Variable | Où l'obtenir |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | L'URL publique de votre instance, sans barre oblique finale. Conservez `http://localhost:3000` pour un test local. |
| `BETTER_AUTH_URL` | La même valeur. Décommentez la ligne. |
| `BETTER_AUTH_SECRET` | La sortie de `openssl rand -base64 32`. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | Une [application OAuth GitHub](https://github.com/settings/developers) dont l'URL de rappel est `<your url>/api/auth/callback/github`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | À la place de GitHub : un [client OAuth Google](https://console.cloud.google.com/apis/credentials) dont l'URI de redirection est `<your url>/api/auth/callback/google`. |

Laissez `DATABASE_URL` tel quel : Compose dirige l'application vers son propre conteneur Postgres et ignore la valeur de `.env`. Pour changer le mot de passe de la base, définissez `POSTGRES_PASSWORD` avant le premier démarrage.

### 3. Démarrer la pile [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

Cette commande construit l'image, démarre Postgres et le proxy, exécute le service ponctuel `migrate` (`drizzle-kit push`), puis démarre l'application sur le port 3000. La première construction prend plusieurs minutes. Une fois terminée, les quatre services ressemblent à ceci :

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

`migrate` est censé s'arrêter : il synchronise le schéma, puis s'arrête. Pour suivre la synchronisation du schéma et le démarrage de l'application :

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. Se connecter [#4-sign-in]

Ouvrez `NEXT_PUBLIC_APP_URL` dans un navigateur et connectez-vous avec GitHub, Google ou un code reçu par e-mail. Votre compte est créé à la première connexion.

### 5. Devenir administrateur [#5-make-yourself-an-admin]

Ajoutez à `.env` l'adresse e-mail du compte créé à l'étape 4 :

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

Recréez le conteneur de l'application pour qu'il prenne en compte la modification, puis connectez-vous et ouvrez `/admin` :

```bash title="Terminal"
docker compose up -d app
```

L'adresse devient administrateur la première fois qu'elle ouvre `/admin`. `ADMIN_USER_IDS` fonctionne de la même manière avec des identifiants d'utilisateur.

## Utiliser Neon ou un autre Postgres géré [#use-neon-or-another-managed-postgres]

Vous pouvez vous passer du Postgres fourni et n'exécuter que l'image de l'application. Définissez `DATABASE_URL` dans `.env` avec votre chaîne de connexion Neon et laissez `DATABASE_HTTP_ENDPOINT` non défini.

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Appliquez le schéma une première fois, puis après chaque mise à jour, avec l'image de migration :

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Installation manuelle avec Node.js [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

Pour la production, construisez et démarrez l'application :

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` se connecte avec le pilote Neon : il nécessite donc une base Neon. Pour utiliser plutôt le Postgres Docker en développement local, démarrez-le avec `docker compose up -d db db-proxy`, appliquez le schéma avec `docker compose run --rm migrate`, et définissez ces valeurs dans `apps/app/.env.local` :

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

L'installation manuelle les lit toutes depuis `apps/app/.env.local`.

### Tâches planifiées [#scheduled-jobs]

Deux routes effectuent le travail récurrent : `/api/cron/webhooks` relance les envois de webhooks en échec et supprime les anciennes entrées du journal d'audit, et `/api/cron/digest` envoie le résumé hebdomadaire. Sur Vercel, `apps/app/vercel.json` les planifie. Ailleurs, rien ne les appelle tant que vous ne le faites pas. Définissez `CRON_SECRET` et appelez les deux routes depuis votre planificateur avec cette valeur :

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

Sans l'en-tête, les routes répondent `401` en production. [Notifications](/docs/notifications#self-hosting) explique le paramètre `shard` du résumé.

## Reverse proxy et HTTPS [#reverse-proxy-and-https]

Placez l'application derrière un reverse proxy tel que Caddy, nginx ou Traefik qui termine le TLS, et n'exposez pas directement le port 3000 sur internet. La limitation de débit, les e-mails de sécurité et le [journal d'audit](/docs/help/teams/audit-log) lisent l'adresse IP du client d'abord dans `X-Real-IP`, puis dans la première adresse de `X-Forwarded-For` (sur Vercel, `X-Vercel-Forwarded-For` s'intercale entre les deux). Le proxy doit donc définir ces en-têtes, et l'application ne doit être joignable que par son intermédiaire. Faites en sorte que le proxy définisse `X-Real-IP` avec l'adresse d'où il a reçu la connexion. Un proxy qui se contente d'ajouter une valeur à `X-Forwarded-For` permet à un client de placer n'importe quelle adresse en première position.

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

Caddy définit ces en-têtes par défaut. Une fois HTTPS fonctionnel, remplacez `NEXT_PUBLIC_APP_URL` et `BETTER_AUTH_URL` par l'URL en `https://`, mettez à jour les URL de callback OAuth, puis reconstruisez.

### Content-Security-Policy [#content-security-policy]

Les builds de production envoient un en-tête Content-Security-Policy sur les pages propres à QRdx : les pages réservées aux utilisateurs connectés reçoivent un nonce de script neuf à chaque requête, et les pages prérendues une liste d'hôtes de scripts autorisés. Les pages hébergées (`/p`) reçoivent une politique permissive, car elles exécutent les pixels de leur propriétaire et intègrent des médias provenant de n'importe où. Si votre reverse proxy définit aussi `Content-Security-Policy`, les navigateurs appliquent les deux : ne la définissez donc pas à ce niveau. Définissez `CSP_REPORT_ONLY=1` pour envoyer la politique en mode rapport seul pendant que vous vérifiez une nouvelle configuration ; les violations sont consignées par `/api/csp-report`. Ajoutez `CSP_HTTPS=1` lorsque vous servez en HTTPS en dehors de Vercel, afin que les navigateurs passent en HTTPS toute ressource en `http://`. Ces deux variables sont lues là où l'application s'exécute et, pour l'en-tête des pages prérendues, là où elle est construite ; le Dockerfile ne les transmet pas au build, ajoutez-les donc aussi comme arguments de build si les pages prérendues en ont besoin.

## Mettre à jour QRdx [#update-qrdx]

Sauvegardez d'abord la base de données (voir ci-dessous). Récupérez ensuite le code et reconstruisez. Le service `migrate` synchronise de nouveau le schéma avant le démarrage de l'application.

```bash title="Terminal"
git pull
docker compose up -d --build
```

Pour l'installation manuelle, exécutez `git pull`, `bun install` et `bun run db:push`, puis reconstruisez et redémarrez.

Si une modification du schéma supprime des données, `drizzle-kit push` demande une confirmation et le service `migrate` attend une réponse qu'il ne peut pas obtenir. Dans ce cas, exécutez la commande dans un terminal pour examiner et confirmer les changements :

```bash title="Terminal"
docker compose run --rm migrate
```

## Sauvegarder et restaurer [#back-up-and-restore]

Tout ce que QRdx stocke se trouve dans Postgres, sauf les fichiers téléversés, qui sont dans votre bucket R2. Exportez la base de données avant chaque mise à jour, ainsi que selon un calendrier régulier :

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Pour restaurer dans une base vide :

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Avec Neon, utilisez plutôt ses propres sauvegardes et ses branches.

## Différences avec qrdx.dev [#what-is-different-from-qrdxdev]

- **La documentation** est consultable sur qrdx.dev. Votre instance y redirige toutes les URL de la documentation.
- **Les paiements et les offres** nécessitent Polar. Sans lui, tous les comptes ont les limites de l'offre Gratuit et personne ne peut passer à une offre supérieure. Les limites elles-mêmes se trouvent dans `apps/app/lib/plans.ts`, que vous pouvez modifier pour votre instance.
- **Le programme d'affiliation, les demandes de paiement sur facture, les remises pour les associations et le formulaire de contact entreprise** relèvent de l'activité commerciale propre à QRdx et ne fonctionnent que là où QRdx lui-même est exécuté. Une copie auto-hébergée n'en dispose d'aucun.
- **Localisation des scans :** le pays, la région et la ville proviennent des en-têtes de géolocalisation de Vercel. Derrière Cloudflare, seul le pays est lu (`CF-IPCountry`) ; ailleurs, les localisations apparaissent comme inconnues, et les [règles par zone](/docs/precise-location#route-scans-by-area) ne s'appliquent qu'aux scans dont la localisation est partagée.
- **Les domaines personnalisés** sont vérifiés par un enregistrement DNS `TXT` et routés par votre reverse proxy, sauf si vous utilisez Vercel avec les variables de l'API Domains définies. Le bouton **Set up with …** nécessite votre propre modèle Domain Connect : celui de QRdx ne fonctionne que pour qrdx.dev.
- **Les bots de chat et les intégrations** nécessitent chacun une application que vous enregistrez auprès du service concerné (voir le tableau ci-dessus).
- **Les pages d'administration** sont servies par l'application elle-même ; qrdx.dev en fait transiter certaines par un proxy vers une console distincte.

## Dépannage [#troubleshooting]

### « Invalid environment variables » au démarrage [#invalid-environment-variables-on-startup]

Le journal nomme chaque variable manquante ou invalide, puis indique où la définir. Une valeur obligatoire est absente, ou une valeur facultative est invalide : une URL qui n'est pas une adresse complète en `http://` ou `https://`, ou un secret trop court. Une valeur vide est considérée comme non définie et ne pose pas de problème. Corrigez les variables indiquées dans `.env`, puis recréez le conteneur avec `docker compose up -d app`.

### Erreur `redirect_uri` OAuth non concordant [#oauth-redirect_uri-mismatch]

L'URL de callback de votre application OAuth doit être exactement `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` ou `/api/auth/callback/google`. Définissez `BETTER_AUTH_URL` avec la même URL de base que `NEXT_PUBLIC_APP_URL`.

### L'application ne parvient pas à joindre la base de données (`fetch failed`) [#the-app-cant-reach-the-database-fetch-failed]

Avec Postgres standard, `DATABASE_HTTP_ENDPOINT` doit pointer vers le proxy en cours d'exécution. Vérifiez que `docker compose ps db-proxy` indique qu'il est en cours d'exécution.

### `migrate` ne se termine jamais [#migrate-never-finishes]

`drizzle-kit push` attend une confirmation. Exécutez `docker compose run --rm migrate` dans un terminal et répondez-y ; voir [Mettre à jour QRdx](#update-qrdx).

### Une valeur `NEXT_PUBLIC_*` modifiée reste sans effet [#a-changed-next_public_-value-has-no-effect]

Reconstruisez l'image : `docker compose up -d --build`.

### Le port 4444 est déjà utilisé [#port-4444-is-already-in-use]

Modifiez le mappage de port de `db-proxy` dans `docker-compose.yml`. Seul le développement local sur l'hôte l'utilise.

### « the --mount option requires BuildKit » [#the---mount-option-requires-buildkit]

Votre Docker n'a pas BuildKit. Installez le plugin `buildx` ou mettez Docker à jour.

### Le build s'arrête avec `Killed` ou le code de sortie 137 [#the-build-stops-with-killed-or-exit-code-137]

Docker a manqué de mémoire. Allouez-lui au moins 8 Go (Docker Desktop : **Settings** → **Resources**), puis relancez `docker compose up -d --build`.

### « sign-in code email is off for this deployment » [#sign-in-code-email-is-off-for-this-deployment]

Les codes par e-mail ne sont pas envoyés tant que `NEXT_PUBLIC_APP_URL` vaut `localhost`. Utilisez la connexion GitHub ou Google pour un test en local.

Toujours bloqué ? [Ouvrez une issue](https://github.com/qrdxinc/qrdx/issues) en joignant la sortie de `docker compose logs app`, après en avoir retiré les secrets.

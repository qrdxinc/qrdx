Am Ende dieser Seite können Nutzer in deinem Produkt auf **QRdx verbinden** klicken und deine App auf dem Zustimmungsbildschirm von QRdx freigeben. Dein Server hält dann ein Access-Token, das in ihrem Namen `https://api.qrdx.dev/v1` aufruft, begrenzt auf die Scopes, die sie freigegeben haben.

Eine Integration ist eine OAuth-App. Ein [API-Schlüssel](/docs/developers/api-keys) handelt als du selbst in einem Workspace. Ein Token dagegen handelt als die Person, die deine App freigegeben hat, in deren eigenem Workspace, und diese Person kann den Zugriff jederzeit wieder entziehen.

## Bevor du loslegst [#before-you-start]

- Ein QRdx-Konto. Kostenlose Workspaces können 1 OAuth-App haben, Pro 5 und Business 25; ein Workspace nutzt den besten Plan unter seinen Inhabern.
- Ein Server, der ein Secret geheim halten und eine Weiterleitung empfangen kann. Die Codebeispiele sind Node.js mit der Fetch API; jede Sprache mit HTTPS und SHA-256 funktioniert.
- Die zwei `https://`-Redirect-URIs, die du verwenden wirst: eine für die Produktion, eine für die Entwicklung (dafür ist `http://localhost` erlaubt).

## 1. Eine OAuth-App erstellen [#1-create-an-oauth-app]

Öffne [Einstellungen → API-Schlüssel & Apps](/dashboard?to=settings/developers) und wähle **Neue App**. Die App gehört zum gerade geöffneten Workspace. Nur die Inhaber des Workspace können Apps erstellen und ändern; Admins und Mitglieder können sie ansehen.

<Shot id="oauth-new-app-form" />

| Feld | Wofür es gedacht ist |
| --- | --- |
| **Name**, **Beschreibung**, **Logo**, **Website** | Werden auf dem Zustimmungsbildschirm angezeigt. Lade ein quadratisches Logo mit mindestens 128 × 128 px hoch oder füge einen `https://`-Link dazu ein |
| **Redirect-URIs** | Wohin QRdx die Nutzer zurückschickt, eine pro Zeile, bis zu 10. Nur `https://`, dazu `http://localhost` für die Entwicklung. Keine Wildcards oder `#fragments`: Jede Anfrage muss genau eine davon senden |
| **Scopes** | Das Maximum, das deine App anfordern darf. Jede Autorisierung fragt einige oder alle davon an |
| **PKCE erforderlich** | Jede Autorisierung muss eine `S256`-Code-Challenge senden. Empfohlen und standardmäßig aktiviert |

Nach dem Speichern zeigt QRdx die **Client-ID** und das **Client-Secret** an. Kopiere das Secret sofort: QRdx speichert nur einen Hash davon und kann es nicht noch einmal anzeigen. Wenn du es verlierst oder es offengelegt wird, wähle auf der Seite der App **Secret neu generieren**. Das alte Secret funktioniert sofort nicht mehr; Nutzer, die bereits verbunden sind, bleiben verbunden. Beim Erstellen einer App und beim Neugenerieren ihres Secrets musst du zuerst [bestätigen, dass du es bist](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), es sei denn, du hast das in diesem Browser in den letzten 10 Minuten getan.

<Shot id="oauth-app-credentials" />

Bewahre beide Werte auf deinem Server auf:

```bash title=".env"
QRDX_CLIENT_ID=qrdx_app_...
QRDX_CLIENT_SECRET=qrdx_secret_...
```

## 2. Nutzer zu QRdx schicken [#2-send-people-to-qrdx]

Erzeuge einen zufälligen `state` und einen PKCE-`code_verifier`, speichere beide in der Sitzung der Person und leite zur Authorize-URL weiter:

```txt title="Authorize URL"
https://qrdx.dev/api/oauth/authorize
  ?response_type=code
  &client_id=<client id>
  &redirect_uri=https://acme.example/oauth/qrdx/callback
  &scope=profile:read codes:read codes:write
  &state=<random value>
  &code_challenge=<BASE64URL(SHA256(code_verifier))>
  &code_challenge_method=S256
```

| Parameter | Erforderlich | Wert |
| --- | --- | --- |
| `response_type` | Ja | `code` |
| `client_id` | Ja | Die Client-ID deiner App |
| `redirect_uri` | Ja | Eine der Redirect-URIs der App, Zeichen für Zeichen |
| `scope` | Ja | Durch Leerzeichen oder Kommas getrennt; nur Scopes, die die App hat |
| `state` | Empfohlen | Ein beliebiger Wert; QRdx sendet ihn unverändert zurück. Prüfe ihn bei der Rückkehr, um Cross-Site-Request-Forgery zu verhindern |
| `code_challenge` | Wenn die App PKCE verlangt | 43 bis 128 Zeichen: der base64url-kodierte SHA-256 deines `code_verifier` |
| `code_challenge_method` | Nein | `S256`, der Standard und die einzige akzeptierte Methode. `plain` wird mit `invalid_request` abgelehnt |
| `prompt` | Nein | `consent` zeigt den Zustimmungsbildschirm auch dann, wenn die Person diese Scopes schon früher freigegeben hat |

```ts title="lib/qrdx-oauth.ts"
import { createHash, randomBytes } from "node:crypto";

export const QRDX_AUTHORIZE_URL = "https://qrdx.dev/api/oauth/authorize";

export function createPkce() {
  const verifier = randomBytes(32).toString("base64url"); // 43 characters
  const challenge = createHash("sha256").update(verifier).digest("base64url");
  return { verifier, challenge };
}

export function authorizeUrl({ state, challenge }: { state: string; challenge: string }) {
  const url = new URL(QRDX_AUTHORIZE_URL);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: process.env.QRDX_CLIENT_ID!,
    redirect_uri: "https://acme.example/oauth/qrdx/callback",
    scope: "profile:read codes:read codes:write",
    state,
    code_challenge: challenge,
    code_challenge_method: "S256",
  }).toString();
  return url.toString();
}
```

Nutzer, die nicht bei QRdx angemeldet sind, melden sich zuerst an. Dann sehen sie den Zustimmungsbildschirm: das Logo, den Namen und die Website deiner App, wer sie gebaut hat, die angeforderten Berechtigungen und das Konto, mit dem sie angemeldet sind. Apps, die QRdx nicht geprüft hat, tragen den Hinweis **Nicht verifizierte App.** Bei **Autorisieren** müssen sie [bestätigen, dass sie es sind](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), es sei denn, sie haben das in den letzten 10 Minuten getan (eine Anmeldung kurz zuvor zählt). Wer dieselben Scopes für deine App schon freigegeben hat, wird direkt zu dir zurückgeschickt.

<Shot id="oauth-consent-screen" />

Danach leitet QRdx zu deiner `redirect_uri` weiter:

- Freigegeben: `?code=<authorization code>&state=<your state>`. Der Code funktioniert einmal, innerhalb von 10 Minuten.
- Abgebrochen: `?error=access_denied&error_description=...&state=<your state>`.

Ungültige Anfragen werden nie weitergeleitet; sie antworten mit JSON im OAuth-2.0-Format. Eine unbekannte `client_id` ergibt `invalid_client`, eine nicht registrierte `redirect_uri` oder eine `plain`-Challenge ergibt `invalid_request`, und ein Scope, den die App nicht hat, ergibt `invalid_scope`:

```json title="400 Bad Request"
{"error":"invalid_scope","error_description":"Invalid or unsupported scope"}
```

## 3. Den Code gegen Tokens eintauschen [#3-exchange-the-code-for-tokens]

Sende den Code von deinem Server per POST an den Token-Endpunkt. Der Body ist form-kodiert, und `redirect_uri` muss dieselbe sein wie in Schritt 2.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=authorization_code \
  -d client_id=$QRDX_CLIENT_ID \
  -d client_secret=$QRDX_CLIENT_SECRET \
  -d code=$CODE \
  -d redirect_uri=https://acme.example/oauth/qrdx/callback \
  -d code_verifier=$CODE_VERIFIER
```

```ts title="app/oauth/qrdx/callback/route.ts"
export async function GET(req: Request) {
  const params = new URL(req.url).searchParams;
  const session = await getSession(req); // your own session store
  if (params.get("state") !== session.qrdxState) {
    return new Response("Invalid state", { status: 400 });
  }
  if (params.get("error")) {
    return Response.redirect("https://acme.example/settings?qrdx=canceled");
  }

  const response = await fetch("https://qrdx.dev/api/oauth/token", {
    method: "POST",
    body: new URLSearchParams({
      grant_type: "authorization_code",
      client_id: process.env.QRDX_CLIENT_ID!,
      client_secret: process.env.QRDX_CLIENT_SECRET!,
      code: params.get("code") ?? "",
      redirect_uri: "https://acme.example/oauth/qrdx/callback",
      code_verifier: session.qrdxVerifier,
    }),
  });
  if (!response.ok) {
    const { error, error_description } = await response.json();
    throw new Error(`QRdx token exchange failed: ${error} ${error_description}`);
  }

  const tokens: {
    access_token: string;
    token_type: "Bearer";
    expires_in: number;
    refresh_token: string;
    scope: string;
  } = await response.json();
  await saveQrdxTokens(session.userId, tokens); // encrypt at rest
  return Response.redirect("https://acme.example/settings?qrdx=connected");
}
```

```json title="Response fields"
{
  "access_token": "<send as Authorization: Bearer>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "<store encrypted; it rotates on each refresh>",
  "scope": "profile:read codes:read codes:write"
}
```

`scope` listet auf, was gewährt wurde, durch Leerzeichen getrennt. Access-Tokens gelten 1 Stunde und Refresh-Tokens 30 Tage. Sende `code_verifier` genau dann, wenn die Autorisierung eine `code_challenge` hatte; ein Verifier für einen Code, der ohne Challenge ausgestellt wurde, wird abgelehnt. Ein falsches Secret oder ein bereits verwendeter Code ergibt `invalid_client` oder `invalid_grant`, und ein anderer Grant-Typ als die beiden unterstützten ergibt:

```json title="400 Bad Request"
{"error":"unsupported_grant_type","error_description":"Supported: authorization_code, refresh_token"}
```

## 4. Tokens erneuern [#4-refresh-tokens]

Tausche das Refresh-Token vor Ablauf des Access-Tokens gegen ein neues Paar. Refresh-Tokens rotieren: Jedes funktioniert nur einmal, speichere also jedes Mal das neue.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=refresh_token \
  -d client_id=$QRDX_CLIENT_ID \
  -d client_secret=$QRDX_CLIENT_SECRET \
  -d refresh_token=$REFRESH_TOKEN
```

```ts title="lib/qrdx-oauth.ts"
export async function refreshQrdxTokens(refreshToken: string) {
  const response = await fetch("https://qrdx.dev/api/oauth/token", {
    method: "POST",
    body: new URLSearchParams({
      grant_type: "refresh_token",
      client_id: process.env.QRDX_CLIENT_ID!,
      client_secret: process.env.QRDX_CLIENT_SECRET!,
      refresh_token: refreshToken,
    }),
  });
  // invalid_grant: revoked, expired or already used. Ask the person to reconnect.
  if (!response.ok) throw new Error((await response.json()).error);
  return response.json();
}
```

Der Token-Endpunkt erlaubt 30 Anfragen pro Minute und IP-Adresse.

## 5. Die API aufrufen [#5-call-the-api]

Sende das Access-Token als Bearer-Token an `https://api.qrdx.dev/v1`. Token-Anfragen wirken auf den eigenen Workspace der Person, die deine App autorisiert hat (jedes Konto hat einen), mit dem Plan und dem [Tageskontingent](/docs/developers/rest-api#rate-limits) dieses Workspace. Fordere nur das Nötigste an, was deine Integration braucht; Nutzer sehen jeden Scope auf dem Zustimmungsbildschirm.

| Scope | Erlaubt |
| --- | --- |
| `profile:read` | ID, Name, E-Mail und Avatar des Nutzers: `GET /v1/me` und `GET /api/oauth/userinfo` |
| `themes:read` | Die gespeicherten QR-Themes: `GET /v1/themes`, `GET /v1/themes/{id}` |
| `codes:read` | Die dynamischen Codes, Scan-Analysen und gespeicherten Barcodes; Hooks auflisten |
| `codes:write` | Alles, was `codes:read` erlaubt, plus Codes und Barcodes erstellen, bearbeiten und löschen, Conversions melden und Ereignisse abonnieren |

```ts title="lib/qrdx.ts"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${accessToken}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    destinationUrl: "https://acme.example/menu",
    title: "Spring menu",
  }),
});
const { data: code } = await response.json(); // code.shortLink is what the QR encodes
```

Ein `401 INVALID_TOKEN` bedeutet, dass das Token abgelaufen ist oder widerrufen wurde: Erneuere es oder bitte die Person, sich neu zu verbinden. Ein `403 INSUFFICIENT_SCOPE` bedeutet, dass dem Token der Scope fehlt. Die [API-Referenz](/docs/developers/api) listet jeden Endpunkt mit Scope und Fehlern auf.

## 6. Ereignisse mit Webhooks empfangen [#6-receive-events-with-webhooks]

Abonniere im Namen der Person über die REST Hooks API, statt sie eine URL einfügen zu lassen. Dafür brauchst du `codes:write`, und der Plan der Person muss [Webhooks](/docs/webhooks) enthalten (Business); sonst kommt `402 PLAN_REQUIRED` zurück.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/hooks \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"target_url": "https://acme.example/webhooks/qrdx", "events": ["scan.created", "form.submitted"]}'
```

Die `201`-Antwort enthält die Abo-`id` und ein Signatur-`secret`, das nur einmal angezeigt wird. Jede Zustellung wird damit in `X-QRdx-Signature` signiert; siehe [Signaturen prüfen](/docs/webhooks#verify-signatures). Kündige mit `DELETE /v1/hooks/{id}`, wenn die Person die Verbindung trennt. Abos erscheinen außerdem unter **Einstellungen → Webhooks** im eigenen Workspace der Person, wo sie sie entfernen kann.

## 7. Verbindung trennen und Nutzer identifizieren [#7-disconnect-and-identify-people]

Wenn jemand in deinem Produkt QRdx trennt, widerrufe die Tokens. Das Widerrufen eines der beiden Tokens eines Paars widerruft das Paar; der Endpunkt antwortet auch bei unbekannten Tokens mit `200`.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/revoke -d token=$REFRESH_TOKEN
```

Nutzer können den Zugriff jederzeit selbst entziehen, unter **Einstellungen → Autorisierte Apps** in QRdx mit **Zugriff widerrufen**. Jedes Token, das deine App für ihr Konto hält, funktioniert sofort nicht mehr: API-Aufrufe antworten mit `401` und `invalid_token`, und das Erneuern antwortet mit `invalid_grant`. Behandle beides als „getrennt“ und bitte die Person, sich erneut zu verbinden; sie sieht dann den Zustimmungsbildschirm wieder.

Um zu erfahren, wer sich verbunden hat, rufe `GET /api/oauth/userinfo` mit einem `profile:read`-Token auf. Der Endpunkt liefert Claims im OpenID-Stil: `sub`, `name`, `email` und `picture`. Verwende `sub` als stabile Konto-ID, denn E-Mail-Adressen können sich ändern.

```bash title="Terminal"
curl https://qrdx.dev/api/oauth/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

```json title="401 Unauthorized: an expired or revoked token"
{"error":"invalid_token","error_description":"Invalid or expired token"}
```

## 8. Gelistet werden [#8-get-listed]

Wenn deine Integration durchgängig funktioniert, bitte darum, sie zum [Integrationsverzeichnis](/integrations) hinzuzufügen, wo sie als Community-Integration von dir erscheint. Auf der Seite deiner App öffnet **Listen lassen** eine E-Mail an [support@qrdx.dev](mailto:support@qrdx.dev?subject=List%20my%20integration) mit den bereits ausgefüllten Angaben:

- Name und Client-ID deiner App;
- eine Zeile dazu, was sie tut und für wen sie gedacht ist;
- Einrichtungsschritte oder ein Link dazu;
- ein Support-Kontakt.

Das QRdx-Team prüft gelistete Apps und markiert sie als **Verifiziert**, wodurch der Hinweis **Nicht verifizierte App.** vom Zustimmungsbildschirm verschwindet. Wenn du Name, Logo oder Website einer verifizierten App änderst, entfällt das Abzeichen, bis sie erneut geprüft wurde.

## Wenn etwas schiefgeht [#if-something-goes-wrong]

### `invalid_request: redirect_uri not registered` [#invalid_request-redirect_uri-not-registered]

Die `redirect_uri` in der Authorize-URL stimmt nicht Zeichen für Zeichen mit einer der Redirect-URIs der App überein, Schema und abschließender Schrägstrich eingeschlossen. Füge sie zur App hinzu oder korrigiere die URL.

### `invalid_scope` [#invalid_scope]

Die Authorize-URL fordert einen Scope an, den die App nicht hat. Füge den Scope in **Settings → API keys & apps** zur App hinzu und fordere ihn dann erneut an.

### `invalid_grant` beim Refresh [#invalid_grant-on-refresh]

Das Refresh-Token wurde bereits verwendet (jeder Refresh liefert ein neues), ist nach 30 Tagen abgelaufen oder die Person hat den Zugriff deiner App widerrufen. Schicke sie erneut durch die Autorisierung.

### Tokens funktionieren nicht mehr, nachdem du das Secret neu generiert hast [#tokens-stop-working-after-you-regenerated-the-secret]

Nur neue Token-Anfragen verwenden das neue Secret; bestehende Access- und Refresh-Tokens bleiben gültig. Prüfe, dass jede Server-Instanz das neue `QRDX_CLIENT_SECRET` liest.

## Sicherheits-Checkliste [#security-checklist]

- Bewahre das Client-Secret auf deinem Server auf. Browser- und Mobilcode dürfen es nie zu sehen bekommen.
- Nutze PKCE (`S256`) und für jede Autorisierung einen neuen `state`, und prüfe `state` bei der Rückkehr.
- Registriere exakte Redirect-URIs; QRdx vergleicht sie Zeichen für Zeichen.
- Speichere Access- und Refresh-Tokens verschlüsselt und sichere nach jedem Refresh das neue Refresh-Token.
- Widerrufe Tokens, wenn Personen die Verbindung trennen. Wenn du deine App in **Settings → API keys & apps** löschst, werden alle von ihr ausgestellten Tokens widerrufen; wenn du sie pausierst, werden die Tokens abgelehnt, bis du sie wieder fortsetzt.

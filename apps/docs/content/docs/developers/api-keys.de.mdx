Mit einem API-Key können deine eigenen Server, Skripte und CI-Jobs die [REST API](/docs/developers/rest-api) ohne OAuth-Flow aufrufen. Am Ende dieser Seite hast du einen Key für einen Workspace, weißt genau, was er darf, und weißt, wie du ihn rotierst.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

Jeder Endpunkt, der ein OAuth-Zugriffstoken akzeptiert, akzeptiert einen Key im selben Header. Die [Image API](/docs/developers/image-api) und die [Barcode-API](/docs/developers/barcode-api) brauchen beides nicht. Wenn dein Produkt im Namen anderer QRdx-Nutzer handelt, verwende stattdessen eine [OAuth-App](/docs/developers/build-an-integration), damit jede Person sie freigibt.

## Bevor du loslegst [#before-you-start]

- Ein QRdx-Konto, in dem du angemeldet bist. Jeder Plan hat API-Keys.
- Der Workspace, für den der Key gedacht ist. Ein Key gehört zu einem Workspace und handelt dort als du.

## 1. Key erstellen [#create-a-key]

1. Öffne [Einstellungen → API keys & apps](/dashboard?to=settings/developers&new=1) im Workspace, für den der Key gedacht ist. Der Link öffnet den zuletzt verwendeten Workspace; einen anderen wählst du im Workspace-Umschalter. Das Formular **Create API key** öffnet sich.
2. Trage bei **Name** ein, wo der Key verwendet wird, damit du später weißt, welchen du widerrufen musst. Wähle seinen **Access** und unter **Expires**, wie lange er gültig ist. Wähle **Create key**. Ein Key funktioniert ohne dich, deshalb bittet QRdx dich zuerst, [zu bestätigen, dass du es bist](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), außer du hast das in diesem Browser in den letzten 10 Minuten getan.
3. Kopiere den Key aus dem Dialog **Copy your API key**. Er wird nur dieses eine Mal angezeigt: QRdx speichert nur einen Hash davon. Derselbe Dialog zeigt eine curl-Anfrage mit dem Key und der API-Adresse dieser Seite, bereit zum Einfügen.

Ein Key besteht aus `qrdx_` gefolgt von 40 Buchstaben und Ziffern. Listen zeigen nur seinen Anfang, etwa `qrdx_7KpQ2m…`, damit du Keys unterscheiden kannst.

## 2. Zugriff festlegen [#access]

Keys verwenden dieselben Scopes wie OAuth-Apps. Wähle beim Erstellen des Keys eine von drei Optionen:

| Zugriff | Scopes | Erlaubt |
| --- | --- | --- |
| Voller Zugriff | `profile:read`, `themes:read`, `codes:read`, `codes:write` | Alles, was die API kann |
| Nur lesen | `profile:read`, `themes:read`, `codes:read` | Codes, Scan-Analysen, gespeicherte Barcodes, Themes und das Profil lesen |
| Benutzerdefiniert | Die, die du ankreuzt | Was diese Scopes erlauben ([die Scope-Liste](/docs/developers/rest-api#scopes)) |

`codes:write` erlaubt auch alles, was `codes:read` erlaubt. Die Scopes eines Keys lassen sich später nicht ändern; erstelle stattdessen einen neuen Key. Eine Anfrage außerhalb der Scopes des Keys erhält `403 INSUFFICIENT_SCOPE`, und die Meldung nennt den benötigten Scope:

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## 3. Key verwenden [#3-use-it]

Sende den Key als Bearer-Token. Der erste sinnvolle Aufruf ist `GET /v1/me`, der das Profil des Key-Erstellers zurückgibt und bestätigt, dass der Key funktioniert:

```bash title="Terminal"
curl https://api.qrdx.dev/v1/me -H "Authorization: Bearer $QRDX_API_KEY"
```

```json title="200 OK"
{"data":{"id":"usr_docsdev0000000000000001","name":"Ada Lovelace","email":"ada@example.com","image":null}}
```

Bewahre den Key auf einem Server auf, in einer Umgebungsvariable oder einem Secret-Manager, und lies ihn im Code von dort:

```js title="qrdx.mjs"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  headers: { Authorization: `Bearer ${process.env.QRDX_API_KEY}` },
});
```

```python title="qrdx.py"
import os
import requests

response = requests.get(
    "https://api.qrdx.dev/v1/codes",
    headers={"Authorization": f"Bearer {os.environ['QRDX_API_KEY']}"},
)
```

## Workspaces und Rollen [#workspaces-and-roles]

Ein Key gehört zu dem Workspace, der beim Erstellen geöffnet war, und handelt dort als du:

- Der Key arbeitet mit den Codes, Scans, Barcodes, Hooks und Themes dieses Workspace, im Rahmen des Plans und des [Tageskontingents](/docs/developers/rest-api#rate-limits) des Workspace.
- Er darf tun, was du im Workspace tun darfst, beurteilt nach deiner [Rolle](/docs/teams) zum Zeitpunkt jeder Anfrage. In deinem eigenen Workspace bist du Owner. Ändert sich deine Rolle, ändern sich auch die Rechte des Keys; verlässt du den Workspace, funktioniert der Key nicht mehr, und mit dem Löschen eines Workspace werden auch seine Keys gelöscht.

Jedes Mitglied eines Workspace kann Keys erstellen. Owner und Admins sehen alle Keys im Workspace und können jeden davon widerrufen; Mitglieder sehen und widerrufen nur ihre eigenen. Jede Person kann pro Workspace bis zu 25 aktive Keys haben; widerrufene und abgelaufene Keys zählen nicht.

## Ablauf, letzte Nutzung und Widerruf [#revoke]

- **Ablauf.** Unter **Expires** gilt ein Key unbegrenzt (**Never**) oder 30 Tage, 90 Tage oder 1 Jahr. Ein abgelaufener Key erhält `401 INVALID_TOKEN` und bleibt als **Expired** markiert in der Liste, bis du ihn widerrufst.
- **Letzte Nutzung.** Die Liste zeigt das Datum, an dem sich jeder Key zuletzt bei einer Anfrage authentifiziert hat.
- **Widerruf.** Wähle **Revoke** neben einem Key und bestätige mit **Revoke key**. Danach erhalten Anfragen damit `401 INVALID_TOKEN`. Ein Widerruf lässt sich nicht rückgängig machen.

```json title="401 Unauthorized"
{
  "code": "INVALID_TOKEN",
  "message": "Invalid API key: it doesn't exist, was revoked or has expired, or its creator left the workspace. Check that you copied the whole key, or create a new one at https://qrdx.dev/dashboard?to=settings/developers.",
  "status": 401,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## Keys sicher aufbewahren [#keep-keys-safe]

- Packe einen Key niemals in eine Webseite, eine Mobile-App, einen Prompt oder ein Repository. Browser-Code, der ein QR-Bild braucht, nutzt die schlüsselfreie [Image API](/docs/developers/image-api).
- Verwende pro Einsatzort einen eigenen Key, damit du einen widerrufen kannst, ohne die anderen zu beeinträchtigen.
- Gib Skripten, die nur Berichte erstellen, einen **Read only**-Key, und gib kurzlebigen Jobs einen Key mit Ablaufdatum.
- Wenn ein Key geleakt wurde, widerrufe ihn und erstelle einen neuen. Das Präfix `qrdx_` macht Keys in Code und Logs leicht auffindbar, und Secret-Scanner können `qrdx_[0-9A-Za-z]{40}` abgleichen.

## Wenn etwas schiefgeht [#if-something-goes-wrong]

### `401 UNAUTHORIZED` [#401-unauthorized]

Die Anfrage hatte keinen `Authorization`-Header. Prüfe den Header-Namen und ob dein HTTP-Client ihn sendet; der Wert ist `Bearer ` gefolgt vom ganzen Key.

### `401 INVALID_TOKEN` [#401-invalid_token]

Der Key wurde unvollständig kopiert, widerrufen, ist abgelaufen oder sein Ersteller hat den Workspace verlassen. Erstelle einen neuen Key. Bei einem OAuth-Token aktualisiere es oder schicke die Person erneut durch die Autorisierung.

### `403 INSUFFICIENT_SCOPE` [#403-insufficient_scope]

Der Key ist **Read only** oder ein **Custom**-Key ohne den in der Meldung genannten Scope. Erstelle einen Key mit diesem Scope; zu einem bestehenden Key lassen sich keine Scopes hinzufügen.

### API keys aren't available on this deployment yet [#api-keys-arent-available-on-this-deployment-yet]

Eine [selbst gehostete](/docs/self-hosting) Instanz zeigt das, bis ihre Datenbank die Tabelle `api_key` hat, die der Schema-Sync nach einem Update anlegt (der Service `migrate` mit Docker, sonst `bun run db:push`). Bis dahin lehnt die API Keys mit `401` ab. Ihre API liegt unter `/api/v1` auf der eigenen Domain, und genau diese Adresse trägt der Dialog für neue Keys ein.

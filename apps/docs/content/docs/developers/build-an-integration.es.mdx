Al terminar esta página, las personas podrán hacer clic en **Connect QRdx** en tu producto, aprobar tu app en la pantalla de consentimiento de QRdx, y tu servidor tendrá un token de acceso que llama a `https://api.qrdx.dev/v1` en su nombre, limitado a los permisos que aprobaron.

Una integración es una app OAuth. A diferencia de una [clave de API](/docs/developers/api-keys), que actúa como tú en un solo espacio de trabajo, un token actúa como la persona que aprobó tu app, en su propio espacio de trabajo, y esa persona puede retirar el acceso en cualquier momento.

## Antes de empezar [#before-you-start]

- Una cuenta de QRdx. Los espacios de trabajo Gratis pueden tener 1 app OAuth, Pro 5 y Business 25; un espacio de trabajo usa el mejor plan entre sus propietarios.
- Un servidor que pueda guardar un secreto y recibir una redirección. Los ejemplos de código son Node.js con la Fetch API; sirve cualquier lenguaje con HTTPS y SHA-256.
- Las dos URI de redirección `https://` que vas a usar: una para producción y otra para desarrollo (para esta se permite `http://localhost`).

## 1. Crea una app OAuth [#1-create-an-oauth-app]

Abre [Ajustes → Claves de API y apps](/dashboard?to=settings/developers) y elige **Nueva app**. La app pertenece al espacio de trabajo que tengas abierto. Solo los propietarios del espacio de trabajo pueden crear y modificar apps; los administradores y miembros pueden verlas.

<Shot id="oauth-new-app-form" />

| Campo | Para qué sirve |
| --- | --- |
| **Nombre**, **Descripción**, **Logotipo**, **Sitio web** | Se muestran en la pantalla de consentimiento. Sube un logotipo cuadrado de al menos 128 × 128 px, o pega un enlace `https://` a uno |
| **URI de redirección** | Adonde QRdx devuelve a las personas, una por línea, hasta 10. Solo `https://`, además de `http://localhost` para desarrollo. Sin comodines ni `#fragments`: cada solicitud debe enviar una de ellas exactamente |
| **Permisos** | Lo máximo que tu app puede solicitar. Cada autorización pide algunos o todos |
| **Requerir PKCE** | Cada autorización debe enviar un code challenge `S256`. Recomendado y activado por defecto |

Después de guardar, QRdx muestra el **Client ID** y el **Client secret**. Copia el secreto en ese momento: QRdx solo guarda un hash y no puede volver a mostrarlo. Si lo pierdes o se filtra, elige **Regenerar secreto** en la página de la app. El secreto anterior deja de funcionar al instante; las personas que ya se conectaron siguen conectadas. Crear una app y regenerar su secreto te piden [confirmar que eres tú](/docs/help/privacy-and-security/two-step-verification#confirm-its-you) primero, salvo que lo hayas hecho en ese navegador en los últimos 10 minutos.

<Shot id="oauth-app-credentials" />

Guarda ambos valores en tu servidor:

```bash title=".env"
QRDX_CLIENT_ID=qrdx_app_...
QRDX_CLIENT_SECRET=qrdx_secret_...
```

## 2. Envía a las personas a QRdx [#2-send-people-to-qrdx]

Genera un `state` aleatorio y un `code_verifier` de PKCE, guarda ambos en la sesión de la persona y redirige a la URL de autorización:

```txt title="Authorize URL"
https://qrdx.dev/api/oauth/authorize
  ?response_type=code
  &client_id=<client id>
  &redirect_uri=https://acme.example/oauth/qrdx/callback
  &scope=profile:read codes:read codes:write
  &state=<random value>
  &code_challenge=<BASE64URL(SHA256(code_verifier))>
  &code_challenge_method=S256
```

| Parámetro | Obligatorio | Valor |
| --- | --- | --- |
| `response_type` | Sí | `code` |
| `client_id` | Sí | El client ID de tu app |
| `redirect_uri` | Sí | Una de las URI de redirección de la app, carácter por carácter |
| `scope` | Sí | Separados por espacios o comas; solo permisos que tenga la app |
| `state` | Recomendado | Cualquier valor; QRdx lo devuelve sin cambios. Compruébalo al volver para evitar la falsificación de solicitudes entre sitios |
| `code_challenge` | Si la app requiere PKCE | De 43 a 128 caracteres: el SHA-256 en base64url de tu `code_verifier` |
| `code_challenge_method` | No | `S256`, el valor por defecto y el único método aceptado. `plain` se rechaza con `invalid_request` |
| `prompt` | No | `consent` muestra la pantalla de consentimiento aunque la persona ya haya aprobado estos permisos antes |

```ts title="lib/qrdx-oauth.ts"
import { createHash, randomBytes } from "node:crypto";

export const QRDX_AUTHORIZE_URL = "https://qrdx.dev/api/oauth/authorize";

export function createPkce() {
  const verifier = randomBytes(32).toString("base64url"); // 43 characters
  const challenge = createHash("sha256").update(verifier).digest("base64url");
  return { verifier, challenge };
}

export function authorizeUrl({ state, challenge }: { state: string; challenge: string }) {
  const url = new URL(QRDX_AUTHORIZE_URL);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: process.env.QRDX_CLIENT_ID!,
    redirect_uri: "https://acme.example/oauth/qrdx/callback",
    scope: "profile:read codes:read codes:write",
    state,
    code_challenge: challenge,
    code_challenge_method: "S256",
  }).toString();
  return url.toString();
}
```

Las personas que no han iniciado sesión en QRdx lo hacen primero. Después ven la pantalla de consentimiento: el logotipo, el nombre y el sitio web de tu app, quién la creó, los permisos que pediste y la cuenta con la que han iniciado sesión. Las apps que QRdx no ha revisado llevan la nota **Unverified app.** **Authorize** les pide [confirmar que son ellas](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), salvo que lo hayan hecho en los últimos 10 minutos (un inicio de sesión de hace unos instantes cuenta). Quien ya aprobó los mismos permisos para tu app vuelve directamente a ti.

<Shot id="oauth-consent-screen" />

Después QRdx redirige a tu `redirect_uri`:

- Aprobado: `?code=<authorization code>&state=<your state>`. El código funciona una sola vez, durante 10 minutos.
- Cancelado: `?error=access_denied&error_description=...&state=<your state>`.

Las solicitudes no válidas nunca redirigen; responden con JSON en el formato de OAuth 2.0. Un `client_id` desconocido es `invalid_client`, una `redirect_uri` no registrada o un challenge `plain` es `invalid_request`, y un permiso que la app no tiene es `invalid_scope`:

```json title="400 Bad Request"
{"error":"invalid_scope","error_description":"Invalid or unsupported scope"}
```

## 3. Intercambia el código por tokens [#3-exchange-the-code-for-tokens]

Desde tu servidor, envía el código al endpoint de tokens. El cuerpo va codificado como formulario y `redirect_uri` debe ser la misma que usaste en el paso 2.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=authorization_code \
  -d client_id=$QRDX_CLIENT_ID \
  -d client_secret=$QRDX_CLIENT_SECRET \
  -d code=$CODE \
  -d redirect_uri=https://acme.example/oauth/qrdx/callback \
  -d code_verifier=$CODE_VERIFIER
```

```ts title="app/oauth/qrdx/callback/route.ts"
export async function GET(req: Request) {
  const params = new URL(req.url).searchParams;
  const session = await getSession(req); // your own session store
  if (params.get("state") !== session.qrdxState) {
    return new Response("Invalid state", { status: 400 });
  }
  if (params.get("error")) {
    return Response.redirect("https://acme.example/settings?qrdx=canceled");
  }

  const response = await fetch("https://qrdx.dev/api/oauth/token", {
    method: "POST",
    body: new URLSearchParams({
      grant_type: "authorization_code",
      client_id: process.env.QRDX_CLIENT_ID!,
      client_secret: process.env.QRDX_CLIENT_SECRET!,
      code: params.get("code") ?? "",
      redirect_uri: "https://acme.example/oauth/qrdx/callback",
      code_verifier: session.qrdxVerifier,
    }),
  });
  if (!response.ok) {
    const { error, error_description } = await response.json();
    throw new Error(`QRdx token exchange failed: ${error} ${error_description}`);
  }

  const tokens: {
    access_token: string;
    token_type: "Bearer";
    expires_in: number;
    refresh_token: string;
    scope: string;
  } = await response.json();
  await saveQrdxTokens(session.userId, tokens); // encrypt at rest
  return Response.redirect("https://acme.example/settings?qrdx=connected");
}
```

```json title="Response fields"
{
  "access_token": "<send as Authorization: Bearer>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "<store encrypted; it rotates on each refresh>",
  "scope": "profile:read codes:read codes:write"
}
```

`scope` lista lo concedido, separado por espacios. Los tokens de acceso duran 1 hora y los de actualización 30 días. Envía `code_verifier` exactamente cuando la autorización tenía un `code_challenge`; se rechaza un verifier para un código emitido sin él. Un secreto incorrecto o un código ya usado responde `invalid_client` o `invalid_grant`, y un tipo de concesión distinto de los dos admitidos responde:

```json title="400 Bad Request"
{"error":"unsupported_grant_type","error_description":"Supported: authorization_code, refresh_token"}
```

## 4. Actualiza los tokens [#4-refresh-tokens]

Antes de que expire el token de acceso, cambia el token de actualización por un nuevo par. Los tokens de actualización rotan: cada uno funciona una vez, así que guarda el nuevo cada vez.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=refresh_token \
  -d client_id=$QRDX_CLIENT_ID \
  -d client_secret=$QRDX_CLIENT_SECRET \
  -d refresh_token=$REFRESH_TOKEN
```

```ts title="lib/qrdx-oauth.ts"
export async function refreshQrdxTokens(refreshToken: string) {
  const response = await fetch("https://qrdx.dev/api/oauth/token", {
    method: "POST",
    body: new URLSearchParams({
      grant_type: "refresh_token",
      client_id: process.env.QRDX_CLIENT_ID!,
      client_secret: process.env.QRDX_CLIENT_SECRET!,
      refresh_token: refreshToken,
    }),
  });
  // invalid_grant: revoked, expired or already used. Ask the person to reconnect.
  if (!response.ok) throw new Error((await response.json()).error);
  return response.json();
}
```

El endpoint de tokens permite 30 solicitudes por minuto por dirección IP.

## 5. Llama a la API [#5-call-the-api]

Envía el token de acceso como token Bearer a `https://api.qrdx.dev/v1`. Las solicitudes con token actúan sobre el propio espacio de trabajo de la persona que autorizó tu app (toda cuenta tiene uno), con el plan y la [cuota diaria](/docs/developers/rest-api#rate-limits) de ese espacio de trabajo. Pide lo mínimo que tu integración necesite; las personas ven cada permiso en la pantalla de consentimiento.

| Permiso | Permite |
| --- | --- |
| `profile:read` | El id, nombre, correo y avatar del usuario: `GET /v1/me` y `GET /api/oauth/userinfo` |
| `themes:read` | Sus temas de QR guardados: `GET /v1/themes`, `GET /v1/themes/{id}` |
| `codes:read` | Sus códigos dinámicos, analíticas de escaneo y códigos de barras guardados; listar hooks |
| `codes:write` | Todo lo que permite `codes:read`, además de crear, editar y eliminar códigos y códigos de barras, informar conversiones y suscribirse a eventos |

```ts title="lib/qrdx.ts"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${accessToken}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    destinationUrl: "https://acme.example/menu",
    title: "Spring menu",
  }),
});
const { data: code } = await response.json(); // code.shortLink is what the QR encodes
```

Un `401 INVALID_TOKEN` significa que el token expiró o fue revocado: actualízalo o pide a la persona que vuelva a conectarse. Un `403 INSUFFICIENT_SCOPE` significa que al token le falta el permiso. La [referencia de la API](/docs/developers/api) lista cada endpoint con su permiso y sus errores.

## 6. Recibe eventos con webhooks [#6-receive-events-with-webhooks]

Suscríbete en nombre de la persona con la REST Hooks API en lugar de pedirle que pegue una URL. Requiere `codes:write`, y el plan de la persona debe incluir [webhooks](/docs/webhooks) (Business); de lo contrario devuelve `402 PLAN_REQUIRED`.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/hooks \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"target_url": "https://acme.example/webhooks/qrdx", "events": ["scan.created", "form.submitted"]}'
```

La respuesta `201` incluye el `id` de la suscripción y un `secret` de firma, que se muestra una sola vez. Cada entrega se firma con él en `X-QRdx-Signature`; consulta [Verificar firmas](/docs/webhooks#verify-signatures). Cancela la suscripción con `DELETE /v1/hooks/{id}` cuando la persona se desconecte. Las suscripciones también aparecen en **Ajustes → Webhooks** de su propio espacio de trabajo, donde pueden eliminarlas.

## 7. Desconecta e identifica a las personas [#7-disconnect-and-identify-people]

Cuando alguien desconecte QRdx en tu producto, revoca sus tokens. Revocar cualquiera de los dos tokens de un par revoca el par; el endpoint responde `200` incluso con tokens desconocidos.

```bash title="Terminal"
curl -X POST https://qrdx.dev/api/oauth/revoke -d token=$REFRESH_TOKEN
```

Las personas pueden retirar el acceso ellas mismas en cualquier momento, en **Ajustes → Apps autorizadas** de QRdx, con **Revocar acceso**. Todos los tokens que tu app tenga para su cuenta dejan de funcionar al instante: las llamadas a la API responden `401` con `invalid_token` y la actualización responde `invalid_grant`. Trata ambos casos como "desconectado" y pídeles que se conecten de nuevo; verán otra vez la pantalla de consentimiento.

Para identificar quién se conectó, llama a `GET /api/oauth/userinfo` con un token de `profile:read`. Devuelve claims al estilo OpenID, `sub`, `name`, `email` y `picture`; usa `sub` como id de cuenta estable, ya que los correos pueden cambiar.

```bash title="Terminal"
curl https://qrdx.dev/api/oauth/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

```json title="401 Unauthorized: an expired or revoked token"
{"error":"invalid_token","error_description":"Invalid or expired token"}
```

## 8. Aparece en el directorio [#8-get-listed]

Cuando tu integración funcione de principio a fin, pide que la añadan al [directorio de integraciones](/integrations), donde aparece como una integración de la comunidad creada por ti. En la página de tu app, **Get listed** abre un correo a [support@qrdx.dev](mailto:support@qrdx.dev?subject=List%20my%20integration) con los datos ya rellenados:

- el nombre de tu app y el client ID;
- una línea sobre lo que hace y a quién va dirigida;
- los pasos de configuración, o un enlace a ellos;
- un contacto de soporte.

El equipo de QRdx revisa las apps listadas y las marca como **Verified**, lo que elimina la nota **Unverified app.** de la pantalla de consentimiento. Cambiar el nombre, el logotipo o el sitio web de una app verificada quita la insignia hasta que se revise de nuevo.

## Si algo sale mal [#if-something-goes-wrong]

### `invalid_request: redirect_uri not registered` [#invalid_request-redirect_uri-not-registered]

El `redirect_uri` de la URL de autorización no coincide carácter por carácter con ninguno de los URI de redirección de la app, incluidos el esquema y la barra final. Añádelo a la app o corrige la URL.

### `invalid_scope` [#invalid_scope]

La URL de autorización solicita un permiso (scope) que la app no tiene. Añade el permiso a la app en **Settings → API keys & apps** y vuelve a solicitarlo.

### `invalid_grant` al renovar [#invalid_grant-on-refresh]

El token de renovación ya se usó (cada renovación devuelve uno nuevo), caducó a los 30 días o la persona revocó tu app. Vuelve a enviarla al proceso de autorización.

### Los tokens dejan de funcionar después de regenerar el secreto [#tokens-stop-working-after-you-regenerated-the-secret]

Solo las nuevas solicitudes de token usan el secreto nuevo; los tokens de acceso y de renovación existentes siguen siendo válidos. Comprueba que todas las instancias de tu servidor lean el nuevo `QRDX_CLIENT_SECRET`.

## Lista de comprobación de seguridad [#security-checklist]

- Guarda el secreto de cliente en tu servidor. El código del navegador y de las apps móviles nunca debe verlo.
- Usa PKCE (`S256`) y un `state` nuevo en cada autorización, y comprueba `state` al volver.
- Registra URI de redirección exactos; QRdx los compara carácter por carácter.
- Almacena los tokens de acceso y de renovación cifrados, y guarda el nuevo token de renovación después de cada renovación.
- Revoca los tokens cuando las personas se desconecten. Al eliminar tu app en **Settings → API keys & apps** se revocan todos los tokens que emitió; si la pausas, los rechaza hasta que la reanudes.

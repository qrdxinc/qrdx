हर REST API एरर JSON में आता है और उसका ढांचा हमेशा एक जैसा रहता है, चाहे वह किसी भी endpoint से आए। अपने कोड में `code` के आधार पर शाखा बनाएं, क्योंकि वह कभी नहीं बदलता; `message` लोगों के पढ़ने के लिए लिखा गया है और उसके शब्द बदल सकते हैं।

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## एरर बॉडी [#the-error-body]

| फ़ील्ड | यह क्या है |
| --- | --- |
| `code` | ऊपर की टेबल से एक स्थिर, मशीन-रीडेबल कोड |
| `message` | क्या गलत हुआ और उसे कैसे ठीक करें, लोगों के पढ़ने के लिए। शब्द बदल सकते हैं |
| `status` | HTTP स्टेटस, दोबारा दिया गया |
| `docs` | वह पेज जो समाधान समझाता है, जब कोई हो |
| `data` | कुछ एरर पर अतिरिक्त जानकारी। `VALIDATION_ERROR` हर समस्या को `data.details` में सूचीबद्ध करता है |

वैलिडेशन एरर हर उस फ़ील्ड का नाम बताता है जो फ़ेल हुआ। कोड के बैच में हर समस्या के साथ पंक्ति का `index` भी होता है, जो 0 से गिना जाता है:

```json title="400 Bad Request"
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid request body",
  "status": 400,
  "data": {
    "details": [
      { "path": "destinationUrl", "message": "Enter a full URL, starting with https://" }
    ]
  }
}
```

इमेज एंडपॉइंट (`GET /v1/qr`, `GET /v1/barcode`) क्वेरी पैरामीटर को `{ "path", "message" }` की जगह `{ "param", "message" }` के रूप में रिपोर्ट करते हैं।

## दोबारा कोशिश करना [#retrying]

- **`429`:** `Retry-After` में दिए गए सेकंड तक रुकें, फिर वही रिक्वेस्ट भेजें। जब रोज़ का कोटा खत्म हो जाता है, तो `X-RateLimit-*` हेडर बताते हैं कि प्लान कितनी रिक्वेस्ट की अनुमति देता है और गिनती कब रीसेट होगी (00:00 UTC)। प्रति मिनट की लिमिट केवल `Retry-After` भेजती है। देखें [रेट लिमिट](/docs/developers/rest-api#rate-limits)।
- **`500`, `502`, `503` और `504`:** एक्सपोनेंशियल बैकऑफ़ के साथ दोबारा कोशिश करें, लगभग एक सेकंड से शुरू करके। AI आर्ट के `5xx` एरर कभी कोई इमेज इस्तेमाल नहीं करते, इसलिए दोबारा कोशिश करने में कुछ खर्च नहीं होता।
- **बाकी `4xx`:** वही रिक्वेस्ट हर बार उसी तरह फ़ेल होगी। पहले उसे ठीक करें।

`POST /v1/codes` को दोबारा भेजना तब सुरक्षित है जब रिक्वेस्ट में `Idempotency-Key` हेडर हो: वही की पहली कोशिश में बने कोड `Idempotent-Replayed: true` के साथ लौटाती है, उन्हें दो बार नहीं बनाती ([कोड बनाएँ](/docs/developers/api/create-codes))। हेडर के बिना, रिक्वेस्ट दोबारा भेजने से पहले अपने कोड की सूची देखें। `POST /v1/conversions` को दोहराना तब सुरक्षित है जब आप अपना `id` भेजते हैं: दोहराने पर `duplicate: true` के साथ `200` मिलता है।

## `/v1/me` और `/v1/themes` [#v1me-and-v1themes]

ये दो एंडपॉइंट वही बॉडी भेजते हैं, साथ में वे OAuth फ़ील्ड भी जो वे हमेशा से भेजते आए हैं, `error` और `error_description` (`message` वाला ही टेक्स्ट), ताकि पुराने क्लाइंट काम करते रहें:

| `error` | `code` |
| --- | --- |
| `invalid_token` | UNAUTHORIZED या INVALID_TOKEN |
| `insufficient_scope` | INSUFFICIENT_SCOPE |
| `rate_limited` | RATE_LIMITED (रोज़ का कोटा) |
| `not_found` | NOT_FOUND (थीम) |

## OAuth एंडपॉइंट [#oauth-endpoints]

`https://qrdx.dev/api/oauth` के तहत के OAuth एंडपॉइंट (authorize, token, revoke, userinfo) इसके बजाय OAuth 2.0 स्टैंडर्ड का पालन करते हैं: `{ "error", "error_description" }`, जहाँ `error` इनमें से एक होता है: `invalid_request`, `invalid_client`, `invalid_grant`, `unsupported_grant_type`, `invalid_token` या `access_denied`। रिफ़्रेश पर `invalid_grant` मिलने का मतलब है कि रिफ़्रेश टोकन पहले ही इस्तेमाल हो चुका है (हर रिफ़्रेश नया टोकन लौटाता है), 30 दिन बाद एक्सपायर हो गया है, या यूज़र ने आपका ऐप रिवोक कर दिया है: यूज़र को दोबारा ऑथराइज़ेशन से गुज़ारें। देखें [REST API और OAuth](/docs/developers/rest-api#get-an-access-token)।

## अनजान एंडपॉइंट [#unknown-endpoints]

`/v1` के तहत ऐसा पाथ जो मौजूद नहीं है, JSON के रूप में `404 NOT_FOUND` लौटाता है, कभी HTML पेज नहीं, साथ में एंडपॉइंट की सूची का `docs` लिंक होता है। [API रेफ़रेंस](/docs/developers/api) में हर एंडपॉइंट की सूची है।

An API key lets your own servers, scripts and CI jobs call the [REST API](/docs/developers/rest-api) without an OAuth flow. By the end of this page you will have a key for one workspace, know exactly what it may do, and know how to rotate it.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

Every endpoint that takes an OAuth access token takes a key in the same header. The [image API](/docs/developers/image-api) and the [barcode API](/docs/developers/barcode-api) need neither. When your product acts for other QRdx users, use an [OAuth app](/docs/developers/build-an-integration) instead, so each person approves it.

## Before you start

- A QRdx account, signed in. Every plan has API keys.
- The workspace the key is for. A key belongs to one workspace and acts there as you.

## 1. Create a key [#create-a-key]

1. Open [Settings → API keys & apps](/dashboard?to=settings/developers&new=1) in the workspace the key is for. The link opens the workspace you last used; pick another one in the workspace switcher. The **Create API key** form opens.
2. Fill in **Name**: where the key is used, so you know which one to revoke later. Choose its **Access** and, under **Expires**, how long it lives. Choose **Create key**. A key works without you, so QRdx asks you to [confirm it's you](/docs/help/privacy-and-security/two-step-verification#confirm-its-you) first, unless you did in that browser in the last 10 minutes.
3. Copy the key from the **Copy your API key** dialog. It's shown only this once: QRdx stores only a hash of it. The same dialog shows a curl request with the key and this site's API address filled in, ready to paste.

A key is `qrdx_` followed by 40 letters and digits. Lists show only its start, such as `qrdx_7KpQ2m…`, so you can tell keys apart.

## 2. Choose its access [#access]

Keys use the same scopes as OAuth apps. Pick one of three options when you create the key:

| Access | Scopes | Allows |
| --- | --- | --- |
| Full access | `profile:read`, `themes:read`, `codes:read`, `codes:write` | Everything the API does |
| Read only | `profile:read`, `themes:read`, `codes:read` | Read codes, scan analytics, saved barcodes, themes and the profile |
| Custom | The ones you tick | What those scopes allow ([the scope list](/docs/developers/rest-api#scopes)) |

`codes:write` also allows everything `codes:read` does. A key's scopes can't be changed later; create a new key instead. A request outside the key's scopes gets `403 INSUFFICIENT_SCOPE`, and the message names the scope it needed:

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## 3. Use it

Send the key as a Bearer token. The first call worth making is `GET /v1/me`, which returns the profile of the key's creator and confirms the key works:

```bash title="Terminal"
curl https://api.qrdx.dev/v1/me -H "Authorization: Bearer $QRDX_API_KEY"
```

```json title="200 OK"
{"data":{"id":"usr_docsdev0000000000000001","name":"Ada Lovelace","email":"ada@example.com","image":null}}
```

Keep the key on a server, in an environment variable or a secret manager, and read it from there in code:

```js title="qrdx.mjs"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  headers: { Authorization: `Bearer ${process.env.QRDX_API_KEY}` },
});
```

```python title="qrdx.py"
import os
import requests

response = requests.get(
    "https://api.qrdx.dev/v1/codes",
    headers={"Authorization": f"Bearer {os.environ['QRDX_API_KEY']}"},
)
```

## Workspaces and roles [#workspaces-and-roles]

A key belongs to the workspace that was open when you created it, and acts there as you:

- The key works with that workspace's codes, scans, barcodes, hooks and themes, under the workspace's plan and [daily quota](/docs/developers/rest-api#rate-limits).
- It can do what you can do in the workspace, judged by your [role](/docs/teams) at the time of each request. In your own workspace you're the owner. If your role changes, the key's rights change with it; if you leave the workspace, the key stops working, and deleting a workspace deletes its keys.

Every member of a workspace can create keys. Owners and admins see every key in the workspace and can revoke any of them; members see and revoke only their own. Each person can have up to 25 active keys in each workspace; revoked and expired keys don't count.

## Expiry, last use and revoking [#revoke]

- **Expiry.** Under **Expires**, a key lives forever (**Never**) or for 30 days, 90 days or 1 year. An expired key gets `401 INVALID_TOKEN` and stays in the list, marked **Expired**, until you revoke it.
- **Last use.** The list shows the date each key last authenticated a request.
- **Revoking.** Choose **Revoke** next to a key and confirm with **Revoke key**. From then on, requests with it get `401 INVALID_TOKEN`. Revoking can't be undone.

```json title="401 Unauthorized"
{
  "code": "INVALID_TOKEN",
  "message": "Invalid API key: it doesn't exist, was revoked or has expired, or its creator left the workspace. Check that you copied the whole key, or create a new one at https://qrdx.dev/dashboard?to=settings/developers.",
  "status": 401,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## Keep keys safe [#keep-keys-safe]

- Never put a key in a web page, a mobile app, a prompt or a repository. Browser code that needs a QR image uses the keyless [image API](/docs/developers/image-api).
- Use one key per place it runs, so you can revoke one without breaking the others.
- Give scripts that only report a **Read only** key, and give short-lived jobs a key that expires.
- If a key leaks, revoke it and create a new one. The `qrdx_` prefix makes keys easy to find in code and logs, and secret scanners can match `qrdx_[0-9A-Za-z]{40}`.

## If something goes wrong

### `401 UNAUTHORIZED`

The request had no `Authorization` header. Check the header name and that your HTTP client sends it; the value is `Bearer ` followed by the whole key.

### `401 INVALID_TOKEN`

The key was copied short, revoked, expired, or its creator left the workspace. Create a new key. For an OAuth token, refresh it or send the person through authorization again.

### `403 INSUFFICIENT_SCOPE`

The key is **Read only** or a **Custom** key without the scope named in the message. Create a key with that scope; scopes can't be added to an existing key.

### API keys aren't available on this deployment yet

A [self-hosted](/docs/self-hosting) instance shows this until its database has the `api_key` table, which the schema sync after an update creates (the `migrate` service with Docker, `bun run db:push` otherwise). Until then the API refuses keys with `401`. Its API lives at `/api/v1` on its own domain, which is the address the new-key dialog fills in.

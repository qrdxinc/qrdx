API key की मदद से आपके अपने सर्वर, स्क्रिप्ट और CI जॉब बिना OAuth फ़्लो के [REST API](/docs/developers/rest-api) कॉल कर सकते हैं। इस पेज के अंत तक आपके पास एक workspace के लिए एक key होगी, आप जानेंगे कि वह ठीक-ठीक क्या कर सकती है, और उसे रोटेट कैसे करना है।

```bash title="Terminal"
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

जो भी endpoint OAuth access token लेता है, वह उसी header में key भी लेता है। [image API](/docs/developers/image-api) और [barcode API](/docs/developers/barcode-api) को दोनों में से कुछ नहीं चाहिए। जब आपका प्रोडक्ट दूसरे QRdx यूज़र्स की ओर से काम करता है, तो इसके बजाय [OAuth app](/docs/developers/build-an-integration) इस्तेमाल करें, ताकि हर व्यक्ति उसे खुद मंज़ूरी दे।

## शुरू करने से पहले [#before-you-start]

- एक QRdx अकाउंट, जिसमें आप साइन इन हों। हर प्लान में API keys मिलती हैं।
- वह workspace जिसके लिए key बनानी है। key एक workspace की होती है और वहाँ आपके रूप में काम करती है।

## 1. key बनाएँ [#create-a-key]

1. जिस workspace के लिए key चाहिए, उसमें [Settings → API keys & apps](/dashboard?to=settings/developers&new=1) खोलें। लिंक आपका पिछली बार इस्तेमाल किया हुआ workspace खोलता है; दूसरा चुनने के लिए workspace switcher इस्तेमाल करें। **Create API key** फ़ॉर्म खुल जाएगा।
2. **Name** भरें: key कहाँ इस्तेमाल होती है, ताकि बाद में पता रहे कि कौन-सी रद्द करनी है। उसका **Access** चुनें और **Expires** के तहत चुनें कि वह कितने समय तक चलेगी। **Create key** चुनें। key आपके बिना भी काम करती है, इसलिए QRdx पहले आपसे [पुष्टि करने](/docs/help/privacy-and-security/two-step-verification#confirm-its-you) को कहता है कि यह आप ही हैं, जब तक कि आपने उसी ब्राउज़र में पिछले 10 मिनट में ऐसा न किया हो।
3. **Copy your API key** डायलॉग से key कॉपी करें। यह सिर्फ़ इसी एक बार दिखती है: QRdx उसका सिर्फ़ hash सहेजता है। इसी डायलॉग में एक curl request भी दिखती है, जिसमें key और इस साइट का API पता भरा होता है, यानी सीधे पेस्ट करने लायक।

## 2. उसका access चुनें [#access]

keys में वही scopes होते हैं जो OAuth apps में होते हैं। key बनाते समय तीन विकल्पों में से एक चुनें:

| Access | Scopes | क्या करने देता है |
| --- | --- | --- |
| Full access | `profile:read`, `themes:read`, `codes:read`, `codes:write` | API जो कुछ भी करता है |
| Read only | `profile:read`, `themes:read`, `codes:read` | कोड, स्कैन analytics, सहेजे गए barcodes, themes और प्रोफ़ाइल पढ़ना |
| Custom | जो आप टिक करें | उन scopes से जो कुछ संभव हो ([scope सूची](/docs/developers/rest-api#scopes)) |

`codes:write` वह सब भी करने देता है जो `codes:read` करने देता है। key के scopes बाद में बदले नहीं जा सकते; इसके बजाय नई key बनाएँ। key के scopes से बाहर की request को `403 INSUFFICIENT_SCOPE` मिलता है, और संदेश में उस scope का नाम होता है जो ज़रूरी था:

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## 3. उसे इस्तेमाल करें [#3-use-it]

key को Bearer token के रूप में भेजें। पहली कॉल `GET /v1/me` करना ठीक रहता है, जो key बनाने वाले की प्रोफ़ाइल लौटाती है और पुष्टि करती है कि key काम कर रही है:

```bash title="Terminal"
curl https://api.qrdx.dev/v1/me -H "Authorization: Bearer $QRDX_API_KEY"
```

```json title="200 OK"
{"data":{"id":"usr_docsdev0000000000000001","name":"Ada Lovelace","email":"ada@example.com","image":null}}
```

key को सर्वर पर रखें, किसी environment variable या secret manager में, और कोड में वहीं से पढ़ें:

```js title="qrdx.mjs"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  headers: { Authorization: `Bearer ${process.env.QRDX_API_KEY}` },
});
```

```python title="qrdx.py"
import os
import requests

response = requests.get(
    "https://api.qrdx.dev/v1/codes",
    headers={"Authorization": f"Bearer {os.environ['QRDX_API_KEY']}"},
)
```

## Workspaces और roles [#workspaces-and-roles]

key उस workspace की होती है जो उसे बनाते समय खुला था, और वहाँ आपके रूप में काम करती है:

- key उस workspace के कोड, स्कैन, barcodes, hooks और themes के साथ काम करती है, workspace के प्लान और [दैनिक कोटा](/docs/developers/rest-api#rate-limits) के अंतर्गत।
- वह वही कर सकती है जो आप workspace में कर सकते हैं, हर request के समय आपके [role](/docs/teams) के आधार पर। अपने workspace में आप owner हैं। अगर आपका role बदलता है, तो key के अधिकार भी बदल जाते हैं; अगर आप workspace छोड़ देते हैं, तो key काम करना बंद कर देती है, और workspace हटाने पर उसकी keys भी हट जाती हैं।

workspace का हर सदस्य keys बना सकता है। Owners और admins workspace की हर key देखते हैं और किसी को भी रद्द कर सकते हैं; members सिर्फ़ अपनी keys देखते और रद्द करते हैं। हर व्यक्ति के हर workspace में अधिकतम 25 सक्रिय keys हो सकती हैं; रद्द और एक्सपायर हो चुकी keys गिनी नहीं जातीं।

## एक्सपायरी, आख़िरी इस्तेमाल और रद्द करना [#revoke]

- **एक्सपायरी।** **Expires** के तहत key हमेशा के लिए चलती है (**Never**) या 30 दिन, 90 दिन या 1 साल के लिए। एक्सपायर हो चुकी key को `401 INVALID_TOKEN` मिलता है और वह सूची में **Expired** के निशान के साथ तब तक रहती है जब तक आप उसे रद्द नहीं करते।
- **आख़िरी इस्तेमाल।** सूची में वह तारीख़ दिखती है जब हर key ने आख़िरी बार किसी request को authenticate किया।
- **रद्द करना।** key के पास **Revoke** चुनें और **Revoke key** से पुष्टि करें। उसके बाद उससे की गई requests को `401 INVALID_TOKEN` मिलता है। रद्द करना वापस नहीं हो सकता।

```json title="401 Unauthorized"
{
  "code": "INVALID_TOKEN",
  "message": "Invalid API key: it doesn't exist, was revoked or has expired, or its creator left the workspace. Check that you copied the whole key, or create a new one at https://qrdx.dev/dashboard?to=settings/developers.",
  "status": 401,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## keys को सुरक्षित रखें [#keep-keys-safe]

- key को कभी किसी वेब पेज, मोबाइल app, prompt या repository में न रखें। जिस ब्राउज़र कोड को QR इमेज चाहिए, वह बिना key वाला [image API](/docs/developers/image-api) इस्तेमाल करे।
- जहाँ-जहाँ key चलती है, वहाँ के लिए अलग key रखें, ताकि एक को रद्द करने से बाकी न टूटें।
- जो स्क्रिप्ट सिर्फ़ रिपोर्ट बनाती हैं, उन्हें **Read only** key दें, और कम समय के जॉब को ऐसी key दें जो एक्सपायर हो जाए।
- अगर कोई key लीक हो जाए, तो उसे रद्द करें और नई बनाएँ। `qrdx_` प्रीफ़िक्स की वजह से keys को कोड और logs में ढूँढना आसान होता है, और secret scanners `qrdx_[0-9A-Za-z]{40}` से उन्हें मैच कर सकते हैं।

## अगर कुछ गड़बड़ हो जाए [#if-something-goes-wrong]

### `401 UNAUTHORIZED` [#401-unauthorized]

request में `Authorization` header नहीं था। header का नाम जाँचें और देखें कि आपका HTTP client उसे भेज रहा है; वैल्यू `Bearer ` और उसके बाद पूरी key होती है।

### `401 INVALID_TOKEN` [#401-invalid_token]

key अधूरी कॉपी हुई थी, रद्द हो गई थी, एक्सपायर हो गई थी, या उसे बनाने वाले ने workspace छोड़ दिया। नई key बनाएँ। OAuth token के लिए, उसे रिफ़्रेश करें या व्यक्ति को फिर से authorization से गुज़ारें।

### `403 INSUFFICIENT_SCOPE` [#403-insufficient_scope]

key **Read only** है या ऐसी **Custom** key है जिसमें संदेश में बताया गया scope नहीं है। उस scope वाली key बनाएँ; मौजूदा key में scopes जोड़े नहीं जा सकते।

### इस deployment पर API keys अभी उपलब्ध नहीं हैं [#api-keys-arent-available-on-this-deployment-yet]

[सेल्फ़-होस्टेड](/docs/self-hosting) instance तब तक यह दिखाता है जब तक उसके database में `api_key` टेबल नहीं आ जाती, जिसे अपडेट के बाद का schema sync बनाता है (Docker में `migrate` service, वरना `bun run db:push`)। तब तक API keys को `401` के साथ ठुकरा देता है। उसका API अपने ही डोमेन पर `/api/v1` पर होता है, और नई key के डायलॉग में यही पता भरा जाता है।

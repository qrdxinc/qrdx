Uma chave de API permite que seus próprios servidores, scripts e jobs de CI chamem a [REST API](/docs/developers/rest-api) sem um fluxo OAuth. Ao final desta página, você terá uma chave para um workspace, saberá exatamente o que ela pode fazer e como rotacioná-la.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

Todo endpoint que aceita um token de acesso OAuth aceita uma chave no mesmo header. A [Image API](/docs/developers/image-api) e a [API de códigos de barras](/docs/developers/barcode-api) não precisam de nenhum dos dois. Quando seu produto age em nome de outros usuários do QRdx, use um [app OAuth](/docs/developers/build-an-integration), para que cada pessoa o aprove.

## Antes de começar [#before-you-start]

- Uma conta QRdx, com login feito. Todos os planos têm chaves de API.
- O workspace para o qual a chave se destina. Uma chave pertence a um workspace e age nele como você.

## 1. Crie uma chave [#create-a-key]

1. Abra [Configurações → Chaves de API e apps](/dashboard?to=settings/developers&new=1) no workspace para o qual a chave se destina. O link abre o último workspace que você usou; escolha outro no seletor de workspace. O formulário **Criar chave de API** é aberto.
2. Preencha **Nome**: onde a chave é usada, para saber qual revogar depois. Escolha o **Acesso** e, em **Expira**, por quanto tempo ela vale. Escolha **Criar chave**. Uma chave funciona sem você, então o QRdx pede que você [confirme que é você](/docs/help/privacy-and-security/two-step-verification#confirm-its-you) antes, a menos que você já tenha confirmado nesse navegador nos últimos 10 minutos.
3. Copie a chave na janela **Copie sua chave de API**. Ela aparece só desta vez: o QRdx guarda apenas um hash dela. A mesma janela mostra uma requisição curl com a chave e o endereço da API deste site já preenchidos, pronta para colar.

Uma chave é `qrdx_` seguido de 40 letras e dígitos. As listas mostram só o início dela, como `qrdx_7KpQ2m…`, para você distinguir as chaves.

## 2. Escolha o acesso [#access]

As chaves usam os mesmos escopos dos apps OAuth. Escolha uma de três opções ao criar a chave:

| Acesso | Escopos | Permite |
| --- | --- | --- |
| Acesso total | `profile:read`, `themes:read`, `codes:read`, `codes:write` | Tudo o que a API faz |
| Somente leitura | `profile:read`, `themes:read`, `codes:read` | Ler códigos, análises de leituras, códigos de barras salvos, temas e o perfil |
| Personalizado | Os que você marcar | O que esses escopos permitem ([a lista de escopos](/docs/developers/rest-api#scopes)) |

`codes:write` também permite tudo o que `codes:read` permite. Os escopos de uma chave não podem ser alterados depois; crie uma nova chave. Uma requisição fora dos escopos da chave recebe `403 INSUFFICIENT_SCOPE`, e a mensagem indica o escopo necessário:

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## 3. Use a chave [#3-use-it]

Envie a chave como token Bearer. A primeira chamada que vale a pena fazer é `GET /v1/me`, que retorna o perfil de quem criou a chave e confirma que ela funciona:

```bash title="Terminal"
curl https://api.qrdx.dev/v1/me -H "Authorization: Bearer $QRDX_API_KEY"
```

```json title="200 OK"
{"data":{"id":"usr_docsdev0000000000000001","name":"Ada Lovelace","email":"ada@example.com","image":null}}
```

Mantenha a chave em um servidor, em uma variável de ambiente ou em um gerenciador de segredos, e leia-a de lá no código:

```js title="qrdx.mjs"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  headers: { Authorization: `Bearer ${process.env.QRDX_API_KEY}` },
});
```

```python title="qrdx.py"
import os
import requests

response = requests.get(
    "https://api.qrdx.dev/v1/codes",
    headers={"Authorization": f"Bearer {os.environ['QRDX_API_KEY']}"},
)
```

## Workspaces e funções [#workspaces-and-roles]

Uma chave pertence ao workspace que estava aberto quando você a criou e age nele como você:

- A chave trabalha com os códigos, leituras, códigos de barras, hooks e temas desse workspace, de acordo com o plano do workspace e a [cota diária](/docs/developers/rest-api#rate-limits).
- Ela pode fazer o que você pode fazer no workspace, conforme sua [função](/docs/teams) no momento de cada requisição. No seu próprio workspace, você é o proprietário. Se sua função mudar, as permissões da chave mudam junto; se você sair do workspace, a chave deixa de funcionar, e excluir um workspace exclui as chaves dele.

Todo membro de um workspace pode criar chaves. Proprietários e administradores veem todas as chaves do workspace e podem revogar qualquer uma; membros veem e revogam apenas as próprias. Cada pessoa pode ter até 25 chaves ativas em cada workspace; chaves revogadas e expiradas não contam.

## Expiração, último uso e revogação [#revoke]

- **Expiração.** Em **Expira**, uma chave vale para sempre (**Nunca**) ou por 30 dias, 90 dias ou 1 ano. Uma chave expirada recebe `401 INVALID_TOKEN` e continua na lista, marcada como **Expirada**, até você revogá-la.
- **Último uso.** A lista mostra a data em que cada chave autenticou uma requisição pela última vez.
- **Revogação.** Escolha **Revogar** ao lado de uma chave e confirme com **Revogar chave**. A partir daí, as requisições com ela recebem `401 INVALID_TOKEN`. A revogação não pode ser desfeita.

```json title="401 Unauthorized"
{
  "code": "INVALID_TOKEN",
  "message": "Invalid API key: it doesn't exist, was revoked or has expired, or its creator left the workspace. Check that you copied the whole key, or create a new one at https://qrdx.dev/dashboard?to=settings/developers.",
  "status": 401,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## Mantenha as chaves seguras [#keep-keys-safe]

- Nunca coloque uma chave em uma página web, em um app mobile, em um prompt ou em um repositório. O código de navegador que precisa de uma imagem de QR usa a [Image API](/docs/developers/image-api), que dispensa chave.
- Use uma chave para cada lugar onde ela roda, para poder revogar uma sem quebrar as outras.
- Dê uma chave **Somente leitura** aos scripts que só geram relatórios, e dê uma chave com expiração aos jobs de curta duração.
- Se uma chave vazar, revogue-a e crie uma nova. O prefixo `qrdx_` facilita encontrar chaves em código e logs, e os scanners de segredos podem usar `qrdx_[0-9A-Za-z]{40}`.

## Se algo der errado [#if-something-goes-wrong]

### `401 UNAUTHORIZED` [#401-unauthorized]

A requisição não tinha o header `Authorization`. Confira o nome do header e se o seu cliente HTTP o envia; o valor é `Bearer ` seguido da chave inteira.

### `401 INVALID_TOKEN` [#401-invalid_token]

A chave foi copiada incompleta, foi revogada, expirou, ou quem a criou saiu do workspace. Crie uma nova chave. Para um token OAuth, atualize-o ou envie a pessoa de novo pela autorização.

### `403 INSUFFICIENT_SCOPE` [#403-insufficient_scope]

A chave é **Somente leitura** ou uma chave **Personalizada** sem o escopo indicado na mensagem. Crie uma chave com esse escopo; não é possível adicionar escopos a uma chave existente.

### As chaves de API ainda não estão disponíveis neste deployment [#api-keys-arent-available-on-this-deployment-yet]

Uma instância [auto-hospedada](/docs/self-hosting) mostra isso até o banco de dados ter a tabela `api_key`, que a sincronização do esquema após uma atualização cria (o serviço `migrate` com Docker, `bun run db:push` nos outros casos). Até lá, a API recusa chaves com `401`. A API dela fica em `/api/v1` no próprio domínio, que é o endereço que a janela de nova chave preenche.

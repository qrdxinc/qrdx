Une clé API permet à vos propres serveurs, scripts et tâches CI d'appeler la [REST API](/docs/developers/rest-api) sans passer par un flux OAuth. À la fin de cette page, vous aurez une clé pour un espace de travail, vous saurez précisément ce qu'elle peut faire et comment la renouveler.

```bash title="Terminal"
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

Tout endpoint qui accepte un jeton d'accès OAuth accepte une clé dans le même en-tête. L'[Image API](/docs/developers/image-api) et l'[API de codes-barres](/docs/developers/barcode-api) n'ont besoin ni de l'un ni de l'autre. Lorsque votre produit agit pour d'autres utilisateurs de QRdx, utilisez plutôt une [application OAuth](/docs/developers/build-an-integration) : chaque personne l'autorise elle-même.

## Avant de commencer [#before-you-start]

- Un compte QRdx, connecté. Tous les forfaits donnent accès aux clés API.
- L'espace de travail auquel la clé est destinée. Une clé appartient à un seul espace de travail et y agit en votre nom.

## 1. Créer une clé [#create-a-key]

1. Ouvrez [Paramètres → Clés API et applications](/dashboard?to=settings/developers&new=1) dans l'espace de travail concerné. Le lien ouvre le dernier espace de travail utilisé ; choisissez-en un autre dans le sélecteur d'espace de travail. Le formulaire **Créer une clé API** s'ouvre.
2. Renseignez **Nom** : indiquez où la clé est utilisée, afin de savoir plus tard laquelle révoquer. Choisissez son **Accès** et, sous **Expiration**, sa durée de vie. Choisissez **Créer la clé**. Une clé fonctionne sans vous : QRdx vous demande donc de [confirmer que c'est bien vous](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), sauf si vous l'avez déjà fait dans ce navigateur au cours des 10 dernières minutes.
3. Copiez la clé depuis la boîte de dialogue **Copiez votre clé API**. Elle n'est affichée qu'une seule fois : QRdx n'en conserve qu'un hash. La même boîte de dialogue affiche une requête curl avec la clé et l'adresse API de ce site déjà renseignées, prête à coller.

Une clé se compose de `qrdx_` suivi de 40 lettres et chiffres. Les listes n'en affichent que le début, par exemple `qrdx_7KpQ2m…`, pour que vous puissiez distinguer les clés.

## 2. Choisir son accès [#access]

Les clés utilisent les mêmes scopes que les applications OAuth. Choisissez l'une des trois options lors de la création de la clé :

| Accès | Scopes | Autorise |
| --- | --- | --- |
| Accès complet | `profile:read`, `themes:read`, `codes:read`, `codes:write` | Tout ce que fait l'API |
| Lecture seule | `profile:read`, `themes:read`, `codes:read` | Lire les codes, les statistiques de scan, les codes-barres enregistrés, les thèmes et le profil |
| Personnalisé | Ceux que vous cochez | Ce que ces scopes autorisent ([la liste des scopes](/docs/developers/rest-api#scopes)) |

`codes:write` autorise aussi tout ce que permet `codes:read`. Les scopes d'une clé ne peuvent pas être modifiés par la suite ; créez plutôt une nouvelle clé. Une requête hors des scopes de la clé reçoit `403 INSUFFICIENT_SCOPE`, et le message indique le scope requis :

```json title="403 Forbidden"
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## 3. L'utiliser [#3-use-it]

Envoyez la clé comme jeton Bearer. Le premier appel à faire est `GET /v1/me`, qui renvoie le profil du créateur de la clé et confirme que la clé fonctionne :

```bash title="Terminal"
curl https://api.qrdx.dev/v1/me -H "Authorization: Bearer $QRDX_API_KEY"
```

```json title="200 OK"
{"data":{"id":"usr_docsdev0000000000000001","name":"Ada Lovelace","email":"ada@example.com","image":null}}
```

Conservez la clé sur un serveur, dans une variable d'environnement ou un gestionnaire de secrets, et lisez-la à partir de là dans votre code :

```js title="qrdx.mjs"
const response = await fetch("https://api.qrdx.dev/v1/codes", {
  headers: { Authorization: `Bearer ${process.env.QRDX_API_KEY}` },
});
```

```python title="qrdx.py"
import os
import requests

response = requests.get(
    "https://api.qrdx.dev/v1/codes",
    headers={"Authorization": f"Bearer {os.environ['QRDX_API_KEY']}"},
)
```

## Espaces de travail et rôles [#workspaces-and-roles]

Une clé appartient à l'espace de travail qui était ouvert lors de sa création et y agit en votre nom :

- La clé fonctionne avec les codes, les scans, les codes-barres, les hooks et les thèmes de cet espace de travail, selon le forfait de l'espace de travail et son [quota quotidien](/docs/developers/rest-api#rate-limits).
- Elle peut faire ce que vous pouvez faire dans l'espace de travail, selon votre [rôle](/docs/teams) au moment de chaque requête. Dans votre propre espace de travail, vous êtes propriétaire. Si votre rôle change, les droits de la clé changent avec lui ; si vous quittez l'espace de travail, la clé cesse de fonctionner, et la suppression d'un espace de travail supprime ses clés.

Tous les membres d'un espace de travail peuvent créer des clés. Les propriétaires et les administrateurs voient toutes les clés de l'espace de travail et peuvent révoquer n'importe laquelle ; les membres ne voient et ne révoquent que les leurs. Chaque personne peut avoir jusqu'à 25 clés actives dans chaque espace de travail ; les clés révoquées et expirées ne comptent pas.

## Expiration, dernière utilisation et révocation [#revoke]

- **Expiration.** Sous **Expiration**, une clé est valable indéfiniment (**Jamais**) ou pendant 30 jours, 90 jours ou 1 an. Une clé expirée reçoit `401 INVALID_TOKEN` et reste dans la liste, marquée **Expirée**, jusqu'à ce que vous la révoquiez.
- **Dernière utilisation.** La liste affiche la date à laquelle chaque clé a authentifié une requête pour la dernière fois.
- **Révocation.** Choisissez **Révoquer** à côté d'une clé et confirmez avec **Révoquer la clé**. Dès lors, les requêtes faites avec elle reçoivent `401 INVALID_TOKEN`. Une révocation est irréversible.

```json title="401 Unauthorized"
{
  "code": "INVALID_TOKEN",
  "message": "Invalid API key: it doesn't exist, was revoked or has expired, or its creator left the workspace. Check that you copied the whole key, or create a new one at https://qrdx.dev/dashboard?to=settings/developers.",
  "status": 401,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

## Protéger vos clés [#keep-keys-safe]

- Ne placez jamais une clé dans une page web, une application mobile, un prompt ou un dépôt. Le code navigateur qui a besoin d'une image QR utilise l'[Image API](/docs/developers/image-api), qui ne requiert aucune clé.
- Utilisez une clé par lieu d'exécution, pour pouvoir en révoquer une sans casser les autres.
- Donnez une clé **Lecture seule** aux scripts qui se contentent de produire des rapports, et une clé qui expire aux tâches de courte durée.
- Si une clé fuit, révoquez-la et créez-en une nouvelle. Le préfixe `qrdx_` rend les clés faciles à repérer dans le code et les journaux, et les outils d'analyse de secrets peuvent détecter `qrdx_[0-9A-Za-z]{40}`.

## En cas de problème [#if-something-goes-wrong]

### `401 UNAUTHORIZED` [#401-unauthorized]

La requête ne contenait pas d'en-tête `Authorization`. Vérifiez le nom de l'en-tête et que votre client HTTP l'envoie ; la valeur est `Bearer ` suivi de la clé complète.

### `401 INVALID_TOKEN` [#401-invalid_token]

La clé a été copiée de façon incomplète, révoquée, ou a expiré, ou son créateur a quitté l'espace de travail. Créez une nouvelle clé. Pour un jeton OAuth, actualisez-le ou renvoyez la personne vers l'autorisation.

### `403 INSUFFICIENT_SCOPE` [#403-insufficient_scope]

La clé est en **Lecture seule**, ou c'est une clé **Personnalisé** sans le scope indiqué dans le message. Créez une clé avec ce scope ; on ne peut pas ajouter de scopes à une clé existante.

### Les clés API ne sont pas encore disponibles sur ce déploiement [#api-keys-arent-available-on-this-deployment-yet]

Une instance [auto-hébergée](/docs/self-hosting) affiche ce message tant que sa base de données n'a pas la table `api_key`, que crée la synchronisation du schéma après une mise à jour (le service `migrate` avec Docker, `bun run db:push` sinon). D'ici là, l'API refuse les clés avec `401`. Son API se trouve à `/api/v1` sur son propre domaine, qui est l'adresse que la boîte de dialogue de nouvelle clé renseigne.

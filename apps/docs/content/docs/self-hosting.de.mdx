Am Ende dieser Anleitung läuft QRdx unter deiner eigenen URL: mit QR-Editor, Konten, dynamischen QR-Codes mit Scan-Analytics, gehosteten Seiten, Workspaces und gespeicherten Themes, auf einer Postgres-Datenbank, die du selbst kontrollierst. Mit Docker Compose dauert das etwa eine halbe Stunde, den größten Teil davon braucht der erste Image-Build.

Die Web-App ist Open Source unter der AGPL-3.0-Lizenz. Zwei Teile sind es nicht: Single Sign-on für Workspaces und das Audit-Log liegen in den `ee/`-Ordnern unter der kommerziellen QRdx-Lizenz und bleiben deaktiviert, solange du keinen Lizenzschlüssel (`QRDX_EE_LICENSE`) setzt. Für den Einsatz in der Produktion brauchst du eine schriftliche Vereinbarung mit QRdx; siehe [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md). Für die [`qrdx`-React-Bibliothek](/docs/getting-started) und die [CLI](/docs/developers/cli) brauchst du das alles nicht: Sie laufen überall ohne Backend, unter der MIT-Lizenz. [Open Source bei QRdx](/open-source-qr-code-generator) listet jeden Teil des Repositorys mit seiner Lizenz auf.

  Wenn ein Schritt nicht wie beschrieben funktioniert, [eröffne ein Issue](https://github.com/qrdxinc/qrdx/issues) mit dem ausgeführten Befehl und dessen Ausgabe.

## Bevor du anfängst [#before-you-start]

- Docker mit Compose v2 und BuildKit (Docker Desktop und die aktuelle Docker Engine enthalten beides) oder Node.js 22 (22.22.3 oder neuer) und [Bun](https://bun.com/docs/installation) 1.4 für das manuelle Setup.
- Mindestens 8 GB Arbeitsspeicher für Docker, während das Image gebaut wird.
- Eine Möglichkeit zum Anmelden, damit Konten angelegt werden können: eine GitHub- oder Google-OAuth-App oder [Resend](https://resend.com) für Anmeldecodes per E-Mail. Anmeldecodes werden nur dann per E-Mail verschickt, wenn `NEXT_PUBLIC_APP_URL` nicht `localhost` ist. `bun run dev` gibt sie stattdessen im Terminal aus, das Docker-Image tut das aber nicht. Für einen lokalen Docker-Test brauchst du also die Anmeldung über GitHub oder Google.
- Postgres: der in `docker-compose.yml` enthaltene Container oder eine [Neon](https://neon.tech)-Datenbank.
- Für alles, was über einen lokalen Test hinausgeht, eine Domain und einen Reverse-Proxy, der HTTPS terminiert.

Die Dokumentation gehört nicht zu einer selbst gehosteten Instanz. Deine Instanz leitet jeden Docs-Link (`/docs` und die Seiten darunter, ihre Markdown-Kopien und `/llms-full.txt`) auf dieselben Seiten bei qrdx.dev weiter.

### So funktioniert die Datenbankverbindung [#how-the-database-connection-works]

Die App spricht mit Postgres über den serverlosen HTTP-Treiber von Neon.

- **Neon:** funktioniert direkt. Setze `DATABASE_URL` auf deinen Neon-Verbindungsstring.
- **Normales Postgres:** braucht davor einen Neon-kompatiblen HTTP-Proxy. `docker-compose.yml` startet einen ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) und setzt `DATABASE_HTTP_ENDPOINT`, damit die App ihre Abfragen dorthin schickt.

Das Schema stammt aus `packages/database/schema.ts` und wird mit `drizzle-kit push` angewendet. Es gibt keine Migrationsdateien, die du von Hand ausführen müsstest.

## Schnellstart mit Docker Compose [#quick-start-with-docker-compose]

### 1. Repository klonen [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. Umgebung konfigurieren [#2-configure-the-environment]

Kopiere die Beispieldatei ins Stammverzeichnis des Repositorys, wo Compose sie liest, und erzeuge das Session-Secret:

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

Öffne `.env` und setze diese Werte. Alle anderen Zeilen können auskommentiert bleiben.

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

Woher die einzelnen Werte kommen:

| Variable | Woher du sie bekommst |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | Die öffentliche URL deiner Instanz, ohne abschließenden Schrägstrich. Für einen lokalen Test bleibt es bei `http://localhost:3000`. |
| `BETTER_AUTH_URL` | Derselbe Wert. Entferne das Kommentarzeichen vor der Zeile. |
| `BETTER_AUTH_SECRET` | Die Ausgabe von `openssl rand -base64 32`. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | Eine [GitHub-OAuth-App](https://github.com/settings/developers), deren Callback-URL `<your url>/api/auth/callback/github` lautet. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Alternativ zu GitHub: ein [Google-OAuth-Client](https://console.cloud.google.com/apis/credentials), dessen Redirect-URI `<your url>/api/auth/callback/google` lautet. |

Lass `DATABASE_URL` unverändert: Compose richtet die App auf den eigenen Postgres-Container aus und ignoriert den Wert in `.env`. Um das Datenbankpasswort zu ändern, setze `POSTGRES_PASSWORD` vor dem ersten Start.

### 3. Stack starten [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

Dabei wird das Image gebaut, Postgres und der Proxy werden gestartet, der einmalige `migrate`-Service (`drizzle-kit push`) läuft durch, und danach startet die App auf Port 3000. Der erste Build dauert mehrere Minuten. Wenn er fertig ist, sehen die vier Services so aus:

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

`migrate` soll sich beenden: Er synchronisiert das Schema und stoppt dann. So siehst du die Schema-Synchronisierung und den Start der App:

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. Anmelden [#4-sign-in]

Öffne `NEXT_PUBLIC_APP_URL` in einem Browser und melde dich mit GitHub, Google oder einem E-Mail-Code an. Dein Konto wird bei der ersten Anmeldung angelegt.

### 5. Dich selbst zum Admin machen [#5-make-yourself-an-admin]

Trage die E-Mail-Adresse des Kontos, das du in Schritt 4 angelegt hast, in `.env` ein:

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

Erstelle den App-Container neu, damit er die Änderung einliest, melde dich dann an und öffne `/admin`:

```bash title="Terminal"
docker compose up -d app
```

Die Adresse wird zum Admin, sobald sie zum ersten Mal `/admin` öffnet. `ADMIN_USER_IDS` funktioniert genauso, nur mit Nutzer-IDs.

## Neon oder ein anderes verwaltetes Postgres verwenden [#use-neon-or-another-managed-postgres]

Du kannst das mitgelieferte Postgres weglassen und nur das App-Image betreiben. Setze `DATABASE_URL` in `.env` auf deinen Neon-Verbindungsstring und lass `DATABASE_HTTP_ENDPOINT` ungesetzt.

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Wende das Schema einmal an, und nach jedem Update erneut, mit dem Migrator-Image:

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Manuelles Setup mit Node.js [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

Für die Produktion baust du die App und startest sie:

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` verbindet sich mit dem Neon-Treiber und braucht deshalb eine Neon-Datenbank. Wenn du stattdessen das Docker-Postgres für die lokale Entwicklung nutzen willst, starte es mit `docker compose up -d db db-proxy`, wende das Schema mit `docker compose run --rm migrate` an und setze diese Werte in `apps/app/.env.local`:

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

  `NEXT_PUBLIC_*`-Werte werden beim Build der App in das Browser-Bundle eingebettet, eine Änderung erfordert also einen neuen Build. Der Docker-Build liest `.env` nur für sechs davon, die in `docker-compose.yml` als Build-Argumente übergeben werden: `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`, `NEXT_PUBLIC_FEATUREBASE_APP_ID` und die beiden Pro-Produkt-IDs. Um eine weitere im Docker-Image zu setzen (die Business-Produkt-IDs, `NEXT_PUBLIC_QRDX_EUR_PRICES`, `NEXT_PUBLIC_SHORT_LINK_BASE_URL`, den Turnstile-Site-Key oder die Umami-IDs), trage sie in `build.args` des Dienstes `app` in `docker-compose.yml` und als `ARG` in der Build-Stage des Dockerfiles ein und führe dann `docker compose up -d --build` aus. Das manuelle Setup liest sie alle aus `apps/app/.env.local`.
</Callout>

### Geplante Jobs [#scheduled-jobs]

Zwei Routen erledigen die wiederkehrende Arbeit: `/api/cron/webhooks` wiederholt fehlgeschlagene Webhook-Zustellungen und löscht alte Audit-Log-Einträge, und `/api/cron/digest` sendet die Wochenübersicht. Auf Vercel plant `apps/app/vercel.json` sie ein. Überall sonst ruft sie niemand auf, bis du es tust. Setze `CRON_SECRET` und rufe beide mit diesem Wert von deinem Scheduler aus auf:

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

Ohne den Header antworten die Routen in Produktion mit `401`. [Benachrichtigungen](/docs/notifications#self-hosting) erklärt den Parameter `shard` der Wochenübersicht.

## Reverse Proxy und HTTPS [#reverse-proxy-and-https]

Stelle die App hinter einen Reverse Proxy wie Caddy, nginx oder Traefik, der TLS terminiert, und gib Port 3000 nicht direkt ins Internet frei. Rate Limiting, die Sicherheits-E-Mails und das [Audit-Log](/docs/help/teams/audit-log) lesen die Client-IP zuerst aus `X-Real-IP` und dann aus der ersten Adresse in `X-Forwarded-For` (auf Vercel kommt `X-Vercel-Forwarded-For` dazwischen). Der Proxy muss diese Header also setzen, und die App darf nur über ihn erreichbar sein. Lass den Proxy `X-Real-IP` auf die Adresse setzen, von der er die Verbindung erhalten hat. Ein Proxy, der nur an `X-Forwarded-For` anhängt, erlaubt es einem Client, eine beliebige Adresse an die erste Stelle zu setzen.

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

Caddy setzt diese Header standardmäßig. Sobald HTTPS funktioniert, ändere `NEXT_PUBLIC_APP_URL` und `BETTER_AUTH_URL` auf die `https://`-URL, aktualisiere die OAuth-Callback-URLs und baue neu.

### Content-Security-Policy [#content-security-policy]

Produktions-Builds senden auf den eigenen Seiten von QRdx eine Content-Security-Policy: Angemeldete Seiten erhalten pro Anfrage eine neue Script-Nonce, vorab gerenderte Seiten eine Allowlist von Script-Hosts. Gehostete Seiten (`/p`) erhalten eine lockere Policy, weil sie die Pixel des Besitzers ausführen und Medien von überall einbetten. Wenn dein Reverse Proxy ebenfalls `Content-Security-Policy` setzt, erzwingen Browser beide. Lass sie dort also weg. Setze `CSP_REPORT_ONLY=1`, um die Policy nur im Report-Only-Modus zu senden, während du ein neues Setup prüfst. Verstöße werden von `/api/csp-report` protokolliert. Füge `CSP_HTTPS=1` hinzu, wenn du außerhalb von Vercel über HTTPS auslieferst, damit Browser jede `http://`-Ressource hochstufen. Beide Variablen werden dort gelesen, wo die App läuft, und für den Header der vorab gerenderten Seiten auch dort, wo sie gebaut wird. Das Dockerfile gibt sie nicht an den Build weiter. Füge sie also auch als Build-Argumente hinzu, wenn die vorab gerenderten Seiten sie brauchen.

## QRdx aktualisieren [#update-qrdx]

Sichere zuerst die Datenbank (siehe unten). Danach ziehst du die Änderungen und baust neu. Der Service `migrate` gleicht das Schema erneut ab, bevor die App startet.

```bash title="Terminal"
git pull
docker compose up -d --build
```

Führe beim manuellen Setup `git pull`, `bun install` und `bun run db:push` aus, baue dann neu und starte neu.

Wenn eine Schema-Änderung Daten löschen würde, fragt `drizzle-kit push` nach einer Bestätigung, und der Service `migrate` wartet auf eine Antwort, die er nicht bekommen kann. Führe ihn in diesem Fall in einem Terminal aus, um die Änderungen zu prüfen und zu bestätigen:

```bash title="Terminal"
docker compose run --rm migrate
```

## Sichern und wiederherstellen [#back-up-and-restore]

Alles, was QRdx speichert, liegt in Postgres, mit Ausnahme hochgeladener Dateien, die in deinem R2-Bucket liegen. Erstelle vor jedem Update und regelmäßig einen Dump der Datenbank:

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

So stellst du in eine leere Datenbank wieder her:

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Bei Neon nutzt du stattdessen die eigenen Backups und das Branching.

## Was anders ist als bei qrdx.dev [#what-is-different-from-qrdxdev]

- **Docs** werden auf qrdx.dev geöffnet. Deine Instanz leitet jede Docs-URL dorthin um.
- **Zahlungen und Pläne** brauchen Polar. Ohne Polar haben alle Konten die Limits des Plans Kostenlos, und niemand kann upgraden. Die Limits selbst stehen in `apps/app/lib/plans.ts`, das du für deine Instanz ändern kannst.
- **Das Partnerprogramm, Rechnungszahlungs-Anfragen, Rabatte für gemeinnützige Organisationen und das Kontaktformular für Enterprise** sind eigene Vertriebsangebote von QRdx und laufen nur dort, wo QRdx selbst läuft. Eine selbst gehostete Kopie hat keines davon.
- **Scan-Standorte:** Land, Region und Stadt stammen aus den Geo-Headern von Vercel. Hinter Cloudflare wird nur das Land gelesen (`CF-IPCountry`). Anderswo werden Standorte als unbekannt angezeigt, und [Gebietsregeln](/docs/precise-location#route-scans-by-area) greifen nur bei Scans mit freigegebenem Standort.
- **Eigene Domains** werden per DNS-`TXT`-Eintrag verifiziert und von deinem Reverse Proxy geroutet, es sei denn, du läufst auf Vercel und hast die Variablen der Domains API gesetzt. Der Button **Einrichten mit …** braucht deine eigene Domain-Connect-Vorlage: Die von QRdx funktioniert nur für qrdx.dev.
- **Chat-Bots und Integrationen** brauchen jeweils eine App, die du bei dem jeweiligen Dienst registrierst (siehe die Tabelle oben).
- **Admin-Seiten** werden von der App selbst ausgeliefert. qrdx.dev leitet einige davon über einen Proxy an eine separate Konsole weiter.

## Fehlerbehebung [#troubleshooting]

### „Invalid environment variables" beim Start [#invalid-environment-variables-on-startup]

Das Log nennt jede fehlende oder ungültige Variable und sagt dann, wo du sie setzt. Entweder fehlt ein erforderlicher Wert, oder ein optionaler ist auf etwas Ungültiges gesetzt: eine URL, die keine vollständige `http://`- oder `https://`-Adresse ist, oder ein zu kurzes Secret. Ein leerer Wert gilt als nicht gesetzt und ist in Ordnung. Korrigiere die genannten Variablen in `.env` und erstelle den Container mit `docker compose up -d app` neu.

### OAuth-`redirect_uri` stimmt nicht überein [#oauth-redirect_uri-mismatch]

Die Callback-URL in deiner OAuth-App muss genau `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` oder `/api/auth/callback/google` lauten. Setze `BETTER_AUTH_URL` auf dieselbe Basis-URL wie `NEXT_PUBLIC_APP_URL`.

### Die App erreicht die Datenbank nicht (`fetch failed`) [#the-app-cant-reach-the-database-fetch-failed]

Bei einfachem Postgres muss `DATABASE_HTTP_ENDPOINT` auf den laufenden Proxy zeigen. Prüfe, ob `docker compose ps db-proxy` ihn als laufend anzeigt.

### `migrate` wird nie fertig [#migrate-never-finishes]

`drizzle-kit push` wartet auf eine Bestätigung. Führe `docker compose run --rm migrate` in einem Terminal aus und beantworte sie. Siehe [QRdx aktualisieren](#update-qrdx).

### Ein geänderter `NEXT_PUBLIC_*`-Wert hat keine Wirkung [#a-changed-next_public_-value-has-no-effect]

Baue das Image neu: `docker compose up -d --build`.

### Port 4444 ist bereits belegt [#port-4444-is-already-in-use]

Ändere die Port-Zuordnung von `db-proxy` in `docker-compose.yml`. Nur die lokale Entwicklung auf dem Host nutzt ihn.

### „the --mount option requires BuildKit" [#the---mount-option-requires-buildkit]

Dein Docker hat kein BuildKit. Installiere das Plugin `buildx` oder aktualisiere Docker.

### Der Build bricht mit `Killed` oder Exit-Code 137 ab [#the-build-stops-with-killed-or-exit-code-137]

Docker ist der Arbeitsspeicher ausgegangen. Gib ihm mindestens 8 GB (Docker Desktop: **Settings** → **Resources**) und führe `docker compose up -d --build` erneut aus.

### „sign-in code email is off for this deployment" [#sign-in-code-email-is-off-for-this-deployment]

E-Mail-Codes werden nicht gesendet, solange `NEXT_PUBLIC_APP_URL` `localhost` ist. Nutze für einen lokalen Test die Anmeldung mit GitHub oder Google.

Hängst du immer noch fest? [Eröffne ein Issue](https://github.com/qrdxinc/qrdx/issues) mit der Ausgabe von `docker compose logs app`, Secrets entfernt.

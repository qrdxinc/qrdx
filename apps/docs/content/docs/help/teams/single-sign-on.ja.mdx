シングルサインオンを使うと、メールコード、Google、GitHub の代わりに、会社のIDプロバイダー経由で QRdx にサインインできます。1つのメールドメインに対して1つの接続を設定し、そのドメインの所有を証明すると、そのドメインのユーザーが会社のメールアドレスを入力したときにシングルサインオンが案内されます。この方法でサインインすると、ワークスペースのメンバーになります。[必須にする](#require-single-sign-on)こともでき、その場合はそのドメインではIDプロバイダーだけがサインインの手段になります。

<Callout type="info">
  シングルサインオンは **Business** プランに含まれます。ワークスペースのオーナーまたは請求担当メンバーのいずれかが Business プランを利用していれば、そのワークスペースで使えます。[シートとワークスペースの上限](/docs/help/teams/seats)をご覧ください。
</Callout>

シングルサインオンは、QRdx 商用ライセンスに基づく Business の機能です。セルフホストの QRdx サーバーで有効にするには、ライセンスキー(`QRDX_EE_LICENSE`)が必要です。[セルフホスティング](/docs/self-hosting#optional-services)をご覧ください。

## 始める前に [#before-you-start]

- ワークスペースの**オーナー**または**管理者**である必要があります。
- `acme.com` のようなメールドメインに、DNSレコードを追加できる必要があります。
- 接続の設定、変更、検証、削除、およびシングルサインオンを必須にする操作では、先に[本人確認](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)が求められます。パスキーまたは2段階認証コードを使います。2段階認証がオフの場合は、メールで届くコードを使うか、OIDC接続であれば、その接続でもう一度サインインして確認します。一度確認すれば、その後10分間の変更が対象になります。

QRdx は、IDプロバイダーが求める標準的な OIDC と SAML 2.0 の設定を使います。各値を貼り付ける場所は、お使いのプロバイダーによって異なります。

## IDプロバイダーとやり取りする内容 [#what-you-exchange-with-your-identity-provider]

| | プロバイダーに渡すもの | プロバイダーから受け取るもの |
| --- | --- | --- |
| **OIDC** | シングルサインオンのページに表示される**リダイレクトURI** | **発行者URL**、**クライアントID**、**クライアントシークレット** |
| **SAML 2.0** | **Assertion Consumer Service(ACS)URL**、**エンティティID(オーディエンス)**、プロバイダーがURLから設定を読み込む場合は**メタデータURL** | **メタデータXML**、または**サインインURL(SSO URL)**、プロバイダーの**エンティティID**、**署名証明書** |

## OIDC での設定 [#set-up-with-oidc]

1. ワークスペースで **設定** → **シングルサインオン** に移動します。**OIDC** が選択されています。
2. IDプロバイダーで QRdx 用のWebアプリ(OIDCクライアント)を作成し、ページに表示されている**リダイレクトURI**を許可するリダイレクト先として追加します。
3. QRdx に戻り、**メールドメイン**(`acme.com` のような会社のドメイン)、**発行者URL**、作成したアプリの**クライアントID**と**クライアントシークレット**を入力します。残りの情報は `<issuer>/.well-known/openid-configuration` から読み込まれるため、発行者はそのドキュメントと完全に一致している必要があります。
4. **接続を保存** をクリックします。

<Shot id="single-sign-on" />

QRdx は `openid`、`email`、`profile` のスコープを要求し、PKCE を使用します。発行者にはインターネットからHTTPSでアクセスできる必要があります。プライベートネットワーク上のIDプロバイダーには対応していません。

## SAML 2.0 での設定 [#set-up-with-saml-20]

1. ワークスペースで **設定** → **シングルサインオン** に移動し、**SAML 2.0** を選択します。
2. IDプロバイダーで QRdx 用のSAMLアプリを作成し、ページに表示されている**Assertion Consumer Service(ACS)URL**と**エンティティID(オーディエンス)**を設定します。プロバイダーが QRdx の設定をURLから読み込める場合は、**メタデータURL**も設定します。
3. 下の表の説明に従って、アサーションでユーザーのメールアドレスと名前を送信します。
4. QRdx に戻り、**メールドメイン**を入力して、プロバイダーの**メタデータXML**を貼り付けます。または **詳細を入力する** をクリックして、**サインインURL(SSO URL)**、プロバイダーの**エンティティID**、**署名証明書**を入力します。
5. **接続を保存** をクリックします。

| 項目 | 送信方法 |
| --- | --- |
| メールアドレス | **NameID**(メール形式)として、または `email` という名前の属性として送信します。 |
| 名前 | `givenName` と `surname`、`firstName` と `lastName`、またはX.500名の `urn:oid:2.5.4.42` と `urn:oid:2.5.4.4`。あるいは表示名を `displayName`、`name`、`urn:oid:2.16.840.1.113730.3.1.241` のいずれかで送信します。名前がない場合、QRdx はメールアドレスの@より前の部分を使います。 |

プロバイダーはレスポンスに署名し、HTTP-Redirect のサインインURLを含める必要があります。QRdx は、有効な署名がないレスポンスや、有効期間(`NotBefore` と `NotOnOrAfter`)がないレスポンスを拒否します。

署名には SHA-256 以上の強度が必要です。QRdx は SHA-1 で署名またはダイジェストされたレスポンスを拒否します。QRdx アプリ用にプロバイダーが SHA-1 に設定されている場合は、SHA-256 に切り替えてください。

QRdx はサインインリクエストに署名しません。QRdx アプリに対して署名付きリクエストを必須にする設定がプロバイダー側でオンになっている場合は、オフにしてください。オンのままだと、ユーザーはサインインする前に拒否されます。

## ドメインを検証する [#verify-your-domain]

ドメインの所有を証明するまでは、誰もこの接続でサインインできません。

1. シングルサインオンのページの **検証** で、TXTレコードの**名前**と**値**をコピーします。
2. DNSプロバイダーでTXTレコードを追加します。
3. **検証** をクリックします。新しいレコードが反映されるまで数分、場合によってはそれ以上かかることがあります。QRdx がまだレコードを見つけられない場合はその旨が表示されますので、しばらく待ってからもう一度お試しください。

検証用の値の有効期間は7日間です。期限が切れた場合は、ページを再読み込みして新しい値を取得し、レコードを更新してください。

検証済みのドメインにはサブドメインも含まれます。たとえば `acme.com` は `eu.acme.com` もカバーします。1つのドメインをシングルサインオン用に検証できるのは、1つのワークスペースだけです。別のワークスペースがすでに検証している場合や、重複するドメインが検証されている場合は、保存または検証のときに QRdx がお知らせします。

## チームに表示される内容 [#what-your-team-sees]

1. サインインページで会社のメールアドレスを入力し、通常のメールサインインと同じように **コードをメールで受け取る** をクリックします。
2. コードを送信する前に、QRdx はアドレスのドメインを確認します。検証済みのドメインであれば、会社ではシングルサインオンでサインインする旨が表示され、**SSOで続行** が案内されます。ユーザーが求めない限り、コードは送信されません。
3. **SSOで続行** を選ぶとIDプロバイダーに移動し、その後 QRdx に戻って、サインインした状態でワークスペースに入ります。

[シングルサインオンを必須](#require-single-sign-on)にしていない限り、代わりに **コードをメールで受け取る** を選ぶこともできます。メール欄の下にある **SSOでサインイン** も引き続き使えます。会社のメールアドレスを尋ねたうえで、そのままIDプロバイダーに移動します。

QRdx がシングルサインオンを案内するのは、ドメインが検証済みで、ワークスペースが Business プランである間だけです。この確認はドメインのみで行われるため、その人が QRdx アカウントを持っているかどうかが表示されることはありません。

ユーザーが[2段階認証](/docs/help/privacy-and-security/two-step-verification)をオンにしている場合、IDプロバイダーでのサインイン後にも、QRdx は2つ目のステップを求めます。ただし、そのデバイスでは再度求めないように選択している場合を除きます。これは、シングルサインオンが必須の場合も同じです。

SSOでサインインするたびに、その人がワークスペースにいることが確認されます。

- メンバーではない人は、**新しいメンバー** で選んだロール(**メンバー**(デフォルト)または**閲覧者**)で参加します。
- ワークスペースへの招待が保留中の人は、招待のロールで参加し、招待は承諾済みになります。
- すでにメンバーの人は、現在のロールのままです。ロールは **チーム** ページでいつでも変更できます。

これには、ワークスペースから削除した人も含まれます。その人は、次にSSOでサインインしたときに再び参加します。

同じメールアドレスの QRdx アカウントをすでに持っている場合、SSOでのサインインではそのアカウントが使われます。ご自身のワークスペースと、その中のすべての内容はそのまま残ります。

QRdx は、プロバイダーから送られてきたアドレスが検証済みドメインのものである場合にだけ、この接続でサインインさせます。同じアドレス宛のメールコードなど、ほかのサインイン方法は、シングルサインオンを必須にしない限り引き続き使えます。

メールアドレスは、IDプロバイダーで検証済みである必要があります。アドレスが未検証であるとプロバイダーが QRdx に伝えた場合(OIDCの `email_verified` クレーム、またはSAMLの `email_verified` あるいは `emailVerified` 属性が false)、QRdx はその人をサインインさせず、アカウントも作成せず、既存のアカウントとも連携しません。管理者にそちらでアドレスを検証してもらうよう求めるメッセージが表示されます。プロバイダーがどちらとも伝えない場合、QRdx は検証済みドメインについてはプロバイダーを信頼します。

QRdx からサインアウトしても、IDプロバイダーからはサインアウトされません。IDプロバイダーにまだサインインしている間は、次回のSSOサインインでパスワードを求められることなくそのまま通ります。共有のコンピューターでは、IDプロバイダーからもサインアウトしてください。

## ID プロバイダーから QRdx を開く [#open-qrdx-from-your-identity-provider]

SAML 接続では、ID プロバイダー側から開始することもできます。ID プロバイダーのアプリダッシュボードで QRdx アプリをクリックすると、QRdx のサインインページを経由せずに QRdx にサインインできます。これは一般に IdP 起点のサインインと呼ばれます。

ID プロバイダーで、QRdx 用に作成した SAML アプリを開き、アプリダッシュボードでユーザーに表示されること、そして ID プロバイダーから開始するサインインが許可されていることを確認してください。ユーザーは、ワークスペースのダッシュボードに移動します。QRdx は、アプリから送信される **RelayState** を無視します。そのため、QRdx が要求していないサインインによって、開くページが決まることはありません。

QRdx 側からサインインを開始する場合と同じルールが適用されます。ドメインが確認済みであること、ワークスペースが Business であること、レスポンスが SHA-256 以上の強度で署名されていることが必要です。QRdx では、さらに次の条件も必要です。

- ID が付与された、暗号化されていないアサーションが 1 つだけであること。
- アサーションに有効期限があること（`Conditions` 内の `NotOnOrAfter`）。ほとんどの ID プロバイダーは、デフォルトで送信します。

1 つのレスポンスでサインインできるのは 1 回だけです。同じレスポンスが再度届いた場合、QRdx は拒否し、もう一度サインインするよう案内します。2 段階認証を有効にしているユーザーには、QRdx がまず 2 段階目の認証を求め、その後ダッシュボードに移動します。

アプリダッシュボードからのサインインは、2 段階目の認証に答えた場合を除き、[本人確認](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)としては扱われません。QRdx が 2 段階目の認証を求めていないためです。確認を求める変更を行う前に、通常どおり本人確認を行ってください。

OIDC 接続は、常に QRdx から開始します。QRdx を ID プロバイダーのアプリダッシュボードに表示するには、QRdx のサインインページへのリンクとして追加してください。

## シングルサインオンを必須にする [#require-single-sign-on]

ドメインが確認済みになると、そのドメインのユーザーが ID プロバイダー経由でしかサインインできないように設定できます。**シングルサインオン**ページで、ドメインの **Require single sign-on for** をオンにします。接続と同様に、サブドメインも対象です。

オンの間、そのドメインのアドレスには次のようになります。

- メールコード、Google、GitHub ではサインインできません<IfAvailable feature="passkeys">。**Continue with passkey** でもできません</IfAvailable>。会社がシングルサインオンを必須にしている旨と、**Continue with SSO** が表示されます。
- ID プロバイダーでのサインイン後も、[2 段階認証](/docs/help/privacy-and-security/two-step-verification)は引き続き適用されます。<IfAvailable feature="passkeys">パスキーも、2 段階目の認証として使用できます。</IfAvailable>
- サインインの有効期間は最長 24 時間です。その後は、再度 ID プロバイダーを経由する必要があります。そのため、ID プロバイダーで割り当てを解除したユーザーは QRdx に再びサインインできず、1 日以内にサインアウトされます。
- QRdx のメールアドレスを、ドメイン外のアドレスに変更することはできません。また、他のユーザーがそのドメインのアドレスに変更することもできません。そのドメインのアドレスが QRdx に入る方法は、シングルサインオンでのサインインだけです。

オンにすると、ドメインのすべてのユーザーが、シングルサインオンで開始されていないセッションからサインアウトされます。シングルサインオンで開始されたセッションは、そのサインインから 24 時間後に終了します。これについてメールは送信されません。次回、SSO でサインインするよう案内されます。

**オーナーは他のサインイン方法を維持できます。** この設定は、ワークスペースのオーナーには適用されません。オーナーは引き続き、メールコード、Google、GitHub<IfAvailable feature="passkeys">、パスキー</IfAvailable>を使用でき、セッションが短縮されることもなく、メールアドレスも変更できます。そのため、ID プロバイダーに問題が起きても、全員がこの設定から締め出されることはありません。オーナーのロールは、必要な少数のユーザーに限定してください。

オンにするには、次の条件があります。

- Business プランの**オーナー**または**管理者**であり、確認済みのドメインがあること。また、[本人確認](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)を求められます。
- そのドメインのアドレスを持つ管理者の場合は、先にシングルサインオンでサインインしてください。そうしないと、オンにした時点でサインアウトされます。この方法でサインインすれば、接続が機能していることも確認できます。

オフにする、接続を削除する、またはワークスペースが Business でなくなると、必須ではなくなります。ユーザーは現在のセッションを維持でき、他のサインイン方法も再び使用できます。すべての QRdx サーバーに反映されるまで最大 1 分かかることがあります。その間に別の方法でサインインしたユーザーは、そのままサインアウトされる場合があり、1 分後に再びサインインできます。

シングルサインオンはサインインに関する機能です。API キーはサインインではないため、必須にしても API キーは停止しません。**チーム**ページでユーザーを削除すると、そのユーザーがワークスペース用に作成した API キーは停止します。

## ユーザーを完全に削除する [#remove-someone-for-good]

SSO でサインインするたびにユーザーが再び追加されるため、**チーム**ページで削除するだけでは不十分です。

1. ID プロバイダーで、QRdx アプリへの割り当てを解除します（または ID プロバイダー上のアカウントをオフにします）。これで、QRdx にサインインできなくなります。
2. 次に、**チーム**ページで削除します。ユーザーのアドレスが確認済みドメインのものである場合は、削除ダイアログでお知らせします。

[シングルサインオンを必須にしている](#require-single-sign-on)場合、手順 1 により、24 時間以内に QRdx からもサインアウトされます。**チーム**ページでも削除して、メンバーではなくなり、ワークスペース用の API キーも使えなくなるようにしてください。

ワークスペースからユーザーを削除しても、そのユーザーの QRdx アカウントは削除されません。そのアドレスにシングルサインオンが必須でない限り、ユーザーはメールコード、Google、GitHub で自分のワークスペースにサインインできます。

## 接続の変更または削除 [#change-or-remove-the-connection]

- **Replace secret**（OIDC）または **Replace certificate**（SAML）は、ID プロバイダーでシークレットや証明書をローテーションしたときに、接続を更新します。メタデータ XML から設定した SAML 接続を変更するには、削除してから設定し直します。
- **Remove** はシングルサインオンをオフにし、必須設定も解除します。全員がワークスペースに残り、メールコード、Google、GitHub でサインインできます。

## プランが変更された場合 [#if-the-plan-changes]

ワークスペースが Business でなくなると、サインインの途中も含め、SSO でサインインできなくなり、シングルサインオンの必須設定も解除されます。ユーザーにはメッセージが表示され、別の方法でサインインできます。接続とその設定は保持されるため、ワークスペースが Business に戻ると再び機能し、削除することもできます。

## サポートされていない機能 [#what-isnt-supported]

- 自動プロビジョニングと自動削除（SCIM）。ID プロバイダーからユーザーを削除しても、ワークスペースからは削除されません。[シングルサインオンの必須設定](#require-single-sign-on)がない場合、QRdx のセッションも終了しません。**チーム**ページでも削除してください（[ユーザーを完全に削除する](#remove-someone-for-good)を参照）。
- ID プロバイダーのロールやグループ。全員が **New members** で設定されたロールで参加します。
- ワークスペースごとに複数の接続、または複数のドメインを設定すること。
- OIDC 接続での ID プロバイダー起点のサインイン（SAML では利用できます。[ID プロバイダーから QRdx を開く](#open-qrdx-from-your-identity-provider)を参照）、SAML のシングルログアウト、暗号化されたアサーション。
- インターネットから到達できない ID プロバイダー。

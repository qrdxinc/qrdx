Alla fine di questa guida avrai QRdx in esecuzione al tuo URL: l'editor di QR code, gli account, i QR code dinamici con analisi delle scansioni, le pagine ospitate, gli spazi di lavoro e i temi salvati, su un database Postgres che controlli tu. Il percorso con Docker Compose richiede circa mezz'ora, per la maggior parte dovuta alla prima build dell'immagine.

L'app web è open source con licenza AGPL-3.0. Due parti non lo sono: il single sign-on per gli spazi di lavoro e l'audit log si trovano nelle cartelle `ee/` sotto la licenza commerciale di QRdx e restano disattivati finché non imposti una chiave di licenza (`QRDX_EE_LICENSE`). Per usarli in produzione serve un accordo scritto con QRdx; consulta [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md). Non ti serve nulla di tutto questo per usare la [libreria React `qrdx`](/docs/getting-started) o la [CLI](/docs/developers/cli): funzionano ovunque senza backend, con licenza MIT. [Open source in QRdx](/open-source-qr-code-generator) elenca ogni parte del repository e la sua licenza.

## Prima di iniziare [#before-you-start]

- Docker con Compose v2 e BuildKit (Docker Desktop e le versioni attuali di Docker Engine includono entrambi), oppure Node.js 22 (22.22.3 o successivo) e [Bun](https://bun.com/docs/installation) 1.4 per la configurazione manuale.
- Almeno 8 GB di memoria per Docker durante la build dell'immagine.
- Un modo per accedere, così da poter creare gli account: un'app OAuth di GitHub o Google, oppure [Resend](https://resend.com) per i codici di accesso via email. I codici di accesso vengono inviati via email solo quando `NEXT_PUBLIC_APP_URL` non è `localhost`. `bun run dev` li stampa invece nel terminale, ma l'immagine Docker no, quindi un test locale con Docker richiede l'accesso con GitHub o Google.
- Postgres: il container incluso in `docker-compose.yml`, oppure un database [Neon](https://neon.tech).
- Per qualsiasi uso oltre a un test locale, un dominio e un reverse proxy che gestisca HTTPS.

La documentazione non fa parte di un'istanza self-hosted. La tua istanza reindirizza ogni link alla documentazione (`/docs` e le pagine sotto di esso, le loro copie in Markdown e `/llms-full.txt`) alle stesse pagine su qrdx.dev.

### Come funziona la connessione al database [#how-the-database-connection-works]

L'app comunica con Postgres tramite il driver HTTP serverless di Neon.

- **Neon:** funziona direttamente. Imposta `DATABASE_URL` sulla tua stringa di connessione Neon.
- **Postgres semplice:** richiede davanti un proxy HTTP compatibile con Neon. `docker-compose.yml` ne avvia uno ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) e imposta `DATABASE_HTTP_ENDPOINT` in modo che l'app vi invii le sue query.

Lo schema proviene da `packages/database/schema.ts` e viene applicato con `drizzle-kit push`. Non ci sono file di migrazione da eseguire a mano.

## Avvio rapido con Docker Compose [#quick-start-with-docker-compose]

### 1. Clona il repository [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. Configura l'ambiente [#2-configure-the-environment]

Copia il file di esempio nella radice del repository, dove Compose lo legge, e genera il segreto di sessione:

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

Apri `.env` e imposta questi valori. Tutte le altre righe possono restare commentate.

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

Dove trovare ogni valore:

| Variabile | Dove trovarla |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | L'URL pubblico della tua istanza, senza barra finale. Mantieni `http://localhost:3000` per un test locale. |
| `BETTER_AUTH_URL` | Lo stesso valore. Rimuovi il commento dalla riga. |
| `BETTER_AUTH_SECRET` | L'output di `openssl rand -base64 32`. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | Un'[app OAuth di GitHub](https://github.com/settings/developers) con URL di callback `<your url>/api/auth/callback/github`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | In alternativa a GitHub: un [client OAuth di Google](https://console.cloud.google.com/apis/credentials) con URI di reindirizzamento `<your url>/api/auth/callback/google`. |

Lascia `DATABASE_URL` com'è: Compose punta l'app al proprio container Postgres e ignora il valore in `.env`. Per cambiare la password del database, imposta `POSTGRES_PASSWORD` prima del primo avvio.

### 3. Avvia lo stack [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

Questo comando compila l'immagine, avvia Postgres e il proxy, esegue il servizio one-shot `migrate` (`drizzle-kit push`) e poi avvia l'app sulla porta 3000. La prima build richiede diversi minuti. Quando ha finito, i quattro servizi appaiono così:

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

`migrate` è pensato per terminare: sincronizza lo schema e si ferma. Per seguire la sincronizzazione dello schema e l'avvio dell'app:

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. Accedi [#4-sign-in]

Apri `NEXT_PUBLIC_APP_URL` in un browser e accedi con GitHub, Google o un codice via email. Il tuo account viene creato al primo accesso.

### 5. Diventa amministratore [#5-make-yourself-an-admin]

Aggiungi a `.env` l'indirizzo email dell'account che hai creato al passaggio 4:

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

Ricrea il container dell'app in modo che legga la modifica, poi accedi e apri `/admin`:

```bash title="Terminal"
docker compose up -d app
```

L'indirizzo diventa amministratore la prima volta che apre `/admin`. `ADMIN_USER_IDS` funziona allo stesso modo con gli id utente.

## Usa Neon o un altro Postgres gestito [#use-neon-or-another-managed-postgres]

Puoi saltare il Postgres incluso ed eseguire solo l'immagine dell'app. Imposta `DATABASE_URL` in `.env` sulla tua stringa di connessione Neon e lascia `DATABASE_HTTP_ENDPOINT` non impostato.

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Applica lo schema una volta, e di nuovo dopo ogni aggiornamento, con l'immagine del migrator:

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Configurazione manuale con Node.js [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

Per la produzione, compila e avvia l'app:

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` si connette con il driver di Neon, quindi richiede un database Neon. Per usare invece il Postgres di Docker per lo sviluppo locale, avvialo con `docker compose up -d db db-proxy`, applica lo schema con `docker compose run --rm migrate` e imposta questi valori in `apps/app/.env.local`:

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

La configurazione manuale li legge tutti da `apps/app/.env.local`.
</Callout>

### Job pianificati [#scheduled-jobs]

Due route svolgono il lavoro ricorrente: `/api/cron/webhooks` ritenta le consegne dei webhook fallite ed elimina le vecchie righe del registro di controllo, e `/api/cron/digest` invia il riepilogo settimanale. Su Vercel, `apps/app/vercel.json` li pianifica. Altrove, nessuno li chiama finché non lo fai tu. Imposta `CRON_SECRET` e chiama entrambe le route dal tuo scheduler usandolo:

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

Senza l'header, in produzione le route rispondono `401`. [Notifiche](/docs/notifications#self-hosting) spiega il parametro `shard` del riepilogo.

## Reverse proxy e HTTPS [#reverse-proxy-and-https]

Metti l'app dietro un reverse proxy come Caddy, nginx o Traefik che termini il TLS, e non esporre direttamente la porta 3000 a internet. Il rate limiting, le email di sicurezza e il [registro di audit](/docs/help/teams/audit-log) leggono l'IP del client prima da `X-Real-IP` e poi dal primo indirizzo di `X-Forwarded-For` (su Vercel, `X-Vercel-Forwarded-For` si inserisce in mezzo), quindi il proxy deve impostare questi header e l'app deve essere raggiungibile solo tramite il proxy. Fai in modo che il proxy imposti `X-Real-IP` sull'indirizzo da cui ha ricevuto la connessione. Un proxy che si limita ad aggiungere valori a `X-Forwarded-For` permette a un client di inserire un indirizzo qualsiasi come primo.

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

Caddy imposta questi header per impostazione predefinita. Quando HTTPS funziona, cambia `NEXT_PUBLIC_APP_URL` e `BETTER_AUTH_URL` con l'URL `https://`, aggiorna gli URL di callback OAuth ed esegui di nuovo la build.

### Content-Security-Policy [#content-security-policy]

Le build di produzione inviano una Content-Security-Policy sulle pagine di QRdx: le pagine con accesso effettuato ricevono a ogni richiesta un nuovo nonce per gli script, mentre le pagine prerenderizzate ricevono una allowlist di host per gli script. Le pagine ospitate (`/p`) ricevono una policy permissiva, perché eseguono i pixel del proprietario e incorporano contenuti multimediali da qualsiasi origine. Se anche il tuo reverse proxy imposta `Content-Security-Policy`, i browser applicano entrambe, quindi omettila lì. Imposta `CSP_REPORT_ONLY=1` per inviare la policy in modalità solo report mentre verifichi una nuova configurazione; le violazioni vengono registrate da `/api/csp-report`. Aggiungi `CSP_HTTPS=1` quando servi in HTTPS fuori da Vercel, così i browser aggiornano ogni risorsa `http://`. Entrambe vengono lette dove l'app è in esecuzione e, per l'header delle pagine prerenderizzate, dove viene compilata; il Dockerfile non le passa alla build, quindi aggiungile anche come argomenti di build se le pagine prerenderizzate ne hanno bisogno.

## Aggiornare QRdx [#update-qrdx]

Prima fai il backup del database (vedi sotto). Poi esegui pull e build. Il servizio `migrate` sincronizza di nuovo lo schema prima dell'avvio dell'app.

```bash title="Terminal"
git pull
docker compose up -d --build
```

Per l'installazione manuale, esegui `git pull`, `bun install` e `bun run db:push`, poi ricompila e riavvia.

Se una modifica allo schema eliminerebbe dei dati, `drizzle-kit push` chiede conferma e il servizio `migrate` resta in attesa di una risposta che non può ricevere. In tal caso, eseguilo in un terminale per rivedere e confermare le modifiche:

```bash title="Terminal"
docker compose run --rm migrate
```

## Backup e ripristino [#back-up-and-restore]

Tutto ciò che QRdx archivia è in Postgres, tranne i file caricati, che sono nel tuo bucket R2. Esegui il dump del database prima di ogni aggiornamento e a intervalli regolari:

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Per ripristinare in un database vuoto:

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Con Neon, usa invece i suoi backup e il branching.

## Cosa cambia rispetto a qrdx.dev [#what-is-different-from-qrdxdev]

- **La documentazione** si apre su qrdx.dev. La tua istanza reindirizza lì ogni URL della documentazione.
- **Pagamenti e piani** richiedono Polar. Senza, ogni account ha i limiti del piano Gratuito e nessuno può passare a un piano superiore. I limiti si trovano in `apps/app/lib/plans.ts`, che puoi modificare per la tua istanza.
- **Il programma di affiliazione, le richieste di pagamento tramite fattura, gli sconti per organizzazioni non profit e il modulo di contatto enterprise** sono vendite proprie di QRdx e funzionano solo dove gira QRdx stesso. Una copia self-hosted non ne ha nessuno.
- **Posizioni delle scansioni:** paese, regione e città provengono dagli header geo di Vercel. Dietro Cloudflare viene letto solo il paese (`CF-IPCountry`); altrove le posizioni risultano sconosciute e le [regole per area](/docs/precise-location#route-scans-by-area) corrispondono solo alle scansioni che condividono la posizione.
- **I domini personalizzati** vengono verificati con un record DNS `TXT` e instradati dal tuo reverse proxy, a meno che tu non usi Vercel con le variabili della Domains API impostate. Il pulsante **Set up with …** richiede un tuo template Domain Connect: quello di QRdx funziona solo per qrdx.dev.
- **I chatbot e le integrazioni** richiedono ciascuno un'app che registri presso il relativo servizio (vedi la tabella sopra).
- **Le pagine di amministrazione** sono servite dall'app stessa; qrdx.dev ne inoltra alcune a una console separata.

## Risoluzione dei problemi [#troubleshooting]

### "Invalid environment variables" all'avvio [#invalid-environment-variables-on-startup]

Il log indica ogni variabile mancante o non valida, poi dice dove impostarla. Manca un valore obbligatorio, oppure uno facoltativo è impostato su un valore non valido: un URL che non è un indirizzo completo `http://` o `https://`, o un segreto troppo corto. Un valore vuoto conta come non impostato e va bene. Correggi le variabili indicate in `.env` e ricrea il container con `docker compose up -d app`.

### Mancata corrispondenza di `redirect_uri` in OAuth [#oauth-redirect_uri-mismatch]

L'URL di callback nella tua app OAuth deve essere esattamente `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` oppure `/api/auth/callback/google`. Imposta `BETTER_AUTH_URL` sullo stesso URL di base di `NEXT_PUBLIC_APP_URL`.

### L'app non riesce a raggiungere il database (`fetch failed`) [#the-app-cant-reach-the-database-fetch-failed]

Con Postgres semplice, `DATABASE_HTTP_ENDPOINT` deve puntare al proxy in esecuzione. Controlla che `docker compose ps db-proxy` lo mostri in esecuzione.

### `migrate` non termina mai [#migrate-never-finishes]

`drizzle-kit push` è in attesa di una conferma. Esegui `docker compose run --rm migrate` in un terminale e rispondi; vedi [Aggiornare QRdx](#update-qrdx).

### Un valore `NEXT_PUBLIC_*` modificato non ha effetto [#a-changed-next_public_-value-has-no-effect]

Ricompila l'immagine: `docker compose up -d --build`.

### La porta 4444 è già in uso [#port-4444-is-already-in-use]

Cambia la mappatura della porta di `db-proxy` in `docker-compose.yml`. La usa solo lo sviluppo locale sull'host.

### "the --mount option requires BuildKit" [#the---mount-option-requires-buildkit]

Il tuo Docker non ha BuildKit. Installa il plugin `buildx` oppure aggiorna Docker.

### La build si interrompe con `Killed` o codice di uscita 137 [#the-build-stops-with-killed-or-exit-code-137]

Docker ha esaurito la memoria. Assegnagli almeno 8 GB (Docker Desktop: **Settings** → **Resources**) ed esegui di nuovo `docker compose up -d --build`.

### "sign-in code email is off for this deployment" [#sign-in-code-email-is-off-for-this-deployment]

I codici via email non vengono inviati mentre `NEXT_PUBLIC_APP_URL` è `localhost`. Per un test in locale usa l'accesso con GitHub o Google.

Sei ancora bloccato? [Apri una issue](https://github.com/qrdxinc/qrdx/issues) con l'output di `docker compose logs app`, dopo aver rimosso i segreti.

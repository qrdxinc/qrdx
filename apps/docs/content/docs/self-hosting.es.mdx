Al terminar esta guía tendrás QRdx funcionando en tu propia URL: el editor de QR, cuentas, códigos QR dinámicos con analíticas de escaneo, páginas alojadas, espacios de trabajo y temas guardados, sobre una base de datos Postgres que controlas tú. El camino con Docker Compose lleva aproximadamente media hora, la mayor parte en la primera compilación de la imagen.

La aplicación web es de código abierto bajo la licencia AGPL-3.0. Dos partes no lo son: el inicio de sesión único (SSO) del espacio de trabajo y el registro de auditoría están en las carpetas `ee/` bajo la licencia comercial de QRdx y permanecen desactivados salvo que configures una clave de licencia (`QRDX_EE_LICENSE`). Usarlos en producción requiere un acuerdo por escrito con QRdx; consulta [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md). No necesitas nada de esto para usar la [biblioteca de React `qrdx`](/docs/getting-started) ni la [CLI](/docs/developers/cli): funcionan en cualquier lugar sin backend, bajo la licencia MIT. [Código abierto en QRdx](/open-source-qr-code-generator) enumera cada parte del repositorio y su licencia.

<Callout type="warn" title="La configuración de Docker es nueva">
  Si un paso no funciona como está escrito, [abre una incidencia](https://github.com/qrdxinc/qrdx/issues) con el comando que ejecutaste y su salida.
</Callout>

## Antes de empezar [#before-you-start]

- Docker con Compose v2 y BuildKit (Docker Desktop y las versiones actuales de Docker Engine incluyen ambos), o Node.js 22 (22.22.3 o posterior) y [Bun](https://bun.com/docs/installation) 1.4 para la configuración manual.
- Al menos 8 GB de memoria para Docker mientras se compila la imagen.
- Una forma de iniciar sesión para poder crear cuentas: una aplicación OAuth de GitHub o Google, o [Resend](https://resend.com) para códigos de inicio de sesión por correo. Los códigos se envían por correo solo cuando `NEXT_PUBLIC_APP_URL` no es `localhost`. `bun run dev` los imprime en la terminal, pero la imagen de Docker no, así que una prueba local con Docker necesita inicio de sesión con GitHub o Google.
- Postgres: el contenedor incluido en `docker-compose.yml` o una base de datos de [Neon](https://neon.tech).
- Para cualquier uso más allá de una prueba local, un dominio y un proxy inverso que termine HTTPS.

La documentación no forma parte de una instancia autoalojada. Tu instancia redirige todos los enlaces de la documentación (`/docs` y las páginas que dependen de él, sus copias en Markdown y `/llms-full.txt`) a las mismas páginas en qrdx.dev.

### Cómo funciona la conexión a la base de datos [#how-the-database-connection-works]

La aplicación se comunica con Postgres mediante el controlador HTTP serverless de Neon.

- **Neon:** funciona directamente. Configura `DATABASE_URL` con tu cadena de conexión de Neon.
- **Postgres normal:** necesita delante un proxy HTTP compatible con Neon. `docker-compose.yml` ejecuta uno ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) y define `DATABASE_HTTP_ENDPOINT` para que la aplicación envíe allí sus consultas.

El esquema proviene de `packages/database/schema.ts` y se aplica con `drizzle-kit push`. No hay archivos de migración que ejecutar a mano.

## Inicio rápido con Docker Compose [#quick-start-with-docker-compose]

### 1. Clona el repositorio [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. Configura el entorno [#2-configure-the-environment]

Copia el archivo de ejemplo a la raíz del repositorio, donde Compose lo lee, y genera el secreto de sesión:

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

Abre `.env` y define estos valores. Todas las demás líneas pueden seguir comentadas.

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

De dónde sale cada valor:

| Variable | Dónde obtenerla |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | La URL pública de tu instancia, sin barra final. Mantén `http://localhost:3000` para una prueba local. |
| `BETTER_AUTH_URL` | El mismo valor. Descomenta la línea. |
| `BETTER_AUTH_SECRET` | La salida de `openssl rand -base64 32`. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | Una [aplicación OAuth de GitHub](https://github.com/settings/developers) cuya URL de retorno sea `<your url>/api/auth/callback/github`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | En lugar de GitHub: un [cliente OAuth de Google](https://console.cloud.google.com/apis/credentials) cuyo URI de redirección sea `<your url>/api/auth/callback/google`. |

Deja `DATABASE_URL` como está: Compose dirige la aplicación a su propio contenedor de Postgres e ignora el valor de `.env`. Para cambiar la contraseña de la base de datos, define `POSTGRES_PASSWORD` antes del primer arranque.

### 3. Inicia el stack [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

Esto compila la imagen, inicia Postgres y el proxy, ejecuta el servicio puntual `migrate` (`drizzle-kit push`) y luego inicia la aplicación en el puerto 3000. La primera compilación tarda varios minutos. Cuando termina, los cuatro servicios se ven así:

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

`migrate` está pensado para terminar: sincroniza el esquema y se detiene. Para ver la sincronización del esquema y el arranque de la aplicación:

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. Inicia sesión [#4-sign-in]

Abre `NEXT_PUBLIC_APP_URL` en un navegador e inicia sesión con GitHub, Google o un código por correo. Tu cuenta se crea en el primer inicio de sesión.

### 5. Conviértete en administrador [#5-make-yourself-an-admin]

Añade a `.env` la dirección de correo de la cuenta que creaste en el paso 4:

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

Vuelve a crear el contenedor de la aplicación para que lea el cambio, luego inicia sesión y abre `/admin`:

```bash title="Terminal"
docker compose up -d app
```

La dirección se convierte en administradora la primera vez que abre `/admin`. `ADMIN_USER_IDS` funciona igual, pero con ids de usuario.

## Usa Neon u otro Postgres administrado [#use-neon-or-another-managed-postgres]

Puedes omitir el Postgres incluido y ejecutar solo la imagen de la aplicación. Define `DATABASE_URL` en `.env` con tu cadena de conexión de Neon y deja `DATABASE_HTTP_ENDPOINT` sin definir.

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Aplica el esquema una vez, y de nuevo tras cada actualización, con la imagen del migrador:

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Configuración manual con Node.js [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

Para producción, compila e inicia la aplicación:

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` se conecta con el controlador de Neon, por lo que necesita una base de datos de Neon. Para usar en cambio el Postgres de Docker en desarrollo local, inícialo con `docker compose up -d db db-proxy`, aplica el esquema con `docker compose run --rm migrate` y define estos valores en `apps/app/.env.local`:

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

  Los valores `NEXT_PUBLIC_*` se incrustan en el paquete del navegador cuando se compila la app, así que cambiar uno implica volver a compilar. La compilación de Docker lee `.env` solo para seis de ellos, pasados como argumentos de compilación en `docker-compose.yml`: `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`, `NEXT_PUBLIC_FEATUREBASE_APP_ID` y los dos ids de producto de Pro. Para definir otro en la imagen de Docker (los ids de producto de Business, `NEXT_PUBLIC_QRDX_EUR_PRICES`, `NEXT_PUBLIC_SHORT_LINK_BASE_URL`, la clave del sitio de Turnstile o los ids de Umami), añádelo a `build.args` del servicio `app` en `docker-compose.yml` y como `ARG` en la etapa de compilación del Dockerfile, y luego ejecuta `docker compose up -d --build`. La instalación manual los lee todos de `apps/app/.env.local`.
</Callout>

### Tareas programadas [#scheduled-jobs]

Dos rutas realizan el trabajo recurrente: `/api/cron/webhooks` reintenta las entregas de webhooks fallidas y elimina las filas antiguas del registro de auditoría, y `/api/cron/digest` envía el resumen semanal. En Vercel, `apps/app/vercel.json` las programa. En cualquier otro sitio, nada las llama hasta que lo hagas tú. Define `CRON_SECRET` y llama a ambas desde tu programador con él:

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

Sin la cabecera, las rutas responden `401` en producción. [Notificaciones](/docs/notifications#self-hosting) explica el parámetro `shard` del resumen.

## Proxy inverso y HTTPS [#reverse-proxy-and-https]

Coloca la aplicación detrás de un proxy inverso como Caddy, nginx o Traefik que termine TLS, y no expongas el puerto 3000 directamente a internet. La limitación de frecuencia, los correos de seguridad y el [registro de auditoría](/docs/help/teams/audit-log) leen la IP del cliente primero de `X-Real-IP` y después de la primera dirección de `X-Forwarded-For` (en Vercel, `X-Vercel-Forwarded-For` se sitúa entre ambas), así que el proxy debe establecer estas cabeceras y la aplicación solo debe ser accesible a través de él. Haz que el proxy establezca `X-Real-IP` con la dirección desde la que recibió la conexión. Un proxy que solo añade valores a `X-Forwarded-For` permite que un cliente ponga cualquier dirección en primer lugar.

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

Caddy establece estas cabeceras por defecto. Cuando HTTPS funcione, cambia `NEXT_PUBLIC_APP_URL` y `BETTER_AUTH_URL` a la URL `https://`, actualiza las URL de callback de OAuth y vuelve a compilar.

### Content-Security-Policy [#content-security-policy]

Las compilaciones de producción envían una Content-Security-Policy en las páginas propias de QRdx: las páginas con sesión iniciada reciben un nonce de script nuevo en cada petición, y las páginas prerrenderizadas, una lista de hosts de scripts permitidos. Las páginas alojadas (`/p`) reciben una política laxa, porque ejecutan los píxeles de su propietario e incrustan contenido multimedia de cualquier origen. Si tu proxy inverso también establece `Content-Security-Policy`, los navegadores aplican ambas, así que omítela ahí. Define `CSP_REPORT_ONLY=1` para enviar la política en modo solo informe mientras compruebas una configuración nueva; `/api/csp-report` registra las infracciones. Añade `CSP_HTTPS=1` cuando sirvas por HTTPS fuera de Vercel, para que los navegadores actualicen cualquier recurso `http://`. Ambas se leen donde se ejecuta la aplicación y, para la cabecera de las páginas prerrenderizadas, donde se compila; el Dockerfile no las pasa a la compilación, así que añádelas también como argumentos de compilación si las páginas prerrenderizadas las necesitan.

## Actualizar QRdx [#update-qrdx]

Primero haz una copia de seguridad de la base de datos (ver más abajo). Después haz pull y vuelve a compilar. El servicio `migrate` sincroniza de nuevo el esquema antes de que arranque la aplicación.

```bash title="Terminal"
git pull
docker compose up -d --build
```

En la instalación manual, ejecuta `git pull`, `bun install` y `bun run db:push`, y después vuelve a compilar y reinicia.

Si un cambio de esquema eliminara datos, `drizzle-kit push` pide confirmación y el servicio `migrate` espera una respuesta que no puede obtener. En ese caso, ejecútalo en una terminal para revisar y confirmar los cambios:

```bash title="Terminal"
docker compose run --rm migrate
```

## Copia de seguridad y restauración [#back-up-and-restore]

Todo lo que almacena QRdx está en Postgres, excepto los archivos subidos, que están en tu bucket de R2. Haz un volcado de la base de datos antes de cada actualización y de forma periódica:

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Para restaurar en una base de datos vacía:

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Con Neon, usa sus propias copias de seguridad y ramas.

## Qué es diferente de qrdx.dev [#what-is-different-from-qrdxdev]

- **Los documentos** se abren en qrdx.dev. Tu instancia redirige allí todas las URL de la documentación.
- **Los pagos y los planes** requieren Polar. Sin él, todas las cuentas tienen los límites del plan Gratis y nadie puede mejorar de plan. Los límites están en `apps/app/lib/plans.ts`, que puedes modificar para tu instancia.
- **El programa de afiliados, las solicitudes de pago con factura, los descuentos para organizaciones sin ánimo de lucro y el formulario de contacto para empresas** son ventas propias de QRdx y solo funcionan donde se ejecuta el propio QRdx. Una copia autoalojada no incluye ninguno.
- **Ubicaciones de los escaneos:** el país, la región y la ciudad provienen de las cabeceras de geolocalización de Vercel. Detrás de Cloudflare solo se lee el país (`CF-IPCountry`); en otros casos las ubicaciones aparecen como desconocidas, y las [reglas por zona](/docs/precise-location#route-scans-by-area) solo coinciden con escaneos que comparten su ubicación.
- **Los dominios personalizados** se verifican con un registro DNS `TXT` y los enruta tu proxy inverso, salvo que uses Vercel con las variables de la Domains API configuradas. El botón **Configurar con …** necesita tu propia plantilla de Domain Connect: la de QRdx solo funciona para qrdx.dev.
- **Los bots de chat y las integraciones** requieren cada uno una aplicación que registres en ese servicio (consulta la tabla anterior).
- **Las páginas de administración** las sirve la propia aplicación; qrdx.dev redirige algunas a una consola independiente mediante proxy.

## Solución de problemas [#troubleshooting]

### "Invalid environment variables" al arrancar [#invalid-environment-variables-on-startup]

El registro nombra cada variable que falta o no es válida y luego indica dónde configurarla. Falta un valor obligatorio, o uno opcional tiene un valor no válido: una URL que no es una dirección completa `http://` o `https://`, o un secreto demasiado corto. Un valor vacío se considera sin definir y no da problemas. Corrige en `.env` las variables indicadas y vuelve a crear el contenedor con `docker compose up -d app`.

### Error de `redirect_uri` en OAuth [#oauth-redirect_uri-mismatch]

La URL de callback de tu aplicación OAuth debe ser exactamente `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` o `/api/auth/callback/google`. Define `BETTER_AUTH_URL` con la misma URL base que `NEXT_PUBLIC_APP_URL`.

### La aplicación no puede acceder a la base de datos (`fetch failed`) [#the-app-cant-reach-the-database-fetch-failed]

Con Postgres sin más, `DATABASE_HTTP_ENDPOINT` debe apuntar al proxy en ejecución. Comprueba que `docker compose ps db-proxy` lo muestre en ejecución.

### `migrate` nunca termina [#migrate-never-finishes]

`drizzle-kit push` está esperando una confirmación. Ejecuta `docker compose run --rm migrate` en una terminal y respóndela; consulta [Actualizar QRdx](#update-qrdx).

### Un valor modificado de `NEXT_PUBLIC_*` no surte efecto [#a-changed-next_public_-value-has-no-effect]

Vuelve a compilar la imagen: `docker compose up -d --build`.

### El puerto 4444 ya está en uso [#port-4444-is-already-in-use]

Cambia la asignación de puertos de `db-proxy` en `docker-compose.yml`. Solo lo usa el desarrollo local en el host.

### "the --mount option requires BuildKit" [#the---mount-option-requires-buildkit]

Tu Docker no tiene BuildKit. Instala el plugin `buildx` o actualiza Docker.

### La compilación se detiene con `Killed` o con el código de salida 137 [#the-build-stops-with-killed-or-exit-code-137]

Docker se quedó sin memoria. Dale al menos 8 GB (Docker Desktop: **Settings** → **Resources**) y ejecuta de nuevo `docker compose up -d --build`.

### "sign-in code email is off for this deployment" [#sign-in-code-email-is-off-for-this-deployment]

Los códigos por correo no se envían mientras `NEXT_PUBLIC_APP_URL` sea `localhost`. Usa el inicio de sesión con GitHub o Google para una prueba local.

¿Sigues atascado? [Abre una incidencia](https://github.com/qrdxinc/qrdx/issues) con la salida de `docker compose logs app`, sin los secretos.

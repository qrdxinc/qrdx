Ao final deste guia, você terá o QRdx rodando na sua própria URL: o editor de QR code, contas, QR codes dinâmicos com análises de leituras, páginas hospedadas, workspaces e temas salvos, tudo em um banco Postgres que você controla. O caminho com Docker Compose leva cerca de meia hora, a maior parte na primeira build da imagem.

O app web é open source sob a licença AGPL-3.0. Duas partes não são: o login único (SSO) do workspace e o log de auditoria ficam nas pastas `ee/`, sob a licença comercial do QRdx, e permanecem desativados a menos que você defina uma chave de licença (`QRDX_EE_LICENSE`). Usá-los em produção exige um acordo por escrito com o QRdx; veja [LICENSING.md](https://github.com/qrdxinc/qrdx/blob/main/LICENSING.md). Você não precisa de nada disso para usar a [biblioteca React `qrdx`](/docs/getting-started) ou a [CLI](/docs/developers/cli): elas rodam em qualquer lugar sem backend, sob a licença MIT. A página [Open source no QRdx](/open-source-qr-code-generator) lista cada parte do repositório e sua licença.

## Antes de começar [#before-you-start]

- Docker com Compose v2 e BuildKit (o Docker Desktop e o Docker Engine atual incluem os dois), ou Node.js 22 (22.22.3 ou posterior) e [Bun](https://bun.com/docs/installation) 1.4 para a configuração manual.
- Pelo menos 8 GB de memória para o Docker durante a build da imagem.
- Uma forma de fazer login, para que as contas possam ser criadas: um app OAuth do GitHub ou do Google, ou o [Resend](https://resend.com) para códigos de login por e-mail. Os códigos de login só são enviados por e-mail quando `NEXT_PUBLIC_APP_URL` não é `localhost`. O `bun run dev` os mostra no terminal, mas a imagem Docker não, então um teste local com Docker precisa de login com GitHub ou Google.
- Postgres: o contêiner incluído no `docker-compose.yml` ou um banco [Neon](https://neon.tech).
- Para qualquer uso além de um teste local, um domínio e um proxy reverso que encerre o HTTPS.

A documentação não faz parte de uma instância auto-hospedada. Sua instância envia todos os links da documentação (`/docs` e as páginas abaixo dele, suas cópias em Markdown e `/llms-full.txt`) para as mesmas páginas em qrdx.dev.

### Como funciona a conexão com o banco de dados [#how-the-database-connection-works]

O app fala com o Postgres pelo driver HTTP serverless da Neon.

- **Neon:** funciona direto. Defina `DATABASE_URL` com a sua string de conexão da Neon.
- **Postgres comum:** precisa de um proxy HTTP compatível com a Neon na frente dele. O `docker-compose.yml` roda um ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) e define `DATABASE_HTTP_ENDPOINT` para que o app envie suas consultas para lá.

O schema vem de `packages/database/schema.ts` e é aplicado com `drizzle-kit push`. Não há arquivos de migração para rodar manualmente.

## Início rápido com Docker Compose [#quick-start-with-docker-compose]

### 1. Clone o repositório [#1-clone-the-repository]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
```

### 2. Configure o ambiente [#2-configure-the-environment]

Copie o arquivo de exemplo para a raiz do repositório, onde o Compose o lê, e gere o segredo de sessão:

```bash title="Terminal"
cp apps/app/.env.example .env
openssl rand -base64 32
# prints a 44-character string: paste it as BETTER_AUTH_SECRET below
```

Abra o `.env` e defina estes valores. Todas as outras linhas podem continuar comentadas.

```bash title=".env"
NEXT_PUBLIC_APP_URL=https://qr.example.com
BETTER_AUTH_URL=https://qr.example.com
BETTER_AUTH_SECRET=<the string openssl printed>

# One sign-in provider. The callback URL for GitHub is
# <NEXT_PUBLIC_APP_URL>/api/auth/callback/github
GITHUB_CLIENT_ID=<client ID of your GitHub OAuth app>
GITHUB_CLIENT_SECRET=<its client secret>
```

De onde vem cada valor:

| Variável | Onde obter |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | A URL pública da sua instância, sem barra no final. Mantenha `http://localhost:3000` para um teste local. |
| `BETTER_AUTH_URL` | O mesmo valor. Descomente a linha. |
| `BETTER_AUTH_SECRET` | A saída de `openssl rand -base64 32`. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | Um [app OAuth do GitHub](https://github.com/settings/developers) cuja URL de callback seja `<your url>/api/auth/callback/github`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | No lugar do GitHub: um [cliente OAuth do Google](https://console.cloud.google.com/apis/credentials) cujo URI de redirecionamento seja `<your url>/api/auth/callback/google`. |

Deixe `DATABASE_URL` como está: o Compose aponta o app para o próprio contêiner Postgres e ignora o valor do `.env`. Para mudar a senha do banco, defina `POSTGRES_PASSWORD` antes da primeira inicialização.

### 3. Inicie a stack [#3-start-the-stack]

```bash title="Terminal"
docker compose up -d --build
```

Isso faz a build da imagem, inicia o Postgres e o proxy, roda o serviço `migrate` de execução única (`drizzle-kit push`) e depois inicia o app na porta 3000. A primeira build leva vários minutos. Quando terminar, os quatro serviços ficam assim:

```text title="docker compose ps (columns trimmed)"
NAME              SERVICE    STATUS
qrdx-db-1         db         running (healthy)
qrdx-db-proxy-1   db-proxy   running
qrdx-migrate-1    migrate    exited (0)
qrdx-app-1        app        running
```

O `migrate` foi feito para encerrar: ele sincroniza o schema e para. Para acompanhar a sincronização do schema e a inicialização do app:

```bash title="Terminal"
docker compose logs -f migrate app
```

### 4. Faça login [#4-sign-in]

Abra `NEXT_PUBLIC_APP_URL` no navegador e faça login com GitHub, Google ou um código por e-mail. Sua conta é criada no primeiro login.

### 5. Torne-se admin [#5-make-yourself-an-admin]

Adicione ao `.env` o endereço de e-mail da conta que você criou no passo 4:

```bash title=".env"
ADMIN_EMAILS=you@example.com
```

Recrie o contêiner do app para que ele leia a mudança, depois faça login e abra `/admin`:

```bash title="Terminal"
docker compose up -d app
```

O endereço se torna admin na primeira vez que abre `/admin`. O `ADMIN_USER_IDS` funciona da mesma forma, com IDs de usuário.

## Use a Neon ou outro Postgres gerenciado [#use-neon-or-another-managed-postgres]

Você pode dispensar o Postgres incluído e rodar apenas a imagem do app. Defina `DATABASE_URL` no `.env` com a sua string de conexão da Neon e deixe `DATABASE_HTTP_ENDPOINT` sem definir.

```bash title="Terminal"
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Aplique o schema uma vez, e de novo a cada atualização, com a imagem do migrador:

```bash title="Terminal"
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Configuração manual com Node.js [#manual-setup-with-nodejs]

```bash title="Terminal"
git clone https://github.com/qrdxinc/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local   # then edit it as in step 2

bun run db:push                                # apply the schema
bun run --filter app dev                       # http://localhost:3000
```

Para produção, faça a build e inicie o app:

```bash title="Terminal"
bun x turbo build --filter=app
bun run --filter app start
```

O `bun run db:push` se conecta com o driver da Neon, então precisa de um banco Neon. Para usar o Postgres do Docker no desenvolvimento local, inicie-o com `docker compose up -d db db-proxy`, aplique o schema com `docker compose run --rm migrate` e defina isto em `apps/app/.env.local`:

```bash title="apps/app/.env.local"
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

<Callout type="info" title="Os valores NEXT_PUBLIC_* são fixados no build">
  Os valores `NEXT_PUBLIC_*` são embutidos no bundle do navegador quando o app é compilado, então alterar um deles exige recompilar. O build do Docker lê o `.env` apenas para seis deles, passados como argumentos de build no `docker-compose.yml`: `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`, `NEXT_PUBLIC_FEATUREBASE_APP_ID` e os dois ids de produto do Pro. Para definir outra variável na imagem Docker (os ids de produto do Business, `NEXT_PUBLIC_QRDX_EUR_PRICES`, `NEXT_PUBLIC_SHORT_LINK_BASE_URL`, a site key do Turnstile ou os ids do Umami), adicione-a em `build.args` do serviço `app` no `docker-compose.yml` e como um `ARG` no estágio de build do Dockerfile, e depois execute `docker compose up -d --build`. A instalação manual lê todas elas de `apps/app/.env.local`.
</Callout>

### Jobs agendados [#scheduled-jobs]

Duas rotas fazem o trabalho recorrente: `/api/cron/webhooks` tenta de novo as entregas de webhook que falharam e apaga registros antigos do log de auditoria, e `/api/cron/digest` envia o resumo semanal. Na Vercel, o `apps/app/vercel.json` agenda as duas. Em qualquer outro lugar, nada as chama até que você mesmo o faça. Defina `CRON_SECRET` e chame as duas pelo seu agendador usando esse valor:

```text title="crontab (times in UTC)"
0 4 * * *  curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://qr.example.com/api/cron/webhooks
0 9 * * 1  curl -fsS -H "Authorization: Bearer $CRON_SECRET" "https://qr.example.com/api/cron/digest?shard=all"
```

Sem o header, as rotas respondem `401` em produção. [Notificações](/docs/notifications#self-hosting) explica o parâmetro `shard` do resumo.

## Proxy reverso e HTTPS [#reverse-proxy-and-https]

Coloque o app atrás de um proxy reverso, como Caddy, nginx ou Traefik, que encerre o TLS, e não exponha a porta 3000 diretamente à internet. O limite de requisições, os e-mails de segurança e o [log de auditoria](/docs/help/teams/audit-log) leem o IP do cliente primeiro de `X-Real-IP` e depois do primeiro endereço de `X-Forwarded-For` (na Vercel, `X-Vercel-Forwarded-For` entra no meio). Por isso, o proxy precisa definir esses cabeçalhos e o app só deve ser acessível por ele. Faça o proxy definir `X-Real-IP` com o endereço de onde recebeu a conexão. Um proxy que apenas acrescenta valores a `X-Forwarded-For` permite que o cliente coloque qualquer endereço na frente.

```nginx title="nginx server block (the relevant lines)"
location / {
  proxy_pass http://127.0.0.1:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

O Caddy define esses cabeçalhos por padrão. Quando o HTTPS estiver funcionando, altere `NEXT_PUBLIC_APP_URL` e `BETTER_AUTH_URL` para a URL com `https://`, atualize as URLs de callback do OAuth e faça o rebuild.

### Content-Security-Policy [#content-security-policy]

Os builds de produção enviam uma Content-Security-Policy nas páginas do próprio QRdx: as páginas com login recebem um nonce de script novo a cada requisição, e as páginas pré-renderizadas recebem uma lista de hosts de script permitidos. As páginas hospedadas (`/p`) recebem uma política flexível, porque executam os pixels do dono e incorporam mídia de qualquer lugar. Se o seu proxy reverso também define `Content-Security-Policy`, os navegadores aplicam as duas, então deixe de fora no proxy. Defina `CSP_REPORT_ONLY=1` para enviar a política apenas como relatório enquanto você verifica uma configuração nova; as violações são registradas em `/api/csp-report`. Adicione `CSP_HTTPS=1` quando você servir por HTTPS fora da Vercel, para que os navegadores atualizem qualquer recurso `http://`. As duas variáveis são lidas onde o app roda e, no caso do cabeçalho das páginas pré-renderizadas, onde ele é compilado; o Dockerfile não as repassa ao build, então adicione-as também como argumentos de build se as páginas pré-renderizadas precisarem delas.

## Atualizar o QRdx [#update-qrdx]

Faça o backup do banco de dados primeiro (veja abaixo). Depois, faça o pull e o rebuild. O serviço `migrate` sincroniza o schema de novo antes de o app iniciar.

```bash title="Terminal"
git pull
docker compose up -d --build
```

Na configuração manual, execute `git pull`, `bun install` e `bun run db:push`, depois faça o rebuild e reinicie.

Se uma mudança de schema apagar dados, o `drizzle-kit push` pede confirmação e o serviço `migrate` fica esperando uma resposta que não consegue receber. Nesse caso, execute-o em um terminal para revisar e confirmar as mudanças:

```bash title="Terminal"
docker compose run --rm migrate
```

## Backup e restauração [#back-up-and-restore]

Tudo o que o QRdx guarda está no Postgres, exceto os arquivos enviados, que ficam no seu bucket R2. Faça o dump do banco de dados antes de cada atualização e também de forma agendada:

```bash title="Terminal"
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Para restaurar em um banco de dados vazio:

```bash title="Terminal"
docker compose exec -T db psql -U postgres qrdx < qrdx-backup.sql
```

Com o Neon, use os backups e o branching dele.

## O que é diferente do qrdx.dev [#what-is-different-from-qrdxdev]

- **A documentação** fica no qrdx.dev. Sua instância redireciona todas as URLs da documentação para lá.
- **Pagamentos e planos** precisam do Polar. Sem ele, todas as contas têm os limites do plano Grátis e ninguém consegue fazer upgrade. Os limites ficam em `apps/app/lib/plans.ts`, que você pode alterar na sua instância.
- **O programa de afiliados, os pedidos de pagamento por fatura, os descontos para organizações sem fins lucrativos e o formulário de contato enterprise** são vendas do próprio QRdx e só funcionam onde o próprio QRdx roda. Uma cópia self-hosted não tem nenhum deles.
- **Locais das leituras:** país, região e cidade vêm dos cabeçalhos de geolocalização da Vercel. Atrás da Cloudflare, só o país é lido (`CF-IPCountry`); em outros lugares, os locais aparecem como desconhecidos, e as [regras por área](/docs/precise-location#route-scans-by-area) só correspondem a leituras com localização compartilhada.
- **Domínios personalizados** são verificados com um registro DNS `TXT` e roteados pelo seu proxy reverso, a menos que você rode na Vercel com as variáveis da Domains API definidas. O botão **Configurar com …** precisa do seu próprio template do Domain Connect: o do QRdx só funciona para o qrdx.dev.
- **Bots de chat e integrações** precisam, cada um, de um app que você registra no serviço correspondente (veja a tabela acima).
- **As páginas de admin** são servidas pelo próprio app; o qrdx.dev encaminha algumas delas para um console separado.

## Solução de problemas [#troubleshooting]

### "Invalid environment variables" ao iniciar [#invalid-environment-variables-on-startup]

O log mostra o nome de cada variável ausente ou inválida e depois diz onde defini-la. Falta um valor obrigatório, ou um valor opcional foi definido com algo inválido: uma URL que não é um endereço completo `http://` ou `https://`, ou um segredo curto demais. Um valor vazio conta como não definido e não causa problema. Corrija as variáveis citadas no `.env` e recrie o contêiner com `docker compose up -d app`.

### `redirect_uri` do OAuth não confere [#oauth-redirect_uri-mismatch]

A URL de callback no seu app OAuth deve ser exatamente `<NEXT_PUBLIC_APP_URL>/api/auth/callback/github` ou `/api/auth/callback/google`. Defina `BETTER_AUTH_URL` com a mesma URL base de `NEXT_PUBLIC_APP_URL`.

### O app não consegue acessar o banco de dados (`fetch failed`) [#the-app-cant-reach-the-database-fetch-failed]

Com Postgres puro, `DATABASE_HTTP_ENDPOINT` precisa apontar para o proxy em execução. Verifique se `docker compose ps db-proxy` mostra que ele está rodando.

### O `migrate` nunca termina [#migrate-never-finishes]

O `drizzle-kit push` está esperando uma confirmação. Execute `docker compose run --rm migrate` em um terminal e responda; veja [Atualizar o QRdx](#update-qrdx).

### Um valor `NEXT_PUBLIC_*` alterado não tem efeito [#a-changed-next_public_-value-has-no-effect]

Refaça o build da imagem: `docker compose up -d --build`.

### A porta 4444 já está em uso [#port-4444-is-already-in-use]

Altere o mapeamento de porta do `db-proxy` em `docker-compose.yml`. Só o desenvolvimento local no host usa essa porta.

### "the --mount option requires BuildKit" [#the---mount-option-requires-buildkit]

Seu Docker não tem BuildKit. Instale o plugin `buildx` ou atualize o Docker.

### O build para com `Killed` ou código de saída 137 [#the-build-stops-with-killed-or-exit-code-137]

O Docker ficou sem memória. Dê a ele pelo menos 8 GB (Docker Desktop: **Settings** → **Resources**) e execute `docker compose up -d --build` de novo.

### "sign-in code email is off for this deployment" [#sign-in-code-email-is-off-for-this-deployment]

Os códigos por e-mail não são enviados enquanto `NEXT_PUBLIC_APP_URL` for `localhost`. Use o login com GitHub ou Google para um teste local.

Ainda travado? [Abra uma issue](https://github.com/qrdxinc/qrdx/issues) com a saída de `docker compose logs app`, sem os segredos.

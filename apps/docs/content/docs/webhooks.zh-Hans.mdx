读完本页后，你控制的 URL 会在你所选的每个事件发生后几分钟内收到一个带签名的 `POST` 请求，你的服务器会验证每个请求确实来自 QRdx，你也会了解重试、重复投递和投递日志的行为。

Webhooks 会在事件发生时，将工作区中的事件推送到你的服务器：有人填写表单时更新 CRM，某个二维码的扫描次数达到 1,000 时在内部工具中发消息，或者自行保存一份扫描数据。

<Callout type="info" title="Business 方案">
Webhooks、Zapier 和 Make 的 hook，以及 Slack 和 Discord 提醒，都属于 **Business** 方案。邮件提醒和每周摘要属于 Pro；参见[通知](/docs/notifications)。方案对比请见[方案与限额](/docs/plans-and-limits)。
</Callout>

## 开始之前 [#before-you-start]

- 一个能响应 `POST` 请求的公开 `https://` URL。IP 地址、`localhost` 以及解析到私有网络的主机名都会被拒绝，并且不会跟随重定向。本地开发时，请使用能提供公开主机名的隧道。
- 在工作区中拥有所有者或管理员角色。成员可以查看端点及其投递日志，但不能添加或更改端点。

## 1. 添加端点 [#1-add-an-endpoint]

1. 在你想接收事件的工作区中打开[设置 → Webhooks](/dashboard?to=settings/webhooks)。该链接会打开你上次使用的工作区；在工作区切换器中选择其他工作区，仍会停留在同一页面。
2. 选择 **Add endpoint**，输入 **Endpoint URL** 并勾选所需的 **Events**，然后在对话框中选择 **Add endpoint**。QRdx 会先要求你[确认是你本人操作](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)；之后每次更改端点的 URL 时也会再次要求确认，而更改事件或停用端点则不需要。
3. 复制保存后显示的 **Signing secret**。所有者和管理员可以在端点的 **Deliveries** 页面再次显示或轮换它。
4. 选择 **Send test**。QRdx 会发送一个带签名的 `ping` 事件，并在投递日志中显示响应状态。

## 2. 选择事件 [#2-pick-the-events]

| 事件 | 触发时机 | 说明 |
| --- | --- | --- |
| `scan.created` | 动态二维码被扫描 | 批量发送：每个端点每分钟最多一个请求，最多包含 100 次扫描以及准确的 `count` |
| `scan.milestone` | 二维码的第 1 次扫描，然后是 10、100、500、1,000、5,000、10,000、50,000、100,000、500,000 和 1,000,000 次扫描，之后每满一百万次 | 每个里程碑只触发一次 |
| `code.created` | 在控制台或通过 API 创建动态二维码 | 每个二维码一个事件，批量创建时也是如此 |
| `code.updated` | 二维码的目标地址、标题、设计或短链接域名发生更改 | `changes` 列出相关字段 |
| `form.submitted` | 有人在托管页面上提交表单 | 包含填写的答案 |
| `ping` | 你选择 **Send test** | |

机器人、链接预览和预取器产生的扫描，以及同一访客的快速重复扫描，都不会被计入，也不会触发事件，这与[扫描分析](/docs/dynamic-qr-codes#scan-analytics)中的规则完全一致。

## 3. 读取负载 [#payloads]

每个请求都是带 JSON 正文的 `POST`，并包含以下标头：

| 标头 | 值 |
| --- | --- |
| `Content-Type` | `application/json` |
| `User-Agent` | `QRdx-Webhooks/1.0 (+https://qrdx.dev/docs/webhooks)` |
| `X-QRdx-Event` | 事件类型，例如 `code.created` |
| `X-QRdx-Delivery` | 投递 ID：每次重试都相同，因此你可以忽略重复项 |
| `X-QRdx-Timestamp` | 本次尝试签名时的 Unix 秒数 |
| `X-QRdx-Signature` | `t=<timestamp>,v1=<hex HMAC-SHA256>` |

正文始终是一个包含 `id`、`type`、`created_at` 和 `data` 的信封：

```json title="code.created"
{
  "id": "evt_cm3x8c1a20001",
  "type": "code.created",
  "created_at": "2026-10-31T09:30:00.000Z",
  "data": {
    "code": {
      "id": "cm3x7q2l40000",
      "slug": "aB3dE5f",
      "title": "Spring menu",
      "short_link": "https://qrdx.dev/q/aB3dE5f",
      "destination_url": "https://example.com/menu",
      "status": "active",
      "scan_count": 0,
      "created_at": "2026-10-31T09:30:00.000Z",
      "updated_at": "2026-10-31T09:30:00.000Z"
    },
    "actor_id": "user_123"
  }
}
```

一个 `scan.created` 批次：

```json title="scan.created"
{
  "id": "evt_cm3x9d0b10002",
  "type": "scan.created",
  "created_at": "2026-10-31T09:31:00.000Z",
  "data": {
    "window_started_at": "2026-10-31T09:31:00.000Z",
    "window_seconds": 60,
    "count": 2,
    "scans": [
      {
        "scan_id": "cm3x9d0b00001",
        "code": { "id": "cm3x7q2l40000", "slug": "aB3dE5f", "title": "Spring menu" },
        "scanned_at": "2026-10-31T09:31:00.000Z",
        "country": "DE",
        "region": "BE",
        "city": "Berlin",
        "device_type": "mobile",
        "os": "iOS",
        "browser": "Safari",
        "referer": null,
        "source": "qr"
      }
    ]
  }
}
```

如果一分钟内到达的扫描超过 100 次，`scans` 只包含前 100 次，`count` 则是准确的总数。轻触 [NFC 标签](/docs/nfc)时 `source` 为 `nfc`，扫描二维码时为 `qr`。扫描负载绝不包含 IP 地址或访客哈希值。

其他事件包含：

- `scan.milestone`：`milestone`、`code`（`id`、`slug`、`title`、`scan_count`）以及达到该里程碑的 `scan`。
- `code.updated`：与 `code.created` 相同，另加 `changes`，例如 `["destination_url"]`。
- `form.submitted`：`response_id`、`page`（`id`、`title`）、`code`（`id`、`slug`，或 `null`）、`fields`（`name`、`label`、文本形式的 `value`）以及 `submitted_at`。

如果想在第一个真实事件到来之前，查看用你自己的数据生成的各事件负载，请调用[获取示例事件](/docs/developers/api/get-hook-samples)：

```bash title="Terminal"
curl "https://api.qrdx.dev/v1/hooks/sample?event=scan.created" \
  -H "Authorization: Bearer $QRDX_API_KEY"
```

## 4. 验证签名 [#verify-signatures]

使用你的签名密钥对 `<timestamp>.<raw body>` 计算 HMAC-SHA256，并与 `X-QRdx-Signature` 中的 `v1` 比较。请使用原始请求正文，即在任何 JSON 解析之前的内容，并拒绝时间戳早于五分钟的请求。

```ts title="lib/qrdx-webhook.ts"
import { createHmac, timingSafeEqual } from "node:crypto";

export function isFromQRdx(rawBody: string, header: string, secret: string) {
  const parts = Object.fromEntries(
    header.split(",").map((part) => part.trim().split("=", 2)),
  );
  const timestamp = Number(parts.t);
  if (!timestamp || Math.abs(Date.now() / 1000 - timestamp) > 300) return false;

  const expected = createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");
  const received = Buffer.from(parts.v1 ?? "");
  return (
    received.length === expected.length &&
    timingSafeEqual(received, Buffer.from(expected))
  );
}
```

```python title="qrdx_webhook.py"
import hmac
import hashlib
import time


def is_from_qrdx(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(part.strip().split("=", 1) for part in header.split(","))
    timestamp = int(parts.get("t", "0"))
    if not timestamp or abs(time.time() - timestamp) > 300:
        return False
    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(parts.get("v1", ""), expected)
```

轮换密钥会立即生效：旧密钥将无法再通过验证，因此轮换后请马上更新你的服务器。

## 5. 响应与处理重试 [#5-respond-and-handle-retries]

请在 10 秒内返回任意 `2xx` 状态码。其他情况（错误状态码、重定向、超时、主机无法访问）都算作失败，QRdx 会按逐渐增长的间隔重试，约为 1 分钟、4 分钟、16 分钟、1 小时、4 小时、17 小时和 24 小时。每次重试会在等待结束后的几分钟内发出。总共 8 次尝试，历时大约两天，之后该投递会被标记为失败。

投递可能会重复到达（响应缓慢后的重试、手动重试），也可能乱序到达。请使用 `X-QRdx-Delivery` 或信封中的 `id` 忽略重复项；如果处理耗时超过几秒，请在返回 `2xx` 之后再执行。

## 之后如何更改 [#change-it-later]

每个端点的 **Deliveries** 页面会列出最近 50 次投递，包括其事件、状态、尝试次数和负载。**Retry now** 会立即重新发送失败或待处理的投递；**Send again** 会重新发送已送达的投递。投递记录保留 30 天。

<Shot id="webhook-deliveries" />

在端点的菜单中，你可以 **Edit** 其 URL 和事件，**Disable endpoint**（停止新的投递；**Enable endpoint** 可恢复），显示或 **Rotate** 其 **Signing secret**，以及 **Delete** 该端点，同时也会删除它的日志。如果工作区的方案不再包含 webhooks，端点会保留，但在重新升级到 Business 之前不会发送任何内容。无论哪种情况，你的二维码都会继续正常工作。

## Zapier、Make 和 n8n（REST Hooks）[#zapier-make-and-n8n-rest-hooks]

自动化工具可以通过 REST Hooks API 自行订阅和取消订阅。请使用 [API 密钥](/docs/developers/api-keys)或 OAuth 访问令牌进行身份验证：订阅或取消订阅需要 `codes:write`，列出需要 `codes:read`。Hook URL 通常是保密的，因此仅有 `codes:read` 时，`target_url` 只显示主机部分（`https://hooks.zapier.com`）。令牌请求作用于你自己的工作区；密钥则作用于创建它的工作区。如果改用已登录的浏览器会话订阅，系统会先要求你[确认是你本人操作](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)，在最近 10 分钟内未确认时会返回 `403 CONFIRMATION_REQUIRED`。订阅就是普通的端点：它们会出现在 **Settings → Webhooks** 中，你也可以在那里将其移除。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/v1/hooks` | 订阅。正文：`target_url`（或 Zapier 的 `hookUrl`）和 `event`（或 `events` 数组）。返回 `201`，附带订阅的 `id` 及其 `secret` |
| `DELETE` | `/v1/hooks/{id}` | 取消订阅（`204`） |
| `GET` | `/v1/hooks` | 列出订阅和端点 |
| `GET` | `/v1/hooks/{id}` | 单个订阅 |
| `GET` | `/v1/hooks/sample?event=<event>` | `event` 最近的示例负载，以数组形式返回（Zapier 的 "perform list"） |

```bash title="Terminal"
curl https://api.qrdx.dev/v1/hooks \
  -H "Authorization: Bearer $QRDX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"target_url": "https://hooks.zapier.com/hooks/standard/123/abc/", "event": "form.submitted"}'
```

```json title="201 Created (fields)"
{
  "id": "<hook id>",
  "target_url": "https://hooks.zapier.com/hooks/standard/123/abc/",
  "events": ["form.submitted"],
  "event": "form.submitted",
  "active": true,
  "created_at": "<ISO 8601 time>",
  "secret": "whsec_<shown only here>"
}
```

没有 Business 方案时，订阅调用会返回 `402`：

```json title="402 Payment Required"
{"code":"PLAN_REQUIRED","message":"Webhooks and Zapier/Make hooks are part of the Business plan.","status":402}
```

一次 `scan.created` 投递就是一个批次，因此在 Zapier 中请使用 `data.scans` 的行项目来处理每次扫描。在 n8n 中，[QRdx 的 n8n 节点](/docs/developers/n8n)中的 QRdx Trigger 节点会替你发起这些调用并检查每个签名；普通的 Webhook 节点同样可用，设置方式与其他端点相同。参考页面有[订阅事件](/docs/developers/api/create-hook)、[列出 hooks](/docs/developers/api/list-hooks)和[取消订阅](/docs/developers/api/delete-hook)。

## 出现问题时 [#if-something-goes-wrong]

### 端点 URL 被拒绝 [#the-endpoint-url-is-refused]

只接受公开的 `https://` 主机名：不接受 `http://`、IP 地址、`localhost`，也不接受解析到私有网络的名称。开发期间请使用带公开主机名的隧道。

### 每次投递都显示失败状态 [#every-delivery-shows-a-failed-status]

你的服务器在 10 秒内返回了非 `2xx` 的响应、进行了重定向，或者没有响应。打开该投递的详情，查看确切的 HTTP 状态或错误，修复后选择 **Retry now**。如果你的处理程序较慢，请先返回 `2xx`，之后再处理。

### 签名验证不通过 [#signatures-dont-verify]

请确认你对原始请求正文计算哈希，而不是对重新序列化后的 JSON 对象计算，并且你的服务器使用的是当前密钥：轮换密钥后，旧密钥会立即失效。也请检查服务器的时钟，因为时间戳校验允许的误差为五分钟。

### 不再收到事件 [#events-stopped-arriving]

可能是工作区已退出 Business 方案（端点会保留，但会暂停），端点处于 **Disabled** 状态，或者创建该订阅的 Zap、场景或工作流已被关闭并取消订阅。请检查 **Settings → Webhooks**。

### `POST /v1/hooks` 返回 `403 CONFIRMATION_REQUIRED` [#403-confirmation_required-from-post-v1hooks]

你使用的是浏览器会话来订阅。请在 QRdx 中确认是你本人操作，并在 10 分钟内重试，或者在你的服务器上使用 API 密钥订阅。

## 自托管 [#self-hosting]

投递会立即发送；重试以及所属分钟已结束的扫描批次，则由定时任务发送。QRdx 通过 GitHub Actions 工作流每 5 分钟运行一次该任务，这种方式适用于 Vercel 的免费 Hobby 方案，同时 `apps/app/vercel.json` 也会每天完整运行一次。GitHub 可能会延迟启动定时运行，因此重试通常会在几分钟内完成，而不是精确到分钟。

要采用同样的做法，请复制 `.github/workflows/webhook-worker.yml`，将你的 `CRON_SECRET` 添加为 Actions 密钥，并将任务 URL 添加为变量 `WEBHOOK_WORKER_URL`。你也可以使用环境中设置的 `CRON_SECRET`，从任意调度器调用该任务：

```bash title="crontab (every 1 to 5 minutes)"
curl -H "Authorization: Bearer $CRON_SECRET" https://your-host/api/cron/webhooks
```

在 URL 后加上 `?source=github` 后，该任务会先检查 Upstash Redis 中的一个小标记；如果没有到期的内容，就会返回 `{"skipped": true}`，而不会查询数据库，因此可缩容至零的数据库可以保持休眠（没有 Upstash 时，它总是运行完整任务）。请保留每天一次不带该参数的调用：这次运行始终会执行完整任务并修复标记。其他定时任务列在[自托管](/docs/self-hosting#scheduled-jobs)中。

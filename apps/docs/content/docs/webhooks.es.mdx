Al terminar esta página, una URL que controlas recibirá un `POST` firmado pocos minutos después de cada evento que hayas elegido, tu servidor verificará que cada solicitud proviene de QRdx y sabrás cómo se comportan los reintentos, los duplicados y el registro de entregas.

Los webhooks envían a tu servidor los eventos de un espacio de trabajo en cuanto ocurren: actualiza un CRM cuando alguien rellene un formulario, publica en una herramienta interna cuando un código supere los 1.000 escaneos o conserva tu propia copia de los datos de escaneo.

<Callout type="info" title="Plan Business">
Los webhooks, los hooks de Zapier y Make, y las alertas de Slack y Discord forman parte del plan **Business**. Las alertas por correo y el resumen semanal forman parte de Pro; consulta [Notificaciones](/docs/notifications). Compara los planes en [Planes y límites](/docs/plans-and-limits).
</Callout>

## Antes de empezar [#before-you-start]

- Una URL pública `https://` que responda a solicitudes `POST`. Las direcciones IP, `localhost` y los nombres de host que resuelven a redes privadas se rechazan, y las redirecciones no se siguen. Para desarrollo local, usa un túnel que te dé un nombre de host público.
- Rol de propietario o administrador en el espacio de trabajo. Los miembros pueden ver los endpoints y sus registros de entregas, pero no añadirlos ni modificarlos.

## 1. Añade un endpoint [#1-add-an-endpoint]

1. Abre [Ajustes → Webhooks](/dashboard?to=settings/webhooks) en el espacio de trabajo cuyos eventos quieres recibir. El enlace abre el último espacio de trabajo que usaste; elige otro en el selector de espacios de trabajo y seguirás en la misma página.
2. Elige **Añadir endpoint**, introduce la **URL del endpoint** y marca los **Eventos** que quieras; luego elige **Añadir endpoint** en el cuadro de diálogo. Antes, QRdx te pide [confirmar que eres tú](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), y lo vuelve a pedir cada vez que cambias la URL de un endpoint; cambiar sus eventos o desactivarlo no lo pide.
3. Copia el **Secreto de firma** que aparece tras guardar. Los propietarios y administradores pueden mostrarlo de nuevo, o rotarlo, desde la página **Entregas** del endpoint.
4. Elige **Enviar prueba**. QRdx envía un evento `ping` firmado y muestra el estado de la respuesta en el registro de entregas.

## 2. Elige los eventos [#2-pick-the-events]

| Evento | Cuándo | Notas |
| --- | --- | --- |
| `scan.created` | Se escanea un código dinámico | Por lotes: como máximo una solicitud por minuto y endpoint, con hasta 100 escaneos y el `count` exacto |
| `scan.milestone` | El 1.er escaneo de un código, luego 10, 100, 500, 1.000, 5.000, 10.000, 50.000, 100.000, 500.000 y 1.000.000 de escaneos, y después cada millón | Se activa una vez por hito |
| `code.created` | Se crea un código dinámico, en el panel o mediante la API | Un evento por código, también en la creación masiva |
| `code.updated` | Cambia el destino, el título, el diseño o el dominio del enlace corto de un código | `changes` lista los campos |
| `form.submitted` | Alguien envía un formulario en una página alojada | Incluye las respuestas |
| `ping` | Eliges **Enviar prueba** | |

Los escaneos de bots, vistas previas de enlaces y precargadores, y las repeticiones rápidas de un mismo visitante no se cuentan ni activan eventos, igual que en el [análisis de escaneos](/docs/dynamic-qr-codes#scan-analytics).

## 3. Lee el payload [#payloads]

Cada solicitud es un `POST` con un cuerpo JSON y estas cabeceras:

| Cabecera | Valor |
| --- | --- |
| `Content-Type` | `application/json` |
| `User-Agent` | `QRdx-Webhooks/1.0 (+https://qrdx.dev/docs/webhooks)` |
| `X-QRdx-Event` | El tipo de evento, como `code.created` |
| `X-QRdx-Delivery` | ID de entrega: es el mismo en cada reintento, así que puedes ignorar duplicados |
| `X-QRdx-Timestamp` | Segundos Unix en que se firmó este intento |
| `X-QRdx-Signature` | `t=<timestamp>,v1=<hex HMAC-SHA256>` |

El cuerpo es siempre un envoltorio con `id`, `type`, `created_at` y `data`:

```json title="code.created"
{
  "id": "evt_cm3x8c1a20001",
  "type": "code.created",
  "created_at": "2026-10-31T09:30:00.000Z",
  "data": {
    "code": {
      "id": "cm3x7q2l40000",
      "slug": "aB3dE5f",
      "title": "Spring menu",
      "short_link": "https://qrdx.dev/q/aB3dE5f",
      "destination_url": "https://example.com/menu",
      "status": "active",
      "scan_count": 0,
      "created_at": "2026-10-31T09:30:00.000Z",
      "updated_at": "2026-10-31T09:30:00.000Z"
    },
    "actor_id": "user_123"
  }
}
```

Un lote de `scan.created`:

```json title="scan.created"
{
  "id": "evt_cm3x9d0b10002",
  "type": "scan.created",
  "created_at": "2026-10-31T09:31:00.000Z",
  "data": {
    "window_started_at": "2026-10-31T09:31:00.000Z",
    "window_seconds": 60,
    "count": 2,
    "scans": [
      {
        "scan_id": "cm3x9d0b00001",
        "code": { "id": "cm3x7q2l40000", "slug": "aB3dE5f", "title": "Spring menu" },
        "scanned_at": "2026-10-31T09:31:00.000Z",
        "country": "DE",
        "region": "BE",
        "city": "Berlin",
        "device_type": "mobile",
        "os": "iOS",
        "browser": "Safari",
        "referer": null,
        "source": "qr"
      }
    ]
  }
}
```

Cuando llegan más de 100 escaneos en un minuto, `scans` contiene los primeros 100 y `count` el total exacto. `source` es `nfc` para un toque en una [etiqueta NFC](/docs/nfc) y `qr` para un escaneo de QR. Los payloads de escaneo nunca incluyen direcciones IP ni hashes de visitantes.

Los demás eventos incluyen:

- `scan.milestone`: `milestone`, `code` (`id`, `slug`, `title`, `scan_count`) y el `scan` que lo alcanzó.
- `code.updated`: como `code.created`, más `changes`, por ejemplo `["destination_url"]`.
- `form.submitted`: `response_id`, `page` (`id`, `title`), `code` (`id`, `slug`, o `null`), `fields` (`name`, `label`, `value` como texto) y `submitted_at`.

Para ver un payload de cada evento construido con tus propios datos antes de que llegue el primero real, llama a [Obtener eventos de ejemplo](/docs/developers/api/get-hook-samples):

```bash title="Terminal"
curl "https://api.qrdx.dev/v1/hooks/sample?event=scan.created" \
  -H "Authorization: Bearer $QRDX_API_KEY"
```

## 4. Verifica las firmas [#verify-signatures]

Calcula un HMAC-SHA256 de `<timestamp>.<raw body>` con tu secreto de firma y compáralo con `v1` en `X-QRdx-Signature`. Usa el cuerpo de la solicitud sin procesar, antes de cualquier análisis JSON, y rechaza las marcas de tiempo con más de cinco minutos de antigüedad.

```ts title="lib/qrdx-webhook.ts"
import { createHmac, timingSafeEqual } from "node:crypto";

export function isFromQRdx(rawBody: string, header: string, secret: string) {
  const parts = Object.fromEntries(
    header.split(",").map((part) => part.trim().split("=", 2)),
  );
  const timestamp = Number(parts.t);
  if (!timestamp || Math.abs(Date.now() / 1000 - timestamp) > 300) return false;

  const expected = createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");
  const received = Buffer.from(parts.v1 ?? "");
  return (
    received.length === expected.length &&
    timingSafeEqual(received, Buffer.from(expected))
  );
}
```

```python title="qrdx_webhook.py"
import hmac
import hashlib
import time


def is_from_qrdx(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(part.strip().split("=", 1) for part in header.split(","))
    timestamp = int(parts.get("t", "0"))
    if not timestamp or abs(time.time() - timestamp) > 300:
        return False
    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(parts.get("v1", ""), expected)
```

La rotación del secreto surte efecto de inmediato: el secreto anterior deja de verificar, así que actualiza tu servidor justo después de rotarlo.

## 5. Responde y gestiona los reintentos [#5-respond-and-handle-retries]

Responde con cualquier estado `2xx` en un máximo de 10 segundos. Cualquier otra cosa (un estado de error, una redirección, un tiempo de espera agotado, un host inalcanzable) cuenta como fallo, y QRdx reintenta con esperas crecientes de aproximadamente 1 minuto, 4 minutos, 16 minutos, 1 hora, 4 horas, 17 horas y 24 horas. Cada reintento se envía pocos minutos después de que termine su espera. Son 8 intentos a lo largo de unos dos días, tras los cuales la entrega se marca como fallida.

Las entregas pueden llegar más de una vez (un reintento tras una respuesta lenta, un reintento manual) y desordenadas. Usa `X-QRdx-Delivery` o el `id` del envoltorio para ignorar duplicados, y haz tu trabajo después de responder `2xx` si tarda más de unos pocos segundos.

## Cámbialo más tarde [#change-it-later]

La página **Entregas** de cada endpoint muestra las últimas 50 entregas con su evento, estado, intentos y payload. **Reintentar ahora** reenvía de inmediato una entrega fallida o pendiente; **Enviar de nuevo** reenvía una ya entregada. Las entregas se conservan durante 30 días.

<Shot id="webhook-deliveries" />

Desde el menú de un endpoint puedes **Editar** su URL y sus eventos, **Desactivar endpoint** (las nuevas entregas se detienen; **Activar endpoint** las reanuda), mostrar o **Rotar** su **Secreto de firma**, y **Eliminar** el endpoint, lo que también borra su registro. Si el plan de un espacio de trabajo ya no incluye webhooks, los endpoints se conservan pero no se envía nada hasta que vuelva a tener Business. Tus códigos QR siguen funcionando en ambos casos.

## Zapier, Make y n8n (REST Hooks) [#zapier-make-and-n8n-rest-hooks]

Las herramientas de automatización pueden suscribirse y cancelar su suscripción por sí mismas mediante la API de REST Hooks. Autentícate con una [clave de API](/docs/developers/api-keys) o un token de acceso OAuth: `codes:write` para suscribirte o cancelar la suscripción, `codes:read` para listar. Las URL de los hooks suelen ser secretas, así que con `codes:read` solo, `target_url` muestra únicamente el host (`https://hooks.zapier.com`). Las solicitudes con token actúan sobre tu propio espacio de trabajo; una clave actúa sobre el espacio de trabajo en el que se creó. Si te suscribes con tu sesión iniciada en el navegador, antes se te pide [confirmar que eres tú](/docs/help/privacy-and-security/two-step-verification#confirm-its-you) y se responde `403 CONFIRMATION_REQUIRED` hasta que lo hayas hecho en los últimos 10 minutos. Las suscripciones son endpoints normales: aparecen en **Ajustes → Webhooks**, donde también puedes eliminarlas.

| Método | Ruta | Descripción |
| --- | --- | --- |
| `POST` | `/v1/hooks` | Suscribirse. Cuerpo: `target_url` (o `hookUrl` de Zapier) y `event` (o un array `events`). Devuelve `201` con el `id` de la suscripción y su `secret` |
| `DELETE` | `/v1/hooks/{id}` | Cancelar la suscripción (`204`) |
| `GET` | `/v1/hooks` | Listar suscripciones y endpoints |
| `GET` | `/v1/hooks/{id}` | Una suscripción |
| `GET` | `/v1/hooks/sample?event=<event>` | Payloads de ejemplo recientes para `event`, como un array («perform list» de Zapier) |

```bash title="Terminal"
curl https://api.qrdx.dev/v1/hooks \
  -H "Authorization: Bearer $QRDX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"target_url": "https://hooks.zapier.com/hooks/standard/123/abc/", "event": "form.submitted"}'
```

```json title="201 Created (fields)"
{
  "id": "<hook id>",
  "target_url": "https://hooks.zapier.com/hooks/standard/123/abc/",
  "events": ["form.submitted"],
  "event": "form.submitted",
  "active": true,
  "created_at": "<ISO 8601 time>",
  "secret": "whsec_<shown only here>"
}
```

Sin Business, la llamada de suscripción devuelve `402`:

```json title="402 Payment Required"
{"code":"PLAN_REQUIRED","message":"Webhooks and Zapier/Make hooks are part of the Business plan.","status":402}
```

Una entrega `scan.created` es un lote, así que en Zapier usa los elementos de línea `data.scans` para actuar sobre cada escaneo. En n8n, el nodo QRdx Trigger de los [nodos de QRdx para n8n](/docs/developers/n8n) hace estas llamadas por ti y comprueba cada firma; un nodo Webhook simple también sirve, configurado como cualquier otro endpoint. Las páginas de referencia son [Suscribirse a eventos](/docs/developers/api/create-hook), [Listar hooks](/docs/developers/api/list-hooks) y [Cancelar suscripción](/docs/developers/api/delete-hook).

## Si algo sale mal [#if-something-goes-wrong]

### Se rechaza la URL del endpoint [#the-endpoint-url-is-refused]

Solo se aceptan nombres de host públicos con `https://`: nada de `http://`, direcciones IP, `localhost` ni nombres que se resuelvan a una red privada. Mientras desarrollas, usa un túnel con un nombre de host público.

### Todos los envíos muestran el estado fallido [#every-delivery-shows-a-failed-status]

Tu servidor respondió con algo distinto de `2xx` en menos de 10 segundos, redirigió o no respondió. Abre los detalles del envío para ver el estado HTTP o el error exacto, corrígelo y elige **Reintentar ahora**. Si tu manejador es lento, responde primero `2xx` y procesa después.

### Las firmas no se verifican [#signatures-dont-verify]

Comprueba que calculas el hash del cuerpo bruto de la solicitud, no de un objeto JSON reserializado, y que tu servidor usa el secreto actual: al rotarlo, el anterior deja de ser válido al instante. Revisa también el reloj de tu servidor, ya que la comprobación de la marca de tiempo admite cinco minutos.

### Los eventos dejaron de llegar [#events-stopped-arriving]

El espacio de trabajo salió del plan Business (los endpoints se conservan, pero en pausa), el endpoint está **Desactivado**, o el Zap, el escenario o el flujo de trabajo que creó la suscripción se desactivó y canceló la suscripción. Revisa **Ajustes → Webhooks**.

### `403 CONFIRMATION_REQUIRED` en `POST /v1/hooks` [#403-confirmation_required-from-post-v1hooks]

Te suscribiste con una sesión del navegador. Confirma que eres tú en QRdx y vuelve a intentarlo en un plazo de 10 minutos, o suscríbete con una clave de API desde tu servidor.

## Autoalojamiento [#self-hosting]

Los envíos se realizan de inmediato; los reintentos y los lotes de escaneos cuyo minuto ya terminó los envía un trabajo programado. QRdx lo ejecuta cada 5 minutos desde un flujo de trabajo de GitHub Actions, que funciona en el plan Hobby gratuito de Vercel, y `apps/app/vercel.json` también lo ejecuta completo una vez al día. GitHub puede iniciar las ejecuciones programadas con retraso, así que espera los reintentos en unos pocos minutos, no al minuto exacto.

Para hacer lo mismo, copia `.github/workflows/webhook-worker.yml`, añade tu `CRON_SECRET` como secreto de Actions y la URL de tu trabajo como la variable `WEBHOOK_WORKER_URL`. O llama al trabajo desde cualquier programador con el `CRON_SECRET` que definiste en el entorno:

```bash title="crontab (every 1 to 5 minutes)"
curl -H "Authorization: Bearer $CRON_SECRET" https://your-host/api/cron/webhooks
```

Si añades `?source=github` a la URL, el trabajo primero consulta una pequeña marca en Upstash Redis y devuelve `{"skipped": true}` sin consultar la base de datos cuando no hay nada pendiente, de modo que una base de datos que escala a cero puede seguir inactiva (sin Upstash, siempre ejecuta el trabajo completo). Mantén una llamada al día sin él: esa ejecución siempre hace el trabajo completo y repara la marca. Los demás trabajos programados se enumeran en [Autoalojamiento](/docs/self-hosting#scheduled-jobs).
